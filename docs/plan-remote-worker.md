# Plan: Remote Worker and Open Work

This is the agreed plan for the remote worker and the work queue around it (user decisions 2026-09-28 and 2026-09-29). It is the reference for the next pull requests. Update it when a step is merged or a decision changes.

## 0. Principle

The extension sets up the worker and everything that the worker needs (whether Docker runs, the helper image, the start of the worker and its engine check, the test of a new host, the Docker contexts). From then on the worker is responsible for everything else on the Docker engine, commanded through operations: the extension decides, asks the user, keeps its local records, and sends operations; it runs no Docker action and no script itself. The only exception on purpose is the attach diagnostics, which checks what the local Docker CLI sees. (The user, 2026-10-03: "so we setup the worker an everything that is needed for it and then the worker is responsible for anything else commanded through operations".)

**One concept for commanding Docker, clean code** (the user, 2026-10-03: "assure that all the code architecture is clean and sound and deduplicated everywhere and that we use one concept for commanding docker and not here a script and there something different. Use a uniform approach for all the code"):
- **Engine:** in the worker, every action on the engine goes through one port, `DockerEngine`, implemented over the Docker Engine API on the socket (no `docker` CLI process of our own). The Docker CLI and Docker Compose run only as tools of the Dev Container CLI in the batch helper, and in the extension only for the bootstrap (over the user's Docker context).
- **Scripts in containers:** every script that runs in a container (the dev container, the batch helper, the monitor) is a named script of one registry in the bundle, with typed arguments, run through one primitive (`DockerEngine.exec`: exec create and start, arguments as positional parameters, input and secrets only on standard input, the output masked); no script text is built at a call site.
- **Operations:** the extension commands the worker only through the operations of section 3b, each with typed parameters, checked on both sides by one schema; no Docker command crosses the channel.
- **Effort where the code stays** (the user, 2026-10-03: "do not spend time on code that is going to be replaced", "but do test it when it is required later on", "test and review"): code that a later step replaces gets no extra tests or review rounds beyond what keeps CI green; its tests and its full reviews (defects and mutation testing) come with the step that makes it final.
- **No duplicates:** one function per fact (for example the containers of an environment, the volumes of an environment, the Git state), computed once per operation and passed on; code that a step replaces is removed in that step, and step 11I removes the rest.

## 1. Why

On a remote Docker host every Docker call of the extension opens its own SSH connection (about 1.6 s), and every helper step starts, runs and removes its own container. A first Start needs 15–30 such calls, including about 8 helper containers. The remote worker pays the connection once and runs the work next to the engine.

## 3b. Step 11: the worker as the deputy (design)

Decisions of 2026-10-03 (section 2): the extension sets up the worker; the worker runs every flow on its engine with all its logic; the extension keeps the UI, the local records, the local secrets, and the connect of the window. The call map of today is in [worker-call-map.md](worker-call-map.md).

**Where the code runs.** `src/core` has no `vscode` import, so the pipeline (`EnvironmentService`, `WorkspaceHelper`, the policy, the image check, the session code) runs unchanged in the worker's Node.js process, in its bundle (`dist/helperChannel.js`). Its Docker calls are local there (the engine's socket), so the many small calls of an open cost milliseconds instead of a round trip each; no batching of them is needed. They all go through the one port `DockerEngine` over the Engine API (section 0); 11B introduces it, with the exec primitive and the script registry, and moves the existing adapter calls onto it. The batch helper stays for the steps that need a process on the volume (clone, configuration reads, build, `up`, lifecycle commands), started by the worker as today. The helper image of an open is the worker's own image (it runs from it); its maintenance (rebuild, cleanup) leaves the lock and runs in the bootstrap and the background prebuild.

**Operations.** One per flow, each with its own parameters, never a Docker command: `open` (with `mode`: first, existing, rebuild, selectConfiguration, cloneAgain), `listConfigurations`, `stop`, `delete`, `deleteCheck`, `refresh`, `heartbeat`, `release`, `tokenRemove`, `windowState`, `reconcile`, `monitorSettings`, `vscodePrefetch` (11H). Each runs under the environment lock where today's flow takes it (the worker takes it itself); the lock stays held while a question is open (Q3).

**Requests from the worker (11A).** During an operation the worker sends `ask` messages and waits for the answer; a cancel ends the wait. Kinds:
- `question`: the questions of the call map (trust, files missing, kind changed, configuration changed, recreate, Delete's questions, the configuration pick); the extension shows them and answers.
- `local`: the window status, pending and busy files (`otherWindowOf`, `requireNoOtherWindow`), the remembered refused update; the extension reads them.
- `record`: the registry entry of the environment is a parameter of the operation; each change goes back as a specific operation that the extension applies under its registry lock (decision of 2026-10-04: one operations interface in both directions), only for the environment of the operation.
- `secret`: the GitHub token, the packages sign-in, the registry credentials of a host (`docker-credential-*` stays on the user's computer); the answer is a secret of the operation.
- (Decision A1 of 2026-10-05: no `connect` request; the operation `open` answers with the data that the window needs (container, folder; the user in its entry), and the extension connects the window after the lock is released.)

**Secrets.** A request carries several named secrets (11A); each is masked in every log line, output and error message of the worker (as today for one). The worker gets a secret only when it asks for it, so an operation without a clone or a pull never holds the token.

**Progress and log.** The worker's log lines and progress steps go to the Dev Environments output as today; the extension maps the steps to the progress notification.

**Worker setup.** Outbound network (the image check, the pulls, the downloads of 11H); the volumes it mounts: the socket, the monitor's state volume (locks), `devenv-vscode` (11H). The bootstrap does not change.

**Order and why.** 11A first (everything needs it). 11B moves the core into the worker with Stop and the token removal, the smallest flows, so the proxies are proven before the big ones. 11C and 11D move the remaining small flows. 11E moves the open, the largest. 11F removes what is left in the extension, so a bypass cannot be written (decision 1). 11G and 11H come next: they change what the worker does inside the open, not where it runs. 11I closes the step: the whole code base against section 0. Each PR moves whole flows (never half a flow), and the flows that are not moved yet keep working as today.

**Checks of each PR.** The usual ones; the unit tests of a moved flow run against the worker's code with a fake engine and a fake extension side (questions, records, secrets); the Docker tests of CI drive the flows end to end through a real worker; a live check on a remote host after 11B, 11E and 11H.
