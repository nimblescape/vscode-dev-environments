# Container restrictions

This document lists every restriction that Dev Environments applies to its dev containers, grouped by **who normally configures** the thing that the extension restricts. The requirements are in the concept ([vscode-dev-environments.md](vscode-dev-environments.md), section 9 "Host access" and "Accounts"); the technical decisions are in the [implementation notes](implementation-notes.md).

**Principle.** Nothing that configures the container may reach the computer, with three exceptions that the user decided to keep: the network (including VPN connections of the computer), ports of the container on `localhost` of the computer, and URLs that open in the computer's browser.

**Switch per repository.** The checks are on for every repository by default. The user setting `devEnvLauncher.hostAccessChecksOff` turns them off for the repositories that it lists; then only the refusals of access to the computer are lifted, and everything else in this document still applies. Section 12 lists the class of every refused item; section 13 does so for Docker Compose configurations.

**Kinds of restriction.**

| Kind | Meaning |
|---|---|
| Refused | Start stops with a message that names each offending setting, before anything is pulled, built, or started. The workspace volume is kept. |
| Rewritten / removed | The extension changes the value in the override configuration that it gives to `devcontainer up`. |
| Neutralized | A channel still exists, but the extension makes the container ignore it (environment variables, files in the container). |
| Not passed | A value of the computer does not reach the workspace helper or the container. |
| Kept | The extension leaves it as it is (user decision); see the known limits (section 10). |

**Status.** Everything in this summary is implemented.

A network named by its ID or a unique prefix of its ID is resolved as Docker resolves it, and the network that it names is checked (review round 2, S2-04). | Refused |
| Labels in `runArgs` (`--label`, `-l`) | Refused when the key starts with `devenv.`, `devcontainer.`, or `com.docker.compose.` (compared without case and surrounding spaces; Delete of a Docker Compose environment removes the containers of its project by `com.docker.compose.project`), with the message "options that Dev Environments does not support". The Dev Container CLI puts its id label `devenv.environment-id` before the `runArgs` in `docker run`, and Docker keeps the last label of a key: the extension and the Session Monitor would no longer find the container, or take it for another environment. The CLI adds `devcontainer.metadata` after the `runArgs`, but the policy does not rely on this order. Allowed: exactly the three labels that the override configuration adds itself, `devenv.container-version=4`, `devenv.container-config=unknown`, and `devenv.host-access=unrestricted` (section 12; the merged configuration of such a container holds it). The override configuration also adds `--label com.docker.compose.project=` and `--label com.docker.compose.service=` (empty values, review round 2, D2-1): an image that Docker Compose built for a project of the user (inherited through `FROM`) would otherwise give the dev container that project, and `docker compose -p <project> down` of the user would remove it. The final check of the `runArgs` of the override configuration (and of the merged configuration of an existing container) allows exactly these two; in the repository's `runArgs` they stay refused. | Refused |
| Environment variables of container-only Git: `-e`/`--env` in `runArgs`, `containerEnv`, and `remoteEnv` | Refused, with or without a value (compared without case): the variables that the override configuration sets (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`, `GIT_CONFIG_VALUE_n`, `DOCKER_CONFIG`, `GIT_SSH_COMMAND`, `GH_CONFIG_DIR`) and every other variable of Git's configuration (`GIT_CONFIG`, `GIT_CONFIG_*`, for example `GIT_CONFIG_PARAMETERS`, which Git applies after `GIT_CONFIG_COUNT`). In `docker run`, a `-e` of `runArgs` comes after the `containerEnv` of the override configuration and replaces its value for the main process of the container and for `docker exec`; a `-e NAME` without a value removes it (checked with Docker 29.8). `containerEnv` and `remoteEnv` of the repository would be replaced by the values of the override configuration without a word, or would change Git's configuration. The same variables of Features and the base image are refused on the environment image before each container creation. The variables of the Dev Containers extension, the VS Code server, and GnuPG (for example `SSH_AUTH_SOCK`, `REMOTE_CONTAINERS_IPC`, `GNUPGHOME`) are neither set nor refused. `--env-file` stays allowed below `/workspaces`; its content is not checked (see section 10). | Refused |
| Token and host variables of the GitHub CLI: `-e`/`--env` in `runArgs`, `containerEnv`, and `remoteEnv` | Refused, with or without a value (compared without case), in the same places as the variables of container-only Git (the repository configuration, and each entry of the image metadata of Features and the base image before each container creation): `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, and `GH_HOST`. The GitHub CLI prefers such a token (and `GH_HOST` its host) over the sign-in in `GH_CONFIG_DIR`, so the container would use another GitHub account than the one that owns the environment. By user decision (2026-09-26), nothing else decides who is signed in to GitHub in the container. The refusal names the reason. Other variables of the GitHub CLI (for example `GH_PAGER`) stay allowed. A variable that the Dockerfile of an image sets with `ENV` is not refused (see section 10). | Refused |
| The build of the configuration: `build.context` and `build.dockerfile` (also the older `context` and `dockerFile`), resolved against the folder of the configuration as the CLI resolves them | A path of the workspace helper is refused whatever the switch says (class *protected*): the root `/`, the shared cache volume `/devenv-cache`, the folder with the token `/workspaces/.devenv+`, the Docker socket, every path below `/workspaces` outside the repository, and a folder that contains one of them (for example `/var`). The CLI builds in the helper, where these are mounted, and the build would send them to the builder. Other paths are not checked (as before; the helper has no files of the computer). The paths are checked as written: a symbolic link of the repository that leads there is a known limit for a single container (section 10). | Refused |
| The images of the configuration: `image`, the images of the Dockerfile (with the build arguments of `build.args` and `build.target`): `FROM`, `COPY --from=<ref>`, `RUN --mount=…,from=<ref>`, and the parser directive `# syntax=<ref>` (review round 2, S2-02; stage names and stage indexes are no images), and `--build-context name=docker-image://…` of `build.options` | The image of another environment is refused whatever the switch says (class *protected*): a name of the namespace `devenv-` of Dev Environments, also written with the registry of Docker Hub (`docker.io/`, `index.docker.io/`, `registry-1.docker.io/`) or `library/`; a reference with a variable that cannot be resolved (for example `FROM devenv-abc${TARGETVARIANT}`) when the text before its first `$` is such a name. The Dockerfile is read at the path that the configuration names after the Dev Container CLI resolved its variables; a configured Dockerfile that cannot be read is not supported (review round 2, S2-01). An image ID in place of a name is not supported: `sha256:…` or 64 hexadecimal characters by their form, and any other reference that Docker resolves to a local image whose tags and digests do not name it (a prefix of an image ID, for example `a1b2c3d4`; review round 2, S2-05): it can name any local image, also one of another environment. | Refused |
| Labels of the environment image (from the Dockerfile's `LABEL`, the base image, or a Feature) | Refused before each container creation, whatever the switch says (class *protected*): `devenv.…` and `devcontainer.…` except `devcontainer.metadata` (the only label that the CLI puts on the images that it builds). The labels of Docker Compose (`com.docker.compose.…`) are allowed (review round 2, D2-1): Compose sets its own on the containers that it creates, and the override configuration of a single container sets `com.docker.compose.project` and `.service` empty. A container gets the labels of its image, and the extension, the CLI, and Docker Compose find containers by them (for example `LABEL devenv.compose-service=x` hid a single container from the extension). The dev container is found by the name of the environment in any case. | Refused |
| VS Code settings of the configuration (`customizations.vscode.settings` of the repository, a Feature, or the base image) | `remote.localPortHost` with a value other than `localhost` is refused: the Dev Containers extension writes these settings into the settings of the container, the window applies them, and VS Code would forward the ports of the container on all addresses of the computer. The setting of the user stays the user's choice. Other settings are not checked. | Refused |
| Any other `runArgs` flag | An allow-list of flags that give no access to the computer, each with its reason in the code (`RUN_FLAGS` in `src/core/helper/hostAccess.ts`): the network (`--network`, `--add-host`, `--dns`, `--dns-option`/`--dns-opt`, `--dns-search`, `--ip`, `--ip6`, `--network-alias`, `--expose`); names and variables (`--label`/`-l` and `--env`/`-e` except those above, `--hostname`, `--env-file` only for a file below `/workspaces` without `..`, because `docker run` reads it in the workspace helper); limits (`--memory`/`-m`, `--memory-reservation`, `--memory-swap`, `--memory-swappiness`, `--cpus`, `--cpu-shares`/`-c`, `--cpu-period`, `--cpu-quota`, `--cpu-rt-period`, `--cpu-rt-runtime`, `--cpuset-cpus`, `--cpuset-mems`, `--blkio-weight`, `--pids-limit`, `--shm-size`, `--ulimit`, `--storage-opt size=…`, `--oom-score-adj` of 0 or more); the user (`--user`, `--group-add`, `--workdir`); `--init`, `--platform`, `--tmpfs`, `--isolation`, `--sysctl` (Docker accepts only settings of the container's own namespaces); flags that only take rights away (`--cap-drop` with any value, `--read-only`, `--security-opt no-new-privileges`); the health check (`--health-cmd`, `--health-interval`, `--health-retries`, `--health-start-period`, `--health-start-interval`, `--health-timeout`, `--no-healthcheck`); the stop (`--stop-signal`, `--stop-timeout` up to 20 seconds, `--restart no` or `on-failure[:n]`); logs in files of the container (`--log-driver json-file`, `local`, or `none`, and `--log-opt` of the size, rotation, mode, and content of the log); flags without effect (`--entrypoint` and `--attach`/`-a`: the CLI sets its own); `--cap-add SYS_PTRACE`, `--security-opt seccomp=unconfined`, and `-p` on a loopback address. Flags are matched by their exact name: another flag that starts like one of these (for example `--dns-foo`) is unknown and refused, and it does not take the next entry as its value. Everything else is refused, including stray arguments, entries that are not strings, a flag without its value at the end of the list, and groups of short flags that contain a flag that is not known or that takes a value. Flags and values that the policy does not support get a message of their own ("options that Dev Environments does not support"), for example `--restart=always` (it starts the container together with Docker, outside the Session Monitor) and `--stop-timeout=60` (longer than a stop of the Session Monitor may take). A negative `--oom-score-adj` and other log drivers count as access to the computer. The final `runArgs` of the override configuration are checked again before `up`. | Refused |
| `--rm`, `-i`, `-t`, `--interactive`, `--tty`, `-d`, `--detach` in `runArgs`, also in groups such as `-it`, `-ti`, or `-dit` | Allowed, but removed from the `runArgs` of the override configuration, read with the same flag parser as the check (a flag that is the value of another flag stays), and named in the log with the reason. `--rm`: the extension manages the container life cycle (stop, start, recreation), and Docker would delete the container at each stop. `-i` and `-t`: the Dev Container CLI in the workspace helper has no terminal, so `-it` makes the start fail ("stdin is not a terminal"); alone, they do nothing for a dev container. `-d`: the CLI stays attached to the container, and Docker refuses `-d` together with the CLI's `-a`. | Removed |
| `--name` in `runArgs` (without it, Docker picks a random name) | Removed, read with the same flag parser as the check (a `--name` that is the value of another flag stays), and named in the log; the extension adds `--name devenv-<owner>-<repository>-<short id>` at the end, followed by `--hostname <repository name>` (lowercase, one DNS label), unless the configuration sets `--hostname`/`-h`, `--network container:…` (also `name=container:…`) or `--uts host` (Docker refuses a host name there), or `--network host` (the container keeps the host name of the computer). | Removed |
| Published ports with an address (`appPort` strings, `-p`/`--publish`) | Every address outside `127.0.0.0/8` and `::1` is refused (for example `0.0.0.0`, `[::]`, `localhost`), and so are `-P`/`--publish-all`, `appPort` entries that are neither a number nor a string, and Docker's long syntax (`published=8080,target=80`, any value with `=`), which has no address, so Docker would publish it on all addresses. | Refused |
| `build.options` (the CLI appends them unchanged to `docker build`) | Refused: `--secret`, `--ssh`, `--allow`, `--output`/`-o`, `--build-context` except `docker-image://` and `http(s)://`, stray arguments, unknown options. Allowed: `--network` (also `host`), `--add-host`, `--build-arg`, `--target`, `--label`, `--platform`, `--pull`, `--no-cache`. | Refused |
| `hostRequirements.gpu` (Dev Containers turns it into `--gpus all`) | Every value other than `false`, `null`, or absent is refused. The cpus, memory, and storage requirements are neither checked nor applied. | Refused |
| `initializeCommand` (Dev Containers runs it on the computer) | Refused (any non-empty value) and never passed to `up`: in the workspace helper it would run with the Docker socket. | Refused |
| `dockerComposeFile` (Docker Compose) | Every service is checked with the rules of this document, and Docker Compose runs the checked model, rewritten: section 13. | Refused / Rewritten |
| `workspaceMount` and `workspaceFolder` | Always the environment's named volume at `/workspaces`, with the folder `/workspaces/<repository>`; the repository's values are ignored. | Rewritten |
| `${localEnv:NAME}` and `${env:NAME}` (values of the computer) | Not passed. They resolve to their default, to an empty value, or to the helper's own value (`HOME=/root`, `PATH`, `HOSTNAME`, `NODE_VERSION`, `YARN_VERSION`). One warning names them, and those that get the helper's value. | Not passed |

## 4. Dev Container CLI

| What it normally does | What the extension does | Kind |
|---|---|---|
| Mounts the workspace as a bind mount of the local folder | The workspace is always the environment's named volume (see section 1). | Rewritten |

## 10. Known limits

- **Same macOS user.** The account separation protects against using the wrong GitHub account. It does not protect against another person or process working as the same macOS user: `docker exec`, Docker Desktop, and the Dev Containers commands reach every environment, including another account's token file. The registry, the reopen record, pending operations, and the Session Monitor are shared by all accounts. The remedy is separate users on the computer.
- **Channels of the Dev Containers extension and VS Code.** The IPC socket of the Dev Containers extension with its client script (`/tmp/vscode-remote-containers-ipc-<id>.sock`, `/tmp/vscode-remote-containers-<id>.js`), the SSH agent socket (`/tmp/vscode-ssh-auth-<id>.sock`), and the GPG agent socket exist in every attached container, and their variables (`REMOTE_CONTAINERS_IPC`, `SSH_AUTH_SOCK`) keep their values in the VS Code server and its terminals (user decision). Git does not use them: the settings of the container switch the credential helpers of Git and Docker off, `GIT_SSH_COMMAND` switches the SSH agent off for Git, and Git signs nothing unless the user configures it. A process of the remote user or root that looks for them can use them: through the IPC socket it can read, store, or erase the computer's Git and Docker credentials (the computer's credential helpers decide what `git credential fill` returns), and through the agents it can use the SSH and GPG keys of the computer. The settings of the container are in `~/.vscode-server/data/Machine/settings.json`, which the Dev Containers extension writes only at the first attach of a new container: a process in the container can change or remove the file (then the user's settings apply again; the variables of Git and Docker still keep Git and Docker on the configuration of the volume, except for Git older than 2.31 and processes without the variables), and a `~/.vscode-server` on a volume keeps the file of an earlier container. The VS Code remote API (clipboard, `openExternal`, the `code` command, commands of local extensions, sign-in requests with consent, Git askpass) stays available too. Full isolation needs a separate macOS user, a VM, or Docker Desktop Enhanced Container Isolation.
- **Ports on `127.0.0.1` are reachable from every container.** Binding published ports to `127.0.0.1` protects against the network only: every container reaches `localhost` of the computer through `host.docker.internal`, also the ports that VS Code forwards for another environment, including one of another GitHub account, and services of the computer that listen on `127.0.0.1`. Network access to the computer is allowed (user decision), so the extension does not block it; a service that other containers must not reach needs its own authentication.
- **`--network host` on Linux with Docker Engine shares more than ports.** The container joins the network namespace of the computer. Besides its ports and the services on `127.0.0.1`, it reaches the abstract Unix sockets of the computer, which have no file and need no mount: for example the X11 display of the desktop (`@/tmp/.X11-unix/X0`), some D-Bus buses, and the sockets of other local programs. Most of them check who connects (the X11 cookie, the user ID for D-Bus), but a program that accepts any local connection can be used from the container. `--network host` is allowed (user decision); a repository that uses it has this access. With Docker Desktop, the host network is the network of its virtual machine, not of the computer.
- **Configurations that take rights away.** With `--cap-drop` of the file rights of root (for example `ALL` or `DAC_OVERRIDE`), root in the container may not change files of the user. The extension then writes `~/.gitconfig` as the remote user (the token is removed by the workspace helper, which such a configuration does not affect); the change of owner after `up` fails, which is logged. With `--read-only` and no writable home folder (a volume or `--tmpfs`), VS Code Server cannot be installed.
- **`--env-file` follows links, and its content is not checked.** The check allows only a path below `/workspaces`, but a symbolic link of the repository at that path can point to another file of the workspace helper during `up` (its image, or the cache volume `devenv-helper-cache`). The file can change until the container starts, so its variables are not checked. Docker applies the `-e` values after those of the file, so the variables of the override configuration's `containerEnv` keep their values; the file can still set the other variables of Git's configuration (for example `GIT_CONFIG_PARAMETERS`, which Git applies after `GIT_CONFIG_COUNT`), for all processes of the container, also the VS Code server and its terminals. Like an `ENV` of an image, the file can also set the token and host variables of the GitHub CLI (`GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GH_HOST`), which `gh` then prefers over the sign-in of the owner account; Git is not affected.
- **Links in the build of a single container.** `build.context` and `build.dockerfile` of a single container are checked as written (a path of the workspace helper is refused, section 1). A symbolic link of the repository that leads to such a path (for example a folder `ctx` that links to `/devenv-cache`) is not resolved: the builder follows it in the workspace helper. For Docker Compose configurations the real paths are checked (section 13).
- **The machine settings file of VS Code Server.** The settings of the container (the switches of the Dev Containers features, section 5, and the refusal of `remote.localPortHost`, section 1) reach `~/.vscode-server/data/Machine/settings.json` only when the Dev Containers extension creates that file. An image that ships its own file keeps its values, and any process in the container can change the file. Such a file can set `remote.localPortHost` to `allInterfaces`, so that VS Code forwards the ports on all addresses of the computer, and it can leave out the settings that switch the Git and Docker credential forwarding off (Git in the container still uses only its own configuration, section 5). The extension does not read this file.
- **Volumes of a failed first open.** When the first open of a repository fails after `up` created the container, the extension removes the environment (its container, images, workspace volume, and entry). The additional volumes that it created with the labels of the environment (for example a volume of the configuration) and the volumes that Docker created at `up` (for example `${devcontainerId}-history`) stay, and no Delete lists them; `docker volume rm` removes them. The registry keeps them with the account, as after a Delete that kept them.
- **Named volumes without labels.** The check knows the volumes of Dev Environments, of the Dev Containers extension, of the environments of other accounts, and the existing volumes that Docker Compose, the Dev Containers extension, or Docker labelled. A volume without such labels, for example one created with `docker volume create`, can be mounted by any configuration that knows its name. The volumes of the environments of other accounts are known from the registry, also the volumes that a Delete kept (with the account whose environment used them; a volume that the Deletes of two accounts kept is refused to both; the records of a volume that no longer exists are dropped when a configuration mounts its name, because a new volume of that name is empty). After a loss of the registry, the records of kept volumes are lost with it and cannot be restored (the Delete removed the containers that the restore reads): the environment of any account can then mount such a volume; `docker volume rm` removes it. Otherwise, after a loss of the registry, the restore reads them from the containers of the environments, which a loss of the registry does not remove (their named volumes without devenv labels, recorded again so that they stay protected, and kept by Delete; without the volumes that the policy gives to something else by their names or labels: anonymous volumes, volumes of the Dev Containers extension, of the helper, of other environments, and of other programs); an environment whose container is gone too has only its workspace volume known, and the account whose environment of the repository opens first then records a fixed-name volume of the repository as its own, so that the environment of the other account is refused it.
- **Repository code runs, with the network.** Dockerfile `RUN`, Feature install scripts and entrypoints, and lifecycle commands run. A container is not a strong security boundary.
- **Old Git in the image.** Git older than 2.32 ignores `GIT_CONFIG_GLOBAL`, and Git older than 2.31 also `GIT_CONFIG_COUNT`: it reads the volume's configuration (before 2.31 also the credential helper of the container) only through the extension's `~/.gitconfig`, which is missing when the image brings its own file with content. With the settings of the container, the Dev Containers extension configures no forwarding helper; without them (a changed settings file), such Git may use the computer's credential helper for hosts other than github.com, and Git older than 2.9, which does not clear helpers with an empty value, also for github.com; the extension checks the Git version of each new container and warns about Git older than 2.9. `sudo git` and `env -i git` also drop the variables.
- **The token stays after sign-out.** When a window leaves an environment because of a sign-out or an account change, the workspace helper removes the token file and the sign-in of the GitHub CLI (`gh/hosts.yml`) from the volume of the environment, whether its container runs or not. Otherwise (an environment that no window of this computer shows) both stay until the next open or Delete. Only revoking VS Code's access on GitHub makes it invalid.
- **`ENV` of an image can still choose the GitHub CLI's account.** The host access policy refuses the token and host variables of the GitHub CLI (`GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GH_HOST`) only in the configuration: `runArgs`, `containerEnv`, and `remoteEnv` of the repository, the Features, and the base image. A variable that a Dockerfile (of the repository or of the base image) sets with `ENV` is part of the image, not of any configuration, so it is not refused; `gh` in the container then uses that token or host instead of the sign-in of the owner account. The same holds for a variable that a shell profile of the image or a process in the container sets. Git is not affected: its credential helper for github.com always uses the token of the owner account.
- **Not restricted yet:** X11 forwarding (XQuartz; the Dev Containers extension forwards it unless the environment of the container has a non-empty `DISPLAY`; `DISPLAY=''` in `remoteEnv` does not stop it), the copy of `~/.ssh/known_hosts` (at each attach, when the container has no such file; an empty file would stop it), and the user's dotfiles (cloned and installed in each new container; they cannot be switched off for one container).

## 11. Known gaps

Found when this summary was verified against the code. Gaps 1 to 7 and 9 are fixed or documented; gap 8 is resolved by one environment per repository and account.

1. **Fixed: the `runArgs` check could be bypassed.** The check runs on the repository's `runArgs`, but `docker run` gets them after the removal of `--name` (which also removes the next entry, even when `--name` is the value of another flag) and after entries that are not strings are dropped. `["--label","--name","--init","--label","-v/Users:/host"]` passes and becomes a bind mount. Fixed: entries that are not strings are refused, `--name` is removed with the same flag parser as the check, and the final `runArgs` are checked before `up`.
2. **Fixed: the empty `~/.gitconfig` did not stop the copy.** The Dev Containers extension skips the copy only when the file has a section other than `[filter]` or `[safe]`, so the computer's `~/.gitconfig` is appended at the first attach. Fixed with the documented setting `copyGitConfig: false` for the container (gap 3, section 5); the extension relies on no internal check of the Dev Containers extension (user decision).
3. **Fixed: `REMOTE_CONTAINERS_IPC` carries credentials, not the browser.** In Dev Containers 0.470.0 the socket answers only the requests of its forwarding credential helpers of Git and Docker, with the computer's credentials (read, store, and erase); `$BROWSER`, the `code` command, `openExternal`, Open in Browser, and port forwarding use the channels of VS Code itself. Fixed only with the documented settings of the Dev Containers extension for the container (`copyGitConfig` under both keys, `gitCredentialHelperConfigLocation: none`, `dockerCredentialHelper: false`, `githubCLILoginWithToken: false`): Git and Docker in the container do not use the socket. By user decision, no variable of the Dev Containers extension or the VS Code server is set or changed, so `REMOTE_CONTAINERS_IPC`, `SSH_AUTH_SOCK`, and `$BROWSER` keep their values, and the extension no longer writes the placeholder that kept the GPG agent out. Containers of an older version are created again (container version 3; version 4 adds `GH_CONFIG_DIR`). The sockets stay usable by a process that looks for them (section 10). To verify in real VS Code (V-8).
4. **Fixed: other named volumes could be mounted** (for example the Dev Containers `vscode` volume); only `devenv-*` names were protected. Rule: a mount may use anonymous volumes, tmpfs, the own workspace volume, and named volumes of the repository, but no volume that belongs to something else: another environment (by its name, or used by an environment of another account), another container (by the name of an anonymous volume), the workspace helper, the Dev Containers extension (by its names), or another program (by the labels of an existing volume). See section 1; volumes without labels stay a limit (section 10). With one environment per repository and account, a fixed volume name of a repository used by the environment of another account is refused by the same rule.
5. **Fixed: a repository label could replace the id label.** A repository `--label devenv.environment-id=…` won over the CLI's id label. Labels with the prefixes `devenv.` and `devcontainer.` in `runArgs` are refused (section 1).
6. **Fixed: `-e`/`--env-file` in `runArgs` could override the Git variables** (`GIT_CONFIG_*`, `DOCKER_CONFIG`, `GNUPGHOME`, `GIT_SSH_COMMAND`, `SSH_AUTH_SOCK`) for the container's main process and plain `docker exec`. The variables that the extension sets (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`, `DOCKER_CONFIG`, `GIT_SSH_COMMAND`, `GH_CONFIG_DIR`) and every other `GIT_CONFIG*` variable are refused in `-e`/`--env`, `containerEnv`, and `remoteEnv`, also of Features and the base image (section 1). `GNUPGHOME` and `SSH_AUTH_SOCK` are no longer set by the extension (user decision), so there is nothing of it to override. `--env-file` stays allowed below `/workspaces`: Docker applies `-e` after the file, so the extension's own values win; the other variables of the file are a documented limit (section 10).
7. **Documented: ports on `127.0.0.1` are reachable from every container** through `host.docker.internal`, including ports that VS Code forwards for another account's environment. Binding to localhost protects against the LAN only. A known limit (section 10), because network access to the computer is allowed.
8. **The row "Environment of another account" and the `otherAccount` message reveal** that another account has an environment of a repository that the signed-in account can access. Resolved by one environment per repository and account: the row is gone, and `otherAccount` names only an environment that a command names by its ID (a row or the status bar item from before an account change, a restored window, an account change during an open, and an account change during Switch branch…: the environment whose branch it switched, also after a repository pick).
9. **Fixed for the configuration: a configuration could make VS Code forward ports on all addresses of the computer** (found with gap 3): `remote.localPortHost: allInterfaces` in `customizations.vscode.settings` becomes a setting of the container, which the window applies. Refused (section 1). An image or a process in the container can still write the setting into the machine settings file of VS Code Server (a known limit, section 10).

## 12. The switch per repository (host access checks off)

User request (2026-09-26): "application of the security policy shall be configurable per repository, by default it is on". The user setting `devEnvLauncher.hostAccessChecksOff` lists the repositories (`owner/name`, compared without case and surrounding spaces) whose host access checks are off; it has the scope `application`, so only the user settings count, and a workspace, a folder, or a repository cannot turn a check off. Invalid entries are ignored, with one warning. The context menu of a repository row has **Turn Off Host Access Checks…** (after a modal warning that lists what becomes possible) and **Turn On Host Access Checks**. The switch is read at each open.

**What changes while the checks are off.** Only the items of the class *computer* below are no longer refused. Published ports without an address are no longer bound to `127.0.0.1` (section 6): `runArgs` and `appPort` keep what the configuration writes. The row shows `host access unrestricted` with a warning in its tooltip, the log says so at every open, and each container that is created gets the label `devenv.host-access=unrestricted`. Turning the checks off applies when the container of the environment is created next, for example with **Rebuild**: an existing container keeps its current settings, such as published ports that are bound to this computer only (`127.0.0.1`). A container that was created with the checks on is not created again only because they are off now (it has less access). With the Docker socket (a bind mount or `--use-api-socket`), privileged mode, or the namespaces of the computer, the container can control Docker and every other environment, also the environments of other GitHub accounts, and read their files and tokens: the checks of account separation that stay on keep the configuration from using other environments by mistake, they are no boundary against a configuration that uses the Docker socket on purpose. The modal warning says so.

**Switching back on.** At the next open, the checks run as before. A container with `devenv.host-access=unrestricted` is not current while the checks are on (`containerIsCurrent`): it is created again from its environment image (the files in the volume are kept, the progress says so) when the configuration and the image metadata pass the checks. The merged configuration of such a container is not checked (the Dev Container CLI merges the metadata of the existing container into it, which holds what the checks allowed while they were off); the image metadata of the environment image is checked before `up`. If a check refuses, the open stops with the usual refusal and the container is not started; a window that is attached to it closes its connection. A refused update of an environment image (concept 7.7) is remembered with the state of the switch: a refusal while the checks were on does not block the update once they are off, and the other way round.

**Classes.** *computer*: lifted while the checks are off. *protected*: refused whatever the switch says: account separation, the identity of the owner account, the integrity of the extension, and items whose class is not clear (the safer choice). *unsupported*: options that the policy does not know or does not support, refused whatever the switch says. The unit test `src/core/helper/hostAccess.checksOff.test.ts` checks each row. The items of Docker Compose configurations have the same classes (section 13, `src/core/helper/composeAccess.checksOff.test.ts`); their containers all get the label `devenv.host-access=unrestricted` (with the checks on, `devenv.host-access=checked`: the model sets the label on every service either way, so that a label of an image that Compose builds or pulls during `up` cannot decide it; review round 2, D2-2).

## 13. Docker Compose configurations

A devcontainer.json with `dockerComposeFile` and `service` starts several containers: the dev service, which VS Code connects to, and the other services (for example a database). Docker Compose starts all of them with the Docker engine of the computer, so the rules of this document apply to **every service**, not only to the dev service. The technical design is in the [implementation notes, section 15](implementation-notes.md#15-docker-compose).

**How it is checked.** The extension reads the merged model of the compose files (`docker compose config`, all profiles) in the workspace helper, without the Docker socket, without network, and with the folder that holds the token hidden. It checks that model before anything is pulled or built, and again before the containers are created. Then Docker Compose runs exactly that model, rewritten as listed below; the compose files of the repository are not read again, so they cannot change between the check and the start. The check is an allow-list: a setting that it does not know is refused as not supported. Items are named `service <name>: …`.

**Rewritten, whatever the switch says** (logged as "Changed in the Docker Compose model"):

| Setting | What the extension does |
|---|---|

| Dev service | Runs the environment image (no `build`, never pulled); the name of the environment; the workspace volume at `/workspaces` (the templates' bind mount `../..:/workspaces` is dropped); the host name of the repository unless the service sets `hostname`, `network_mode: host`, `service:…`, `container:…`, or `uts: host`. |
| Other services | `container_name` removed (two environments of one repository would collide); a built image is named `devenv-<short id>-<service>`. |

The rules of sections 1 to 5 for devcontainer.json, Features, and the base image apply as for a single container (`mounts`, `privileged`, `capAdd`, `securityOpt`, `containerEnv`, `remoteEnv`, `remote.localPortHost`, and the image metadata before each start), with the same switch.

**Stop, start, Delete.** Stop and the Session Monitor stop every container of the environment, the dev container first; before each further container, the Session Monitor checks again that no window uses the environment. A stopped service of a running dev container is started with `docker start`. Delete removes the containers of all services (never a container whose label `devenv.environment-id` names another environment, even when it has the label of the project), the networks of the project, and the images that Docker Compose built for it; the data of the services only when the user ticks them in the question of Delete, the others stay. The data of the services are the own volumes that a service other than the dev service mounts, whatever their name (also a volume with `name:` in the model): the extension records them at each open, and at Delete it also reads the volumes of the containers of the other services. Each volume that the extension creates for such a service also gets the label `devenv.service-data=true`, which keeps it in that question after a lost registry; an environment restored without that knowledge (volumes of an older version, no build record yet) lists all its own additional volumes there, none ticked (review round 2, D2-3). After this update, the side services of an existing Compose environment are created again once (the label `devenv.host-access=checked` is new in their model, D2-2); their named volumes are kept. The images that the other services use as they are (for example `postgres:16`) are never removed as base images after an update or Delete.

**Switching between Docker Compose and a single container** happens only with a build (for example **Rebuild now**). With **Rebuild later**, a failed update, or a refused update, the environment starts as it is: the containers of Docker Compose with `docker start`, a single container as before. From Docker Compose to a single container, the containers of the other services are removed: their named volumes stay; data in their volumes without a name is no longer used, and Docker keeps those volumes as unused volumes (the progress says so).

**Limits.**
- **Repository files in a service.** A service that mounts files or folders of the repository can read and change them, while it runs (for example a database that writes into a mounted folder). It sees only those paths of the workspace volume, not the token.
- **Other services on the network.** The services share the networks of the project and reach each other by name. Every published port is bound to `127.0.0.1`, but, as in section 10, every container reaches `localhost` of the computer through `host.docker.internal`.
- **Variables of other services.** A service other than the dev service may set `GH_TOKEN` and the variables of Git: it has no token of the owner account and no Git configuration of the extension.
- **Remote `include` and `extends`** (Git, OCI) do not work: the model is read without network. Local ones can only name files of the repository and of the helper image (the token is hidden).
- **Newer Compose versions.** The helper installs the current Compose plugin; a new setting of a newer version is refused as not supported until the policy knows it.
- **Old images of rebuilt services** stay as dangling images (`docker image prune` removes them).
- **Links swapped while the build runs.** The real paths of the build contexts and Dockerfiles are read in the model run, before the build. A running dev container of the environment can change a link of the repository between the check and the build (the build runs minutes later, in another helper run that mounts the cache volume): the builder then follows the new link. Only a process of the environment itself can do so, and it runs with the files of the environment already.
- **Labels of images that Compose builds** during the start (the other services with `build`) are not checked before the start; the model sets the labels of the extension on every container, which win over those of the image.
- **An image of another service that is not there yet** (Compose pulls it during the start) is started without the check of its labels.
