# Container restrictions

This document lists every restriction that Dev Environments applies to its dev containers, grouped by **who normally configures** the thing that the extension restricts. The requirements are in the concept ([vscode-dev-environments.md](vscode-dev-environments.md), section 9 "Host access" and "Accounts"); the technical decisions are in the [implementation notes](implementation-notes.md).

**Trust model: a malicious dev container can do harm.** A repository that the user opens is code that the user runs. Its Dockerfile and build, its Features, its lifecycle commands, and the extensions in its container run with the rights of the container. They have the network (the internet, the local network, a VPN of the computer, and the services of the computer through `host.docker.internal` with Docker Desktop), share the kernel of the computer (with Docker Desktop: of its virtual machine), reach the channels that VS Code keeps open to the computer (SSH and GPG agents, the credential socket of the Dev Containers extension, URLs, the clipboard, the X11 display; section 10 and README, "Hardening your computer"), and can use the owner's GitHub token (section 9). The user of the container is chosen by the repository's configuration (`remoteUser`, `containerUser`, or the image), often a user without root rights that can use `sudo`; Dev Environments does not change it.

**What Dev Environments does.** Docker isolation: each environment runs in containers of its own; the repository is in a Docker volume, not in a folder of the computer, and the extension mounts nothing of the computer into the container; published ports are bound to `127.0.0.1` while the checks are on (section 6); the containers and volumes of an environment carry its labels, by which the extension finds them and the checks tell other environments apart. On top of that, the checks of this document refuse the grants of the computer that a configuration can ask for (bind mounts of host files, the Docker socket, privileged mode, capabilities beyond Docker's default set and `SYS_PTRACE`, devices and GPUs, host namespaces, ports on all addresses, volumes of other programs; switch per repository, section 12), and refuse, whatever the switch says, what would break account separation, the identity of the owner account, or the integrity of the extension (classes *protected* and *unsupported*, sections 12 and 13). The token is never an environment variable, and the settings of the Dev Containers extension for each container switch off its copy of the Git configuration, its Git and Docker credential forwarding, and its sign-in of the GitHub CLI (section 5).

**Limits.** The checks are a guard rail against mistakes and copied templates, not a sandbox: a crafted repository can get around them (for example through the way the Dev Container CLI rewrites a Dockerfile), all environments share one Docker (its local images and build cache), the kernel is shared, and the channels of VS Code stay open. Section 10 lists every known limit. Open only repositories that you trust; for others, use a virtual machine or a separate user account with its own Docker.

**Principle of the checks.** The aim is that no setting of the configuration grants the container access to the computer (section 10 lists where the checks do not reach this aim), with three exceptions that the user decided to keep: the network (including VPN connections of the computer), ports of the container on `localhost` of the computer, and URLs that open in the computer's browser.

**Switch per repository.** The checks are on for every repository by default. The user setting `devEnvLauncher.hostAccessChecksOff` turns them off for the repositories that it lists; then only the refusals of access to the computer are lifted, and everything else in this document still applies. Section 12 lists the class of every refused item; section 13 does so for Docker Compose configurations.

**Code.** Every check is in `src/core/policy/`, with one entry point (`checkContainer` in `index.ts`): the rules table in `rules.ts` (the classes, the protected paths, the allowed capabilities and security options), the flags of `runArgs` and `build.options` in `flags.ts`, a single container in `single.ts`, Docker Compose in `compose.ts`, volumes and networks in `volumes.ts`, image references in `images.ts`, and what the extension rewrites instead of refusing in `rewrites.ts`; the switch per repository in `hostAccessChecks.ts` (implementation notes, section 7, "Where the policy lives").

**Kinds of restriction.**

| Kind | Meaning |
|---|---|
| Refused | Start stops with a message that names each offending setting, before anything is pulled, built, or started. The workspace volume is kept. |
| Rewritten / removed | The extension changes the value in the override configuration that it gives to `devcontainer up`. |
| Neutralized | A channel still exists, but the extension makes the container ignore it (environment variables, files in the container). |
| Not passed | A value of the computer does not reach the workspace helper or the container. |
| Kept | The extension leaves it as it is (user decision); see the known limits (section 10). |

**Status.** Everything in this summary is implemented.

## 10. Known limits

- **Same macOS user.** The account separation protects against using the wrong GitHub account. It does not protect against another person or process working as the same macOS user: `docker exec`, Docker Desktop, and the Dev Containers commands reach every environment, including another account's token file. The registry, the reopen record, pending operations, and the Session Monitor are shared by all accounts. The remedy is separate users on the computer.
- **Channels of the Dev Containers extension and VS Code.** The IPC socket of the Dev Containers extension with its client script (`/tmp/vscode-remote-containers-ipc-<id>.sock`, `/tmp/vscode-remote-containers-<id>.js`), the SSH agent socket (`/tmp/vscode-ssh-auth-<id>.sock`), and the GPG agent socket exist in every attached container, and their variables (`REMOTE_CONTAINERS_IPC`, `SSH_AUTH_SOCK`) keep their values in the VS Code server and its terminals (user decision). Git does not use them: the settings of the container switch the credential helpers of Git and Docker off, `GIT_SSH_COMMAND` switches the SSH agent off for Git, and Git signs nothing unless the user configures it. A process of the remote user or root that looks for them can use them: through the IPC socket it can read, store, or erase the computer's Git and Docker credentials (the computer's credential helpers decide what `git credential fill` returns), and through the agents it can use the SSH and GPG keys of the computer. The settings of the container are in `~/.vscode-server/data/Machine/settings.json`, which the Dev Containers extension writes only at the first attach of a new container: a process in the container can change or remove the file (then the user's settings apply again; the variables of Git and Docker still keep Git and Docker on the configuration of the volume, except for Git older than 2.31 and processes without the variables), and a `~/.vscode-server` on a volume keeps the file of an earlier container. The VS Code remote API (clipboard, `openExternal`, the `code` command, commands of local extensions, sign-in requests with consent, Git askpass) stays available too. Full isolation needs a separate user account on the computer or a virtual machine. Docker Desktop Enhanced Container Isolation hardens the container, but does not close these channels.
- **Ports on `127.0.0.1` are reachable from every container.** Binding published ports to `127.0.0.1` protects against the network only (on a remote Docker host, unit 7, `127.0.0.1` is the loopback of the remote computer: the user reaches the ports through the port forwarding of VS Code, and every user and process of that computer can reach them): every container reaches `localhost` of the computer through `host.docker.internal`, also the ports that VS Code forwards for another environment, including one of another GitHub account, and services of the computer that listen on `127.0.0.1`. Network access to the computer is allowed (user decision), so the extension does not block it; a service that other containers must not reach needs its own authentication.
- **`--network host` on Linux with Docker Engine shares more than ports.** The container joins the network namespace of the computer. Besides its ports and the services on `127.0.0.1`, it reaches the abstract Unix sockets of the computer, which have no file and need no mount: for example the X11 display of the desktop (`@/tmp/.X11-unix/X0`), some D-Bus buses, and the sockets of other local programs. Most of them check who connects (the X11 cookie, the user ID for D-Bus), but a program that accepts any local connection can be used from the container. `--network host` is allowed (user decision); a repository that uses it has this access. With Docker Desktop, the host network is the network of its virtual machine, not of the computer.
- **Configurations that take rights away.** With `--cap-drop` of the file rights of root (for example `ALL` or `DAC_OVERRIDE`), root in the container may not change files of the user. The extension then writes `~/.gitconfig` as the remote user; the change of owner after `up` fails, which is logged. Unit 15: the token in `/run/devenv` needs only `CHOWN` of root (review of unit 15, P1): root gives the files to the remote user first, then the folder, and at the next write or a sign-out takes everything in the folder back (`chown -h`, folders mode 0700, top down, never through a link) before it empties it, so `DAC_OVERRIDE` is not needed (for example `--cap-drop DAC_OVERRIDE`, or `--cap-drop ALL` with `--cap-add CHOWN`, `SETUID`, `SETGID`), also when the user put folders without rights or links there. Without `CHOWN` (for example `--cap-drop ALL` alone), root cannot give the token to a remote user other than root: the write stops, removes what it wrote, Git and the GitHub CLI cannot use the owner account, and the open says that Git could not be prepared. At a sign-out, the token is removed as root, and as the remote user when root may not or the folder cannot be read or emptied. With `--read-only` and no writable home folder (a volume or `--tmpfs`), VS Code Server cannot be installed.
- **`--env-file` follows links, and its content is not checked.** The check allows only a path below `/workspaces`, but a symbolic link of the repository at that path can point to another file of the workspace helper during `up` (its image, or the cache volume `devenv-helper-cache`). The file can change until the container starts, so its variables are not checked. Docker applies the `-e` values after those of the file, so the variables of the override configuration's `containerEnv` keep their values; the file can still set the other variables of Git's configuration (for example `GIT_CONFIG_PARAMETERS`, which Git applies after `GIT_CONFIG_COUNT`), for all processes of the container, also the VS Code server and its terminals. Like an `ENV` of an image, the file can also set the token and host variables of the GitHub CLI (`GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GH_HOST`), which `gh` then prefers over the sign-in of the owner account; Git is not affected.
- **Links in the build of a single container.** `build.context` of a single container is checked as written: a path of the workspace helper (also below `/proc`, `/sys`, `/dev`) and any context outside the repository are refused (section 1, review round 3, S3-1). A symbolic link of the repository that leads out of it (for example a folder `ctx` that links to `/devenv-cache`) is not resolved for the context, a local `--build-context`, or the files of `--secret` and `--ssh` of `build.options`: the builder follows it in the workspace helper. The Dockerfile is read only when its real path is in the repository (review round 3, P3-1); a Dockerfile that links out of it, or that could not be read, is refused whatever the switch says (section 1, U2). For Docker Compose configurations the real paths are checked (section 13).
- **`ONBUILD` of a base image.** The `ONBUILD` instructions of the repository's Dockerfile are not checked: they do not run in its own build, only in a later build `FROM` its image. An `ONBUILD` trigger of a base image (for example `ONBUILD COPY --from=devenv-… / /x` in an image of a registry) runs in the build of the repository's Dockerfile and is not checked: its text is part of the image, not of any file that the check reads.
- **The Dockerfile and the Features are not checked.** They run as trusted code, like the rest of the repository (README, "Security: what to expect"); the checks look at the final configuration only. Dev Environments reads the `FROM` lines of the Dockerfile only for the update notice. Within one Docker Engine, a Dockerfile can build from or copy out of the local images of other environments, also of other GitHub accounts (`FROM`, `COPY --from=`, `RUN --mount=…,from=`), and name a BuildKit frontend of its choice (`# syntax=`, `BUILDKIT_SYNTAX`), a program that builds with the images of the local store. The Dockerfile refusals of these forms were removed (user decision 2026-09-27). A Docker of its own for each account would close this (see [the VM isolation concept](concept-vm-isolation.md); not planned). Do not open repositories that you do not trust on a computer where the environments of other accounts hold data that you need to protect.
- **The user that the Dev Container CLI writes for a Docker Compose build with Features.** With Features, the CLI writes the user of the target stage of the dev service (from the `USER` instruction, the build arguments, and the image) as text into its compose file for the build (`_DEV_CONTAINERS_IMAGE_USER`). Computing that user would mean modelling the CLI's own reading of the Dockerfile, so it is not checked; the build target and the name of the last stage, which the CLI writes too, are (section 13).
- **The machine settings file of VS Code Server.** The settings of the container (the switches of the Dev Containers features, section 5, and the refusal of `remote.localPortHost`, section 1) reach `~/.vscode-server/data/Machine/settings.json` only when the Dev Containers extension creates that file. An image that ships its own file keeps its values, and any process in the container can change the file. Such a file can set `remote.localPortHost` to `allInterfaces`, so that VS Code forwards the ports on all addresses of the computer, and it can leave out the settings that switch the Git and Docker credential forwarding off (Git in the container still uses only its own configuration, section 5). The extension does not read this file.
- **Volumes of a failed first open.** When the first open of a repository fails after `up` created the container, the extension removes the environment (its container, images, workspace volume, and entry). The additional volumes that it created with the labels of the environment (for example a volume of the configuration) and the volumes that Docker created at `up` (for example `${devcontainerId}-history`) stay, and no Delete lists them; `docker volume rm` removes them. The registry keeps them with the account, as after a Delete that kept them.
- **Named volumes without labels.** The check knows the volumes of Dev Environments, of the Dev Containers extension, of the environments of other accounts, and the existing volumes that Docker Compose, the Dev Containers extension, or Docker labelled. A volume without such labels, for example one created with `docker volume create`, can be mounted by any configuration that knows its name. The volumes of the environments of other accounts are known from the registry, also the volumes that a Delete kept (with the account whose environment used them; a volume that the Deletes of two accounts kept is refused to both; the records of a volume that no longer exists are dropped when a configuration mounts its name, because a new volume of that name is empty). Such a volume also comes from Docker at `up` (a name that only `up` knows, such as `${devcontainerId}-…`): for example a `${localWorkspaceFolderBasename}-node_modules` volume of two accounts' environments of repositories named `api` that was created without labels stays shared by both (hotfix review 2, P5; accepted). The pipeline names each such volume in the log before it creates a container (`The volume … exists without labels`); `docker volume rm` of the volume, while no container uses it, ends the sharing: the next open creates it with the labels of the environment. After a loss of the registry, the records of kept volumes are lost with it and cannot be restored (the Delete removed the containers that the restore reads): the environment of any account can then mount such a volume; `docker volume rm` removes it. Otherwise, after a loss of the registry, the restore reads them from the containers of the environments, which a loss of the registry does not remove (their named volumes without devenv labels, recorded again so that they stay protected, and kept by Delete; without the volumes that the policy gives to something else by their names or labels: anonymous volumes, volumes of the Dev Containers extension, of the helper, of other environments, and of other programs); an environment whose container is gone too has only its workspace volume known, and the account whose environment of the repository opens first then records a fixed-name volume of the repository as its own, so that the environment of the other account is refused it.
- **`${containerWorkspaceFolder}` in a volume name, with a `workspaceFolder` of the repository.** The extension mounts the workspace at `/workspaces/<name>` (the override configuration), but `read-configuration` resolves `${containerWorkspaceFolder}` and `${containerWorkspaceFolderBasename}` with the `workspaceFolder` that the repository sets. The volumes that the extension creates with the labels of the environment before `up`, and the names that the check of the configuration reads, come from that resolution, while Docker gets the name that `up` resolves with the override. A volume name with these variables can then name a volume that no container uses (it stays, labelled with the environment; `docker volume rm` removes it), or refuse a configuration whose name only looks like that of another volume (a false refusal). No access is given that the policy refuses: the name that Docker really gets comes from the label `devcontainer.metadata` of the environment image, which is checked before a container is created (hotfix review 3, C3-1; accepted).
- **Repository code runs, with the network.** Dockerfile `RUN`, Feature install scripts and entrypoints, and lifecycle commands run. A container is not a strong security boundary.
- **Old Git in the image.** Git older than 2.32 ignores `GIT_CONFIG_GLOBAL`, and Git older than 2.31 also `GIT_CONFIG_COUNT`: it reads the volume's configuration (before 2.31 also the credential helper of the container) only through the extension's `~/.gitconfig`, which is written before the lifecycle commands (so they can use the token with such Git too), and which is missing when the image brings its own file with content: then Git older than 2.31 gets no credential helper for github.com (also not in the lifecycle commands), and Git 2.31 gets the credential helper (`GIT_CONFIG_COUNT`) but not the identity and the other settings of the volume (`GIT_CONFIG_GLOBAL` needs 2.32). With the settings of the container, the Dev Containers extension configures no forwarding helper; without them (a changed settings file), such Git may use the computer's credential helper for hosts other than github.com, and Git older than 2.9, which does not clear helpers with an empty value, also for github.com; the extension checks the Git version of each new container and warns about Git older than 2.9. `sudo git` and `env -i git` also drop the variables.
- **The token stays after sign-out while the container runs.** When a window leaves an environment because of a sign-out or an account change, the extension empties `/run/devenv` of its running dev container. Otherwise (an environment that no window of this computer shows) the token stays in the memory of its running container until the container stops or the next open. Only revoking VS Code's access on GitHub makes it invalid.
- **No token without an open.** The token is written at each open, after the container runs. A container that starts in another way (a restart by Docker, `docker start`) has an empty `/run/devenv` until the next open from a window: Git gets no password, and the GitHub CLI is not signed in. The lifecycle commands (`onCreateCommand`, `updateContentCommand`, `postCreateCommand`, `postStartCommand`) run after the write and can use the token (user decision 2026-09-27: `up --skip-post-create`, the token, then `run-user-commands`); the extension's `~/.gitconfig` is written before them too, so Git older than 2.31 reaches the credential helper (see "Old Git in the image" for an image with its own `~/.gitconfig`). When the write fails, they run without it. Their output in the log, and the details of a failure, show the token as `***` (review PL-1; a command can still copy the token elsewhere).
- **`ENV` of an image can still choose the GitHub CLI's account.** The host access policy refuses the token and host variables of the GitHub CLI (`GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GH_HOST`) only in the configuration: `runArgs`, `containerEnv`, and `remoteEnv` of the repository, and `containerEnv` and `remoteEnv` of the label `devcontainer.metadata` of the base image. A variable that a Dockerfile (of the repository or of the base image) sets with `ENV` is part of the image, not of any configuration, so it is not refused; so is the `containerEnv` of a Feature, which the Dev Container CLI writes as `ENV` into the environment image (hotfix review 1, N7); `gh` in the container then uses that token or host instead of the sign-in of the owner account. The same holds for a variable that a shell profile of the image or a process in the container sets. Git is not affected: its credential helper for github.com always uses the token of the owner account.
- **GPUs through `NVIDIA_VISIBLE_DEVICES` with the NVIDIA runtime as Docker's default.** When the Docker daemon of the computer has `nvidia` as its default runtime (`"default-runtime": "nvidia"` in `daemon.json`, for example on some Linux GPU hosts), the variable `NVIDIA_VISIBLE_DEVICES` (for example `all`) gives a container the GPUs of the computer, without `--gpus`, `--runtime`, `gpus`, or a device reservation. It is not refused: it can come from the configuration (`containerEnv`, `-e`, `environment` of a service) and also from an `ENV` of an image (for example the CUDA images set it), for a single container and for Docker Compose (review round 22, H22-8). With Docker's own default runtime (`runc`, also Docker Desktop), the variable does nothing.
- **Not restricted yet:** X11 forwarding (XQuartz on macOS, Linux, and one report on Windows with `DISPLAY` set in WSL, #11599): the Dev Containers extension forwards the display when `DISPLAY` is set for VS Code. Whether `"DISPLAY": ""` in `remoteEnv` stops it is not verified: a user reports that it does ([#11599](https://github.com/microsoft/vscode-remote-release/issues/11599)), but it may only hide the display from programs that read `DISPLAY`. Also not restricted: the copy of `~/.ssh/known_hosts` (at each attach, when the container has no such file; an empty file would stop it), and the user's dotfiles (cloned and installed in each new container; they cannot be switched off for one container).

## 11. Known gaps

Found when this summary was verified against the code. Gaps 1 to 7 and 9 to 12 are fixed or documented; gap 8 is resolved by one environment per repository and account.

1. **Fixed: the `runArgs` check could be bypassed.** The check runs on the repository's `runArgs`, but `docker run` gets them after the removal of `--name` (which also removes the next entry, even when `--name` is the value of another flag) and after entries that are not strings are dropped. `["--label","--name","--init","--label","-v/Users:/host"]` passes and becomes a bind mount. Fixed: entries that are not strings are refused, `--name` is removed with the same flag parser as the check, and the final `runArgs` are checked before `up`.
2. **Fixed: the empty `~/.gitconfig` did not stop the copy.** The Dev Containers extension skips the copy only when the file has a section other than `[filter]` or `[safe]`, so the computer's `~/.gitconfig` is appended at the first attach. Fixed with the documented setting `copyGitConfig: false` for the container (gap 3, section 5); the extension relies on no internal check of the Dev Containers extension (user decision).
3. **Fixed: `REMOTE_CONTAINERS_IPC` carries credentials, not the browser.** In Dev Containers 0.470.0 the socket answers only the requests of its forwarding credential helpers of Git and Docker, with the computer's credentials (read, store, and erase); `$BROWSER`, the `code` command, `openExternal`, Open in Browser, and port forwarding use the channels of VS Code itself. Fixed only with the documented settings of the Dev Containers extension for the container (`copyGitConfig` under both keys, `gitCredentialHelperConfigLocation: none`, `dockerCredentialHelper: false`, `githubCLILoginWithToken: false`): Git and Docker in the container do not use the socket. By user decision, no variable of the Dev Containers extension or the VS Code server is set or changed, so `REMOTE_CONTAINERS_IPC`, `SSH_AUTH_SOCK`, and `$BROWSER` keep their values, and the extension no longer writes the placeholder that kept the GPG agent out. Every container that the extension creates has these settings (label `devenv.container-version`). The sockets stay usable by a process that looks for them (section 10). To verify in real VS Code (V-8).
4. **Fixed: other named volumes could be mounted** (for example the Dev Containers `vscode` volume); only `devenv-*` names were protected. Rule: a mount may use anonymous volumes, tmpfs, the own workspace volume, and named volumes of the repository, but no volume that belongs to something else: another environment (by its name, or used by an environment of another account), another container (by the name of an anonymous volume), the workspace helper, the Dev Containers extension (by its names), or another program (by the labels of an existing volume). See section 1; volumes without labels stay a limit (section 10). With one environment per repository and account, a fixed volume name of a repository used by the environment of another account is refused by the same rule.
5. **Fixed: a repository label could replace the id label.** A repository `--label devenv.environment-id=…` won over the CLI's id label. Labels with the prefixes `devenv.` and `devcontainer.` in `runArgs` are refused (section 1).
6. **Fixed: `-e`/`--env-file` in `runArgs` could override the Git variables** (`GIT_CONFIG_*`, `DOCKER_CONFIG`, `GNUPGHOME`, `GIT_SSH_COMMAND`, `SSH_AUTH_SOCK`) for the container's main process and plain `docker exec`. The variables that the extension sets (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`, `DOCKER_CONFIG`, `GIT_SSH_COMMAND`, `GH_CONFIG_DIR`) and every other `GIT_CONFIG*` variable are refused in `-e`/`--env`, `containerEnv`, and `remoteEnv`, also of Features and the base image (section 1). `GNUPGHOME` and `SSH_AUTH_SOCK` are no longer set by the extension (user decision), so there is nothing of it to override. `--env-file` stays allowed below `/workspaces`: Docker applies `-e` after the file, so the extension's own values win; the other variables of the file are a documented limit (section 10).
7. **Documented: ports on `127.0.0.1` are reachable from every container** through `host.docker.internal` (Docker Desktop; on a Docker Engine, also a remote one, only when a configuration adds it), including ports that VS Code forwards for another account's environment. Binding to localhost protects against the LAN only. A known limit (section 10), because network access to the computer is allowed.
8. **The row "Environment of another account" and the `otherAccount` message reveal** that another account has an environment of a repository that the signed-in account can access. Resolved by one environment per repository and account: the row is gone, and `otherAccount` names only an environment that a command names by its ID (a row or the status bar item from before an account change, a restored window, an account change during an open, and an account change during Switch branch…: the environment whose branch it switched, also after a repository pick).
9. **Fixed for the configuration: a configuration could make VS Code forward ports on all addresses of the computer** (found with gap 3): `remote.localPortHost: allInterfaces` in `customizations.vscode.settings` becomes a setting of the container, which the window applies. Refused (section 1). An image or a process in the container can still write the setting into the machine settings file of VS Code Server (a known limit, section 10).
10. **Fixed (hotfix M1): the image metadata was checked before the Dev Container CLI resolved its variables.** The check of the label `devcontainer.metadata` before `up` read the mounts as written, but the CLI substitutes every entry at `up`: `source=${localEnv:NOPE:devenv-<other>-<id>}` (the default of a variable that is not set in the helper), `${env:NOPE:devenv-helper-cache}`, and the object form passed the check with the checks on and off and mounted the volume of another environment or the cache volume of the helper. The configuration and the merged configuration are resolved by `read-configuration`, but a Dockerfile's own `LABEL devcontainer.metadata` reaches the image when the CLI adds no label of its own, and the merged configuration is not checked for a container that was created with the checks off. Every check now resolves the variables as the CLI does (section 1).
11. **Fixed (hotfix GH): a variable name with `=` passed the rule for the protected variables.** A `containerEnv` key `GH_TOKEN=x` was not `GH_TOKEN`, but Docker sets `GH_TOKEN=x=<value>`. The rules now apply to the part of the name before the first `=`, and a name with a space or a control character is not supported (section 1).
12. **Fixed (hotfix review 1): the Dev Container CLI substitutes `runArgs` and `appPort` twice.** `read-configuration` substitutes the configuration once, and `up` substitutes the override configuration, whose `runArgs` and `appPort` come from that output, again. A text such as `$${env:NOPE:{}env:NOPE2:devenv-<other>-<id>}` passed the checks as `${env:NOPE2:…}` and became the name of another environment's volume at `up` (also `-v` of the helper cache, `-e GH_TOKEN=…`, and `--label devenv.…`, with the checks on; this was open on main before hotfix M1 too), and `${localEnv:A:$}{localEnv:B:8080}` became `-p 8080` on all addresses or `--rm`. With hotfix M1, a variable of the helper process that is not set (`TERM`, `OLDPWD`) was also left in a bind mount, where its default could add `type=volume`. An entry of `runArgs` or `appPort` with such a variable is now not supported, a variable that is left in any mount is not supported (also a bind mount), `HOME` is known as `/root`, and very long texts are not supported (section 1). The `containerEnv` of a Feature is an `ENV` of the image, not refused (section 2).
13. **Fixed (hotfix review 2): leftover variables of the label were decided on the substituted text.** The check read the substituted mount of the image metadata again to find the variables that the CLI resolves; a crafted mount could hide one in that text (P1), in the string or the object form, and the CLI resolved it at `up` to a volume of another environment, with the checks on and off. The leftovers are now found on the raw strings. Also: an expression `${devcontainerId:…}` with arguments was read as fields of the mount, although the CLI replaces it whole (P6, also on main before the hotfix); the label users (`remoteUser`, `containerUser`) were read unsubstituted for the ownership fix before `up` (P3); `${containerEnv:…}` in `runArgs` was refused although the CLI does not resolve it there (P4); and the size limits ran after checks that take quadratic time on thousands of entries (P2).

## 12. The switch per repository (host access checks off)

User request (2026-09-26): "application of the security policy shall be configurable per repository, by default it is on". The user setting `devEnvLauncher.hostAccessChecksOff` lists the repositories (`owner/name`, compared without case and surrounding spaces) whose host access checks are off; it has the scope `application`, so only the user settings count, and a workspace, a folder, or a repository cannot turn a check off. Invalid entries are ignored, with one warning. The context menu of a repository row has **Turn Off Host Access Checks…** (after a modal warning that lists what becomes possible) and **Turn On Host Access Checks**. The switch is read at each open.

**What changes while the checks are off.** Only the items of the class *computer* below are no longer refused. Published ports without an address are no longer bound to `127.0.0.1` (section 6): `runArgs` and `appPort` keep what the configuration writes. The row shows `host access unrestricted` with a warning in its tooltip, the log says so at every open, and each container that is created gets the label `devenv.host-access=unrestricted`. Turning the checks off applies when the container of the environment is created next, for example with **Rebuild**: an existing container keeps its current settings, such as published ports that are bound to this computer only (`127.0.0.1`). A container that was created with the checks on is not created again only because they are off now (it has less access). With the Docker socket (a bind mount or `--use-api-socket`), privileged mode, or the namespaces of the computer, the container can control Docker and every other environment, also the environments of other GitHub accounts, and read their files and tokens: the checks of account separation that stay on keep the configuration from using other environments by mistake, they are no boundary against a configuration that uses the Docker socket on purpose. The modal warning says so.

**Switching back on.** At the next open, the checks run as before. A container with `devenv.host-access=unrestricted` is not current while the checks are on (`containerIsCurrent`): it is created again from its environment image (the files in the volume are kept, the progress says so) when the configuration and the image metadata pass the checks. The merged configuration of such a container is not checked (the Dev Container CLI merges the metadata of the existing container into it, which holds what the checks allowed while they were off); the image metadata of the environment image is checked before `up`. If a check refuses, the open stops with the usual refusal and the container is not started; a window that is attached to it closes its connection. A refused update of an environment image (concept 7.7) is remembered with the state of the switch: a refusal while the checks were on does not block the update once they are off, and the other way round.

**Classes.** *computer*: lifted while the checks are off. *protected*: refused whatever the switch says: account separation, the identity of the owner account, the integrity of the extension, and items whose class is not clear (the safer choice). *unsupported*: options that the policy does not know or does not support, refused whatever the switch says. The unit test `src/core/helper/hostAccess.checksOff.test.ts` checks each row. The items of Docker Compose configurations have the same classes (section 13, `src/core/helper/composeAccess.checksOff.test.ts`); their containers all get the label `devenv.host-access=unrestricted` (with the checks on, `devenv.host-access=checked`: the model sets the label on every service either way, so that a label of an image that Compose builds or pulls during `up` cannot decide it; review round 2, D2-2).

## 13. Docker Compose configurations

A devcontainer.json with `dockerComposeFile` and `service` starts several containers: the dev service, which VS Code connects to, and the other services (for example a database). Docker Compose starts all of them with the Docker engine of the computer, so the rules of this document apply to **every service**, not only to the dev service. The technical design is in the [implementation notes, section 15](implementation-notes.md#15-docker-compose).

**How it is checked.** The extension reads the merged model of the compose files (`docker compose config`, all profiles) in the workspace helper, without the Docker socket, without network, and with the folder that holds the token hidden. It checks that model before anything is pulled or built, and again before the containers are created. Then Docker Compose runs exactly that model, rewritten as listed below; the compose files of the repository are not read again, so they cannot change between the check and the start. The check is an allow-list: a setting that it does not know is refused as not supported. Items are named `service <name>: …`. The texts that it checks are those that Compose and BuildKit use (review round 19, S19-1): a Compose that prints a literal `$` as `$$` has them unescaped first, so a `dockerfile_inline`, a bind mount path, or an `env_file` with a `$` is checked as it is built or mounted. Because of that, the configuration hash of an existing environment whose model has a `$` changes once: the next open asks about the rebuild as for any change of the configuration (nothing is removed; "Rebuild later" starts the containers as they are). Review round 20 (D20-1): the keys too (for example an environment variable or label named `a$b`), so a model with a `$` in a key changes its hash once in the same way. The Dev Container CLI does not read our model directly: it runs `docker compose config` on it and reads that output, in which such a Compose doubles every `$`. So the extension always writes the checked text of the Dockerfile of the dev service to a file of its own and builds that (review round 20, P20-1), also when the Dockerfile is a file of the repository: the Dev Container CLI and BuildKit read exactly the checked text, whatever `$` the path holds, and a change of the file after the check has no effect on the build.

The rules of sections 1 to 5 for devcontainer.json, Features, and the base image apply as for a single container (`mounts`, `privileged`, `capAdd`, `securityOpt`, `containerEnv`, `remoteEnv`, `remote.localPortHost`, and the image metadata before each start), with the same switch.

**Stop, start, Delete.** Stop and the Session Monitor stop every container of the environment, the dev container first; before each further container, the Session Monitor checks again that no window uses the environment. The sidebar shows the state of the dev container; while another service runs and the dev container does not, the row says so (`Stopped · services running`) and still offers Stop (review round 7, P7-2). Before a container of another service is removed (Delete, the switch to a single container, a stray next to a single container, and, review round 8, P8-3, a failed start of the switch to Docker Compose, a failed first open, and the containers of the project without the label of the environment at Delete), it is stopped with its own stop time, so that a database shuts down cleanly (review round 7, D7-1). A stopped service of a running dev container is started with `docker start`. Delete removes the containers of all services (never a container whose label `devenv.environment-id` names another environment, even when it has the label of the project), the networks of the project, and the images that Docker Compose built for it; the data of the services only when the user ticks them in the question of Delete, the others stay. The data of the services are the own volumes that a service other than the dev service mounts, whatever their name (also a volume with `name:` in the model): the extension records them at each open, and at Delete it also reads the volumes of the containers of the other services. Each volume that the extension creates for such a service also gets the label `devenv.service-data=true`, which keeps it in that question after a lost registry; an environment restored without that knowledge (a volume without that label, no build record yet) lists all its own additional volumes there, none ticked, as "additional volume (possibly data of services)" (review round 2, D2-3; review round 3, P3-4). After this update, the side services of an existing Compose environment are created again once (the label `devenv.host-access=checked` is new in their model, D2-2); their named volumes are kept. The images that the other services use as they are (for example `postgres:16`) are never removed as base images after an update or Delete.

**Switching between Docker Compose and a single container** happens only with a build (for example **Rebuild now**). The dev container that `up` creates (a single container, or the dev service of Docker Compose) carries the label `devenv.config-path` with the configuration path of the environment; after a lost registry, the restored entry gets its configuration path from it again (a path of the form `.devcontainer/devcontainer.json`, `.devcontainer/<folder>/devcontainer.json` with the folder names of the discovery, or `.devcontainer.json`; for any other path the label is left out, and any other value is ignored, review round 4, D4-2; review round 5, D5-2). The other services of Docker Compose do not carry it (review round 5, D5-1): with it, a switch between two configurations that share one compose file would change their configuration in Docker Compose, which would create them again and lose the data in their container file systems. The trade-off: when the dev container of Docker Compose is gone, the restore takes the default configuration (the containers of the other services, which `devenv.compose-service` names, still make the start ask before a switch). An environment without a build record (restored after a lost registry) whose containers are of the other kind than its configuration (also when only containers of the other services of Docker Compose are left) asks first, with a question that names the switch and what **Rebuild now** removes (the containers of the other services, or the single container, and the files outside the volumes; named volumes are kept) and points to **Select configuration…**; **Later** keeps the kind and starts the containers as they are, or, when the dev container of Docker Compose is gone, starts nothing and removes nothing; the question then says so and points to **Rebuild** and **Select configuration…** (review round 3, D3-2; review round 4, D4-3; review round 5, P5-4). **Switch branch…** asks the same question when the configuration of the new branch is of the other kind (review round 5, D5-3); the command **Rebuild** asks nothing, as it is the user's choice. When the start of the new containers of Docker Compose fails after the switch removed the single container, the containers that it created are removed again (their volumes stay), so that no later start of a single container takes one of them for its container (review round 3, D3-1); containers of Docker Compose that existed before that start (for example of an earlier switch that was cancelled) are kept (review round 4, D4-1). Containers of other services of Docker Compose next to a single dev container are strays: they are removed (their volumes stay), and the single container starts as usual (review round 4, P4-3). With **Rebuild later**, a failed update, or a refused update, the environment starts as it is: the containers of Docker Compose with `docker start`, a single container as before. From Docker Compose to a single container, the containers of the other services are removed: their named volumes stay; data in their volumes without a name is no longer used, and Docker keeps those volumes as unused volumes (the progress says so).

**Another dev service of the same compose file** (review round 22, D22-1). **Select configuration…** between two configurations of one compose file whose `service` differs (for example `.devcontainer/api` and `.devcontainer/web`) moves the name of the environment to the new dev service. Before `up`, the extension renames the previous dev container to the default name of Compose for its service (`devenv-<short id>-<service>-<n>`), so that Compose creates it again as another service and keeps its volumes without a name (for example `node_modules`); when the rename fails, the previous dev container is stopped and removed (its volumes stay; the user is told). A container that an earlier failed attempt of Compose left in the state `created` (`<12 hexadecimal characters>_devenv-<short id>-…`) is removed, and the container of the new dev service is stopped before the Dev Container CLI removes it. When the start with the selected configuration fails, the previous configuration stays selected, so the next open starts the environment as it was.

**Limits.**
- **Repository files in a service.** A service that mounts files or folders of the repository can read and change them, while it runs (for example a database that writes into a mounted folder). It sees only those paths of the workspace volume, not the token. Review round 9 (D9-1): the extension gives the files of the repository the owner of the remote user after a new container and after **Switch branch…**; it leaves those paths out, so the data that a service writes there keeps the owner that the service gives it (Postgres refuses a data folder of another owner). Review round 10 (D10-3): in those paths, files and folders of root still get the owner of the remote user (Git rewrites tracked files there as root at **Switch branch…**, for example of a source folder that a node service mounts, `./frontend:/app`), files of any other owner keep it; read-only mounts (`./init.sql:ro`, `./nginx:ro`) and `.git` are not left out at all. A service that runs as root with dropped capabilities (`cap_drop`) could lose write access to one of its files of root there. The paths are kept for as long as a container of a service may still mount them (D10-1: a service that "Rebuild later" did not create again keeps its old folder), also when the first start fails, and include the real path behind a link of the repository (D10-2). Review round 11 (G3, G4, G5): the list is computed from facts at each fix: the paths of the current model, the paths that the existing containers of the other services mount (read from Docker, also for an environment restored after a lost registry, which before left nothing out until its next start), and the paths of earlier models for as long as they still exist in the volume (also after `docker container prune` or a switch to a single container, which before dropped them). It holds at most 1000 paths; beyond (for example a data folder per host name, `./data/${HOSTNAME}`, one more at each start), the fixes give only the files of root in the whole repository the owner of the remote user, and files of any other owner keep it. After a new clone, before the first start, they get the owner of the remote user like every file. **Delete** removes them with the workspace volume; its confirmation names them ("Service data in the repository will be deleted: ./data/postgres.", D9-2). Review round 12: after a resumed clone, the fix before the start leaves the recorded paths and those of the existing containers out also on the path of a single container (D12-1). `find -xdev` stays only out of other file systems, and a local named volume lies on the file system of the workspace volume: so the fix in the dev container also leaves the paths below the repository at which the dev container mounts something else than the workspace volume to their owners (read with `docker inspect` of the dev container: a named volume that the dev service shares with a database, for example `pgdata:/workspaces/api/.pgdata`, a `node_modules` volume, a tmpfs, a bind mount; of the model, of the `mounts` of devcontainer.json, or of `runArgs`, also for a single container), where only files and folders of root change: the folder of a new `node_modules` volume, which Docker creates as root, still gets the remote user (D12-2). A path of a service behind a link of the repository (a mount of `./data`, `data -> storage/pg`) is resolved in the volume at each fix, also for an environment restored after a lost registry and at **Switch branch…**, and both paths are left out (P12-2). A path of a service longer than 4096 characters or deeper than 256 folders counts like more than 1000 paths (S12-1). Review round 13: a mount of the workspace volume below the repository in the dev container (for example `./data:/workspaces/api/pgview` while db mounts `./data`, or `../..` below the repository) is left to its owners too, since it shows files that db may own; the files are still fixed under their own path (D13-1). **Switch branch…** also leaves the real path that a path of a service had before the switch alone (a link `data -> storage/pg` of the branch before, a folder `data` on the new branch; D13-2). An anonymous volume of the dev container (for example a `node_modules` volume without a name) gets the owner of the remote user in full again, also for content that its image put there with another owner, while the host access checks are on; a named volume and a bind mount keep the rule above, since another container or environment may share them. A dev-only named volume whose image content belongs to another user than the remote user keeps that owner: change it with `sudo chown -R`, or use an anonymous volume (D13-3). Review round 14 (P14-1): a mount of the workspace volume at its own path (for example `..:/workspaces/api` and `../src:/workspaces/api/src` of the dev service, the subpath `api/src` at `/workspaces/api/src`) is no alias: its files get the owner of the remote user in full, as the rest of the repository (before, only files of root changed there, so after a change of the uid of the remote user its old files kept the old uid). The extension takes the subpath from `docker inspect` (`HostConfig.Mounts`) and checks in the dev container (`/proc/self/mountinfo`) that the mount shows exactly that folder of the volume; when a link in the volume makes it another folder, or the check cannot be made, the mount stays left to its owners. Review round 15 (K4 = D15-2): a mount of the dev container in `.git` (for example a volume that db shares at `/workspaces/api/.git/pg`, or, with the checks off, a bind of the computer at `.git/hooks`) is left to its owners too (before, the rule that keeps `.git` out of the paths of the services dropped it, and the fix gave its files to the remote user); the rest of `.git` still gets the owner of the remote user in full, and the paths of the services themselves still never include `.git`. - **Other services on the network.** The services share the networks of the project and reach each other by name. Every published port is bound to `127.0.0.1`, but, as in section 10, every container reaches `localhost` of the computer through `host.docker.internal`.
- **Variables of other services.** A service other than the dev service may set `GH_TOKEN` and the variables of Git: it has no token of the owner account and no Git configuration of the extension.
- **Remote `include` and `extends`** (Git, OCI) do not work: the model is read without network. Local ones can only name files of the repository and of the helper image (the token is hidden).
- **Newer Compose versions.** The helper installs the current Compose plugin; a new setting of a newer version is refused as not supported until the policy knows it.
- **Old images of rebuilt services** stay as dangling images (`docker image prune` removes them).
- **Links swapped while the build runs.** The real paths of the build contexts and Dockerfiles are read in the model run, before the build. A running dev container of the environment can change a link of the repository between the check and the build (the build runs minutes later, in another helper run that mounts the cache volume): the builder then follows the new link (review round 20, P20-1: not for the Dockerfile of the dev service, whose checked text is built from a file of the extension; the build context and the Dockerfiles of other services still are). Only a process of the environment itself can do so, but the new link can lead into the cache volume that all environments share (`devenv-helper-cache`, with the files that the Dev Container CLI generates for every environment), not only to the files of the environment: those files can then end up in the image of this environment.
- **Labels of images that Compose builds** during the start (the other services with `build`) are not checked before the start; the model sets the labels of the extension on every container, which win over those of the image.
- **An image of another service that is not there yet** (Compose pulls it during the start) is started without the check of its labels.
