# Implementation Notes — Version 1

These notes add the technical decisions that the concept ([vscode-dev-environments.md](vscode-dev-environments.md)) leaves open. The concept is the source of the requirements. If a note and the concept differ, the concept wins, and the note must be corrected.

## 1. Scope

- Phase 1 and phase 2 of the concept (section 12), including Docker Compose configurations (`dockerComposeFile` and `service`, section 15).
- Not in scope: phase 3 (profile template, backup of unpushed work, `build.cacheFrom`, Podman).
- The verification tasks V-1 to V-12 are not done yet. Code that depends on an unverified assumption has a comment `// Assumption (V-n): …`, so that a later check can find it.

## 4. Local storage

All files are in the global storage folder of the extension (`context.globalStorageUri.fsPath`), on the local computer.

| File | Content | Writers |
|---|---|---|
| `registry.json` | Environment Registry (concept 7.5) | windows, Session Monitor |
| `repositories-<account ID>.json` | Stored result of the discovery of one GitHub account (concept 6.2, 7.4); the account ID is the numeric GitHub user ID of the session. It also records the scan scope it was built with (`scope`, lower-case logins, sorted; empty: all repositories) and the repositories without configuration with their `pushedAt` and default branch (`withoutConfiguration`, for the incremental detection). A list without either field is invalid and built again. | windows |
| `sessions/<window-id>.json` | Window status file (concept 7.9) | one window |
| `pending/<environment-id>.json` | Pending connection file (concept 7.9). Ignored after 2 minutes; the Session Monitor deletes one whose `createdAt` is more than an hour from now (monitor cleanup, user decision 2026-09-29). | windows |
| `operations/<environment-id>.json` | Pending operation, for example `rebuild` (concept 7.14) | windows |
| `disconnect/<environment-id>.json` | Request from a window to the window that is connected to the environment: close the connection first, then hand off the stop, rebuild, or delete (concept 6.2, 7.14). Dropped after 60 seconds; the Session Monitor deletes one whose `requestedAt` is more than 10 minutes from now, and Delete deletes the one of its environment (monitor cleanup, user decision 2026-09-29). | windows |
| `reopen.json` | Reopen record (concept 7.10) | windows |
| `monitor.json` | Settings for the Session Monitor: waiting time, `stopOnClose`, `respectShutdownActionNone`, and (unit 7, PR 2) `remoteStopAfterSeconds`, the time limit of the heartbeats to a remote Session Monitor | windows |
| `computer.id` | Unit 7, PR 2: the id of this installation, 32 random hex digits (128 bits), the source of the heartbeats to a remote Session Monitor (section 16). Created with `wx` by the first reader (EEXIST: read it); invalid content is replaced. No secret. | windows, Session Monitor |
| `monitor.lock` | Process ID of the running Session Monitor | Session Monitor |
| `monitor.version` | Protocol version of the running Session Monitor, `{ "pid": 1234, "version": 1 }` | Session Monitor |
| `monitor.exit` | Request of a window to an older Session Monitor to exit, `{ "pid": 1234, "requestedAt": "…" }` (`requestedAt` only for diagnostics) | windows; Session Monitors delete it when it is left over |
| `monitor.log` | Log of the Session Monitor (the process has no output channel), at most about 1 MB | Session Monitor |
| `helper.json` | State of the workspace helper images (section 7): per helper tag the base image and its digest at the build, `builtAt`, the ID of the image that this installation built (`imageId`), the helper generation of that build (`generation`), `checkedAt`, `lastUsedAt`, a rebuild that a check asked for, and the marks of the cleanup for foreign and removed tags; the time of the last cleanup. `imageId` and `generation` are for diagnosis; no code reads them. User decision 2026-09-29: no previous helper image | windows |

Rules:
- Every JSON write is atomic: write a temporary file in the same folder, then rename it. The temporary file is `.<name>.<pid>.<8 hex digits>.tmp` (`atomicJson.ts`; the cut of `monitor.log` to its newer half in `FileLogger` names its temporary file the same way, review round 8 of PR #63, R8-1); one that a killed write left behind is deleted by the sweep of the Session Monitor when its modification time is more than an hour from now (section 12).
- Read-modify-write of `registry.json` happens under a lock (a lock folder created with `mkdir`, removed after the write; a lock older than 10 seconds counts as stale).
- `deactivate()` uses only synchronous file writes.
- In the workspace volume (not in the global storage), the folder `/workspaces/.devenv+` holds the configuration of the container: `gitconfig`, `credentials.gitconfig`, `docker/`, and `gh/` (only gh's own `config.yml`, no secret) (concept section 9, section 7 "Container-only Git" below). Unit 15: the token is not in the volume. The token and the sign-in of the GitHub CLI are in the tmpfs `/run/devenv` of the running dev container (`TOKEN_FOLDER`).

## 5. Names and labels

- Environment ID: `crypto.randomUUID()`. Short ID: the first 8 characters. An ID is not used when an entry of the registry has its short ID or its volume exists (at most 5 tries), because the names end in the short ID: two environments of one repository (of two accounts) get different names.
- Volume and container name: `devenv-<owner>-<repository>-<short id>`, lower case, only `[a-z0-9_.-]`, at most 63 characters.
- Environment image: `devenv-<short id>:<build number>`.
- Labels on the volume: `nimblescape.devenv.environment-id`, `nimblescape.devenv.repository`, and `nimblescape.devenv.owner-id` (the GitHub user ID of the owner account; `reconcileFromVolumes` restores the owner from it, and its login at the next open). Additional volumes: before `up` creates a container, the pipeline creates each named volume that it mounts (configuration `mounts`, the `runArgs` that Docker gets, and the image metadata; `mountedVolumeNames`) and that does not exist yet, with the same three labels and `nimblescape.devenv.volume=additional` (`LABEL_VOLUME`, `VOLUME_KIND_ADDITIONAL`, `additionalVolumeLabels`). Only these labels make a volume an environment's own (`isOwnVolume`: `nimblescape.devenv.environment-id` is its ID, and `nimblescape.devenv.owner-id` is its owner): the pipeline records such volumes as additional volumes, and Delete removes only them. It records also the existing additional volumes of other environments of the same owner that the environment mounts (`recordedVolumes`, `isSameOwnerAdditionalVolume`), only to protect them (host access policy below). After a lost registry, `reconcileFromVolumes` restores these own volumes (`nimblescape.devenv.volume` with the environment's labels), the additional volumes of other environments of the same owner that the surviving container mounts (`isSameOwnerAdditionalVolume`), and, to protect them (`protectedMountedVolumes`), the named volumes without labels of Dev Environments that the surviving container of the environment mounts (`listEnvironmentContainers`, label `nimblescape.devenv.environment-id`), for example volumes that Docker created at `up` without labels: not the workspace volume, not a name that `foreignVolumeName` gives to something else, not an existing volume with labels of another program or environment (`volumeLabelOwner`), and not a volume that does not exist. As recorded volumes, the policy refuses them to the environments of other accounts; Delete keeps them (`removableVolumes`: not the environment's own) and records them in `keptVolumes` with the owner. A name with `${devcontainerId}` is not created: Dev Container CLI 0.89.0 substitutes `${devcontainerId}` in `read-configuration` only when a container with the id labels exists (`dA&&(q=yn(q,EA=>tg(ht(nA),EA)))` in `devContainersSpecCLI.js`), so before the first `up` the name is unknown; Docker creates that volume at `up` without labels, and it is never the environment's (Delete keeps it). The container gets `nimblescape.devenv.environment-id` through the CLI option `--id-label`, and `nimblescape.devenv.container-version=1` through `runArgs` (`CONTAINER_VERSION` in `src/core/names.ts`, the version of the container setup; raise it when a change of the setup needs existing containers to be created again, for example a change of the settings of the Dev Containers extension for the container, which reach it only through the label of a new container). A label of `runArgs` whose key starts with `nimblescape.devenv.` or `devcontainer.` is refused (section 7, host access policy), except these two labels of the override configuration with their exact values (`CONTAINER_VERSION_LABEL`, `CONTAINER_CONFIG_UNKNOWN_LABEL`). A container without this label, or with an older value, is created again from its environment image (`up --remove-existing-container`, no build, the volume is kept), and the progress shows that the files outside the volume are removed; without the workspace helper, nothing is started (no `docker start` fallback, user decision 2026-09-29). A container created while the configuration could not be read gets `nimblescape.devenv.container-config=unknown` (and no `runArgs` or `appPort` of the repository); it is created again in the same way at the first open that can read the configuration (`containerIsCurrent`).
- Label prefix (user report 2026-09-27): every label key of the extension starts with `nimblescape.devenv.` (`LABEL_PREFIX`; the keys are in `EXTENSION_LABEL_KEYS` in src/core/names.ts, and `names.test.ts` fails for a label of the prefix in the code that is not in the set, and for any `devenv.…` label in the code). Other tools use the prefix `devenv.` (an in-house image tool named devenv puts `devenv.fingerprint` and `devenv.inputs` on its images), so the extension no longer uses it: the host access policy refuses every key with `nimblescape.devenv.` (and `devcontainer.…` except `devcontainer.metadata`, `isReservedLabel` in src/core/policy/rules.ts) in `runArgs`, in the labels of a Compose service, its build, its volumes and networks, and on the images, and allows every other key, also `devenv.…`. No migration: containers, volumes, and images with the old `devenv.…` labels are not found; the environments are created again.
- Registry entry: `owner: { id, login }`, required: an entry without a valid owner is invalid, left out when the file is read, and the next write keeps a copy of the file first, as for any invalid entry. The rule `isAvailableTo` (src/core/ownership.ts) applies to the sidebar, the pickers, all commands, the reopen, restored windows, pending operations, and disconnect requests; the environment service checks it again in each operation, and the controller once more right before it connects the window. One environment per repository and account (D-3): the registry refuses a second entry with the same repository (case-insensitive) and owner, and `findForAccount(repository, accountId)` gives the environment of the signed-in account. `EnvironmentService.open` reads the session first and uses its account: its own environment, else a new environment. The controller looks up only the environment of the signed-in account for a repository (for Start, Search, the switcher, Switch branch…, and Select configuration…, the account of a session with a working token: while GitHub rejects the token, the new sign-in comes before the environment is chosen, so an account change at that sign-in chooses the environment of the new account, also for Try again of a Start; Stop and Delete ask for no new sign-in); A restored window checks the account again right after it takes its environment, and after a failed open pipeline (an account change during its checks, which found no environment of the window yet), and leaves an environment that the account may not use, with its token file. `otherAccount` applies only to an environment that a command names by its ID (a row or the status bar item from before an account change, a restored window, an account change during an open, and an account change during Switch branch…: the environment whose branch it switched, also after a repository pick). Try again of a first open of Switch branch… or Select configuration… runs the step of the command after its pick again, with the same branch or configuration, for the account signed in then: an environment that the account has then gets the branch switched or is rebuilt with the configuration (nothing more when it has that configuration already), as the command does. `reconcileFromVolumes` restores one environment per repository and owner (label `nimblescape.devenv.owner-id`; a volume without a valid owner label is skipped), and only volumes whose name is `resourceName(repository, id)` of their labels; after each `up` (also a failed or cancelled one) and at each open of a running container, its mounted named volumes whose labels make them its own (`isOwnVolume`) join the additional volumes too (a failed first open removes the environment, and its additional volumes stay with its account, a known limit); the additional volumes of a restored entry are the volumes with `nimblescape.devenv.volume` whose labels make them its own. Every other volume (anonymous volumes, volumes of other programs or environments, volumes without the owner label, and `${devcontainerId}` volumes) is never recorded, restored, or removed. Delete removes only the additional volumes that the question listed and the user confirmed (`additionalVolumesToRemove`, also in pending operations and disconnect requests), and only when their labels make them the environment's own and no other environment records them and no Delete of another account kept them (`removableVolumes`); each other one is kept with a log line that names why (for example a volume without the labels of the environment: the user removes it). The question lists only the volumes that Delete would remove (`EnvironmentService.removableAdditionalVolumes`; none when Docker does not answer), so it never offers a volume that it keeps. The additional volumes that a Delete keeps (not confirmed, not removable, or all of them at the Delete of `filesMissing`) are recorded in the same registry change that removes the entry (`EnvironmentRegistry.remove(id, { kept, removed })`, `RegistryFile.keptVolumes`: name, owner, time; one record per name and owner; a removed volume drops all records of its name); `hostAccessInput` adds the records of other owners whose volume exists to `foreignVolumes`, and drops (`forgetKeptVolumes`) the records of a mounted name whose volume no longer exists. Only kept volumes that exist are recorded; a failed first open records the additional volumes that it leaves behind the same way. Invalid records are left out when the file is read, and the next write keeps a copy of the file first (`droppedRecords`). The records cannot be restored after a loss of the registry (container restrictions, section 10).

## 6. Docker

- **Finding the CLI.** The extension host on macOS often has a short `PATH`. Search `PATH`, then `/usr/local/bin`, `/opt/homebrew/bin`, `/Applications/Docker.app/Contents/Resources/bin`, and with `HOME` `~/.docker/bin` (Docker Desktop's per-user CLI setting) and `~/Applications/Docker.app/Contents/Resources/bin` (macOS; user decision 2026-09-27), and `C:\Program Files\Docker\Docker\resources\bin` (Windows). While the CLI is missing (or cannot be started), the extension searches again, at most every 10 seconds, so a Docker installed while VS Code runs is found without a reload.
- **Docker start** as in concept 7.6: `docker info` as the check; `docker desktop start`, and the fallbacks per platform; on Linux with Docker Engine, only the message with `sudo systemctl enable --now docker` and the action **Start Docker**, which runs that command in a terminal after a confirmation. Repeat `docker info` every 2 seconds for at most 2 minutes.
- **Installation plan** (`installPlan` in src/core/docker/dockerSetup.ts; the button **Install Docker** of the sidebar). A modal confirmation lists the exact commands, or the download URL and the target file, and says that an administrator password may be requested in the terminal. The step first looks the CLI up (`lookUpCliNow`): found → "Docker is already installed on this computer." and nothing runs; **Install WSL 2** likewise with `wslReady`. Commands run in a new terminal "Install Docker" (`createTerminal` with `installTerminalOptions`: `/bin/sh` on macOS and Linux, the Windows PowerShell of `%SystemRoot%` on Windows, `cwd` the home folder, `strictEnv` with a fixed `PATH` on every platform (Windows: the folders of `%SystemRoot%` and `%LOCALAPPDATA%\Microsoft\WindowsApps`, where winget lives) and a few kept variables of the computer (`HOME`, `USER`, `LOGNAME`, the language, `TERM`, a proxy, the certificate variables `SSL_CERT_FILE`, `SSL_CERT_DIR`, `CURL_CA_BUNDLE`, on macOS the `HOMEBREW_*` settings, on Windows the folders and names of the user), so that terminal profiles, `terminal.integrated.env.*` of the workspace, the search path of the shell that started VS Code, and files of the opened folder change nothing; on macOS the command names the full path of the Homebrew that was found (a path with unusual characters: the download instead); `show`, `sendText`): joined with `&&` on macOS and Linux, one line per command on Windows (Windows PowerShell before version 7 has no `&&`).
  - macOS: Homebrew found (`brew` in `PATH`, `/opt/homebrew/bin`, or `/usr/local/bin`) → `brew install --cask docker-desktop` (the cask `docker` was renamed to `docker-desktop`). ## 7. Workspace helper

- **Image.** `resources/helper/Dockerfile`, with `ARG BASE_IMAGE=node:24-trixie-slim` (Node.js 24 LTS on Debian 13). It installs `git`, `ca-certificates`, `curl`, `openssh-client`, `tini` (the init process), `util-linux` (`flock`) and `coreutils` (`timeout`) for the lock of the heartbeat records of the remote Session Monitor (`flock` since review round 2 of PR #58, `timeout` since round 3; listed here in round 4), the Docker CLI with the buildx and the Compose plugins (Debian packages `docker-ce-cli`, `docker-buildx-plugin`, and `docker-compose-plugin` from `download.docker.com`; the Compose plugin is not pinned, like `docker-ce-cli`), and `@devcontainers/cli` in a pinned version. It sets `git config --system --add safe.directory '*'`, because the helper runs as root on files of another user.
- **Tag.** `devenv-helper:<first 12 characters of sha256(Dockerfile content + CLI version + helper generation)>` (the generation `HELPER_GENERATION`, below, as `\ngeneration <n>`: review round 3 of PR #64, P5, so raising it gives a new current tag, which is built, and an image of an older generation never stays the current helper), label `nimblescape.devenv.helper=true`. The extension builds the image when this tag is missing (after the installation, and after an extension update that changes the Dockerfile, the CLI version, or the helper generation; in the background right after the activation when the local Docker runs, otherwise at the next open: review round 7 of PR #64, R7-2), with `--pull`; without it when the registry does not answer or when the build with `--pull` fails (for example the pull limit of Docker Hub, which counts the pull of the daemon but not the digest request of the extension): the image then comes from the local base image, and the next check that gets a digest asks for a build with a fresh base image. **Refresh:** only the open pipeline does it, and only with the setting `updateImagesOnConnect` on; the other helper runs (for example of a delete or a branch switch) only build a missing tag. At most once a week per tag, the extension reads the registry digest of the base image, with the registry client and the credentials of the image check (section 9) and its own 5-second limit, in the background: the open does not wait for it, so it overlaps with the image check and adds no wait (NFR-08). A changed digest makes the next open build the same tag again with `--pull --no-cache` (new base image, Debian packages, and Docker CLI; the progress shows "The workspace helper is being updated.") and remove the previous image if it has no tag anymore. No answer from the registry keeps the image, and the check runs again at most once a day; a failed build keeps the image (Docker moves the tag only after a successful build) and checks again a week later. An image built with `--pull` without a recorded digest (built before `helper.json` existed, or the registry answered without a digest) gets the current digest, without a build. A window reuses the result of its helper check for an hour, but an open first checks that the tag still has the image of that result (`docker image inspect <tag>`; review round 4 of PR #64, R4-1: another window may have rebuilt the tag and removed the image that it had before, or a prune removed it): when the tag is gone or has another image, the result is not reused; when Docker does not answer, it is. A helper run of an open that finds its image gone resets the result of the window when it still holds that image, so the next open resolves the helper image again instead of pinning the removed ID. **Cleanup:** at most once a day, of the images with the label `nimblescape.devenv.helper=true`, except the image of the current tag, the extension removes dangling images and helper tags that no window used for 7 days (`lastUsedAt`, written at most once an hour). A helper tag that `helper.json` does not know is foreign (another extension version, possibly of another installation of VS Code such as Insiders, which has its own `helper.json`): it first gets 7 days of grace, so a helper that old windows of another extension version still use is not removed at once. A removed tag keeps a tombstone in `helper.json` for 90 days: when the tag comes back, another installation built it again and uses it, so it is not removed again, and two installations do not remove each other's helper in a loop. Tags of other repositories are never removed, and never with force; a failed removal (for example an image that a helper container uses) is logged and tried again at the next cleanup. Two windows can do this at the same time: each write of `helper.json` is atomic, and the file is advisory, so at worst a check or a build runs twice. **No previous helper image** (user decision 2026-09-29: "there shall be no case where we need a previous helper image"): every start of a stopped environment runs through the Dev Container CLI (`up` and `run-user-commands`, so `postStartCommand` always runs); there is no `docker start` fallback. The one `docker start` left is D-22: stopped side services of a Docker Compose dev container that runs already (the CLI does not call Compose for it). When the current tag is missing and cannot be built (offline after an extension update: Docker Hub, download.docker.com, or npm cannot be reached), no other helper image is used: the ensure fails, and the open fails with “The workspace helper could not be prepared.” (`helperFailed`); the next open tries the build again. *Background prebuild* (`HelperPrebuild` in `src/core/helper/helperPrebuild.ts`, started by `extension.ts` without being awaited): when `helper.json` has no record of the current tag (or only a removal mark; review round 5 of PR #64, R5-2: this record alone decides, so after an update that changed the tag the windows that start first build it and later windows find its record), it builds the current helper image in the background on the local Docker engine, so the first open after an update does not wait for it and the network is needed right after the update rather than at the first open. It asks Docker nothing when it is not due (so an activation does not wake Docker Desktop from its Resource Saver mode), does nothing when the Docker context is a remote host (that host builds its helper at its first open) or when the local Docker does not answer `docker info` (Docker is never started for it; the next activation tries again), and uses `WorkspaceHelper.prebuildImage`, which shares the cached promise of the window with `ensureImage` and the helper runs: an open that starts during the prebuild waits for that build, and a prebuild that starts during the build of an open joins it, so within a window the tag is never built twice. Across windows there is no lock (review round 6 of PR #64, R6-1: a lock left behind by a window that closed or reloaded during the prebuild would block the prebuild of every window for 30 minutes, which is worse than the duplicate build it prevents): windows that start at the same time may each build the tag once (BuildKit shares the layer cache; the extra images are dangling and the daily cleanup removes them), and windows that start later find the record in `helper.json` and do nothing. A caller that joins the shared build of the window (an open, a helper run, or the prebuild) can cancel its own wait with its signal, without cancelling the build, and gets its progress (`onBuild`) too (review round 5 of PR #64, R5-1). It is cancelled when the extension is deactivated (`dispose`, which ends the `docker build`); an open that waited for it then builds for itself. It logs to the Dev Environments output: the build, its output, and its result (a failure is a warning, and the next open tries again). The helper image of an open is resolved once, by its first `prepareHelper` (`HelperImageUse`: the tag and the ID of its image), and passed to every helper run of that open (review round 2 of PR #64, A-N1). `prepareHelper` takes it from the return value of `WorkspaceHelper.ensureImageUse` (the image that this call awaited), never from a callback, so a reset of the cache of the window meanwhile (another engine, a missing image at another run) cannot leave the open with a tag without its ID (review round 3 of PR #64, P1). Every helper run of an open uses the image ID (review round 3 of PR #64, P2): a rebuild of the tag by another window (`--pull --no-cache`) or a build of another installation never changes the helper image in the middle of an open, and an engine switch in the middle of an open finds no such image. The ID of the current tag is the one of the image that the build of this ensure made (review round 3 of PR #64, P4), or else the one that the existing tag has at the ensure. Review round 4 of PR #64 (R4-2/R4-3): each build gets a label with a random nonce, `nimblescape.devenv.build-id=<32 hex characters>`, and `ContainerAdapter.buildImage` then finds its image by that label (`listImagesByLabel`: `docker image ls --filter label=… --no-trunc`, and the same with `--filter dangling=true`, so an image whose tag another build moved meanwhile is found too); exactly one image is expected, otherwise the ID is unknown (with a warning). Only when the ID cannot be read at all does an open run its tag by the tag. Thus the configuration that the Dev Container CLI of that image read and checked is built and started with the same CLI, also when another open in the window (of another repository, since opens are exclusive only per repository) resolves another helper image meanwhile. The later `prepareHelper` calls of the same open do nothing. Helper runs outside an open (stop, delete, branch switch, Git summary) use the tag that the window resolved last. `helper.json` keeps only a full image ID (`sha256:` and 64 hex characters). *Helper generation* (review round 2 of PR #64, A-N2; review round 3 of PR #64, P5): the code constant `HELPER_GENERATION` (`src/core/helper/helperImage.ts`, now 1) is part of the tag hash, so a release that fixes a security problem in the helper image (its tools, its Dockerfile) raises it and every user's helper is built again, also when neither the Dockerfile nor the CLI version changed; it is also recorded per tag at each build and rebuild (`generation`, a positive safe integer, for diagnosis; `parseHelperState` drops any other value). When the image of the tag of an open is gone at a helper run (a prune, or the removal of the old image after another window rebuilt the tag), `docker run` answers "No such image": the run fails with `helperFailed`, without a build (review round 2 of PR #64, A-N1; review round 3 of PR #64, P2: a build may give another image, with another CLI than the one that checked the configuration; the next open resolves the helper image again), and the cache of the window is reset when it still holds that image (review round 4 of PR #64, R4-1). A helper run outside an open that finds its tag gone builds it again once. A `helperFailed` of a helper run in Step 8 (the build, `up`, or the restore with the previous environment image) marks the helper unavailable for the rest of the open (no Git setup); a current container that already ran when Step 5 found it, and still is that container, opens as it is (review round 10 of PR #64, R10-1: not one that the restore started meanwhile), without the restore (which needs the helper too); otherwise the open ends with `helperFailed` (review round 3 of PR #64, P6). The warning that the update failed (`buildFailed`) is left out when the `helperFailed` is itself the failure of the update (of the build, or of a helper run before or at the `up` of the new image); when the update failed for its own reason and the restore then meets a `helperFailed`, both warnings stay (review round 11 of PR #64, R11-3). At a switch between Docker Compose and a single container, or of the dev service of Docker Compose, a `helperFailed` of `up` after the switch removed or moved a container keeps the cleanup of the switch (nothing opens as it is: the containers of the other kind are gone, the previous dev container stays stopped) and ends the open with `helperFailed`, with the detail of the switch, not with `startFailed` (R4-5). - **Run.** Each helper run is `docker run --rm -i` with the workspace volume at `/workspaces` and the label `nimblescape.devenv.helper-run=true`. Only the Dev Container CLI runs (read-configuration, build, up) also get the Docker socket and the cache volume `devenv-helper-cache` (`--user-data-folder`: only what the CLI keeps there itself; CLI 0.89.0 downloads Features into a new folder below the helper's temporary folder at each run, so the volume is no Features cache, and a build or rebuild with Features needs internet access). Git runs (clone, switch branch, Git summary) and the file-reading scripts get neither, because Git runs programs that the repository configuration names (filter drivers). Runs that need no network (Git summary, reading and listing configurations) use `--network none`.
- **Token for the clone.** The token never appears on a command line, in an environment variable of a container, or in `.git/config`. The helper receives it on standard input, writes it to a `tmpfs` mount, and a Git credential helper reads it from there. The remote URL is `https://github.com/<owner>/<repository>.git`.
- **Container-only Git** (concept section 9). At each open, before `devcontainer up` (and also when the container runs already), a helper run without the Docker socket, the cache volume, network, and a token (`GIT_FILES_SCRIPT`) creates `gitconfig` when it is missing (user.name: the GitHub profile name or the login; user.email: `<databaseId>+<login>@users.noreply.github.com`, from `viewer { databaseId login name }`, with the session account as fallback) and ensures its section `[credential "https://github.com"]` (an empty helper, then the helper of the container, which reads `/run/devenv/github-token`), creates `credentials.gitconfig` with an example in comments when it is missing (never overwritten), creates `docker/` and `gh/` (mode 0700; `gh/` only for gh's `config.yml`). Everything gets the numeric owner of `/workspaces/<name>`; on a first open this runs after the ownership fix, and after each creation of a container the ownership fix also covers `/workspaces/.devenv+`. A link in place of a folder or of a file is removed first. A failure is a warning; the environment opens. Exception: a `helperFailed` of the Git setup right before `up` ends the step like one of `up`, with no warning, and nothing is removed for a switch (section 7; review round 11 of PR #64, R11-2; round 12, R12-1: also for Docker Compose, whose Git setup now runs before the switch removes or moves a container). The question for `viewer` starts as soon as the session is known (it overlaps with the Docker start, the clone, and the image check), is shared per account in the window, has a time limit of 5 seconds, and after a failure the fallback counts for 10 minutes.
- **Token in the memory of the container** (unit 15, user decision 2026-09-26, `src/core/helper/containerToken.ts`). The dev container has the tmpfs `/run/devenv` (`TOKEN_TMPFS`: `rw,nosuid,nodev,noexec,size=1m,mode=0700`). The token is kept in memory, not in the volume, and is gone when the container stops; the kernel may swap it to the swap space of the computer or the Docker VM (a tmpfs is swappable memory). The tmpfs: a single container gets `--tmpfs` as the last entry of the `runArgs` of the override configuration, the dev service of Docker Compose an entry in its `tmpfs` in the up model (the other services none; the build model none). The checks accept exactly this `--tmpfs` value only in the override configuration and in the merged configuration of an existing container (`runArgsFindings` with `cleared`), and refuse every mount of a configuration at or below `/run/devenv` or `/var/run/devenv` (`configFolderTarget`, `TOKEN_FOLDER_ALIAS`, class `unsupported`, also with the checks off; a clearer message only), and a `shared`/`rshared` propagation (`-v …:rshared`, `bind-propagation`, Compose `bind.propagation`) at `/` or a parent of either (`tokenPropagationTarget`, class `protected`): `mounts`, `-v`, `--mount`, `--tmpfs`, Compose `volumes`, `tmpfs`, `secrets`, `configs`, and the targets of `volumes_from` of the dev service. `/run` itself stays allowed: Docker mounts ours on top. Lifecycle token (user decision 2026-09-27): when `up` ran, the token is written right after `up` (`runUserCommands` of the pipeline, into the container of the result of `up`, as the remote user of that result), before `devcontainer run-user-commands` (section 8); otherwise in `finish` of the open pipeline, after the ownership fixes and `~/.gitconfig`, on every path where the container runs (running already, or started by `up`; `finish` skips the write when it was done after `up` for the same container), `docker exec -i -u root <container> sh -c TOKEN_WRITE_SCRIPT sh <remote user> <login>` gets the token of the session on standard input only (never in argv or a variable; the output and errors are logged without it). The script (POSIX sh, no awk, dash and BusyBox; tools: `cat`, `id`, `chown`, `chmod`, `mkdir`, `ln`, `rm`, `tr`, `wc`, `stat`, `find`, `ls`) goes into `/run/devenv` (`cd`, then only paths relative to `.`) and writes nothing unless that folder is our tmpfs (`OWN_TMPFS`, review of unit 15, T1/T2: `stat -f -c %T .` is tmpfs; the device of `.` (`stat -c %d`, as major:minor) is on exactly one line of `/proc/self/mountinfo`, with the mount point `/run/devenv`, the root `/`, no optional fields, type tmpfs, `nosuid,nodev,noexec`, the super options `rw,size=1024k,mode=700` (`TOKEN_TMPFS_SUPER_OPTIONS`; SELinux may add `seclabel` or `context=` in between); no parent up to the root of the container at `/run/devenv` or `shared:`; no mount point below `/run/devenv`) (exit 3); a folder that root cannot enter (mode 000 of the user) is given back to root first, only when it is our tmpfs; then it makes the folder `root:root` 0700, takes everything in it back top down without following links (`find . -mindepth 1 -exec chown -h 0:0 {} \; -type d -exec chmod 0700 {} \;`, review of unit 15, P1: root needs no `DAC_OVERRIDE`) and empties it (so no process of the user changes it while it is written; exit 5 when `ls -A .` fails or lists anything), writes `github-token` (0600), `gh/` (0700) with `hosts.yml` (0600: both forms that `gh` reads, the keys `oauth_token`, `user`, and `git_protocol: https` of the host `github.com` and `users.<login>.oauth_token`, the token copied with `cat` from the token file) and `gh/config.yml` as a link to `/workspaces/.devenv+/gh/config.yml` (gh writes that file with `O_TRUNC` through the link, and never puts a token into it: it writes the hosts to `hosts.yml`), gives everything to `id -u`/`id -g` of the remote user (a numeric user as it is): the files first, then `gh/`, and the folder itself last. The login is checked as a GitHub login (1 to 39 letters, digits, hyphens, and underscores, starting with a letter or a digit), in TypeScript and in the script; a login that fails the check, or a token with characters that YAML would need to escape, gives no `hosts.yml` (a note, Git still works). On a failure after the tmpfs check, the folder is emptied again (trap). Exit 5 when root may not change the owner (`--cap-drop` of `CHOWN`) for a remote user other than root: the trap empties the folder again. A failure is logged and gives `Messages.gitSetupFailed`; the open continues, and the lifecycle commands run without the token. The lifecycle commands run after the write and have the token (user decision 2026-09-27). When a window leaves an environment because of the account (sign-out, or another account), the controller first empties `/run/devenv` of the running dev container (`TOKEN_REMOVE_SCRIPT` with `docker exec -u root`, and again as the remote user of the entry when that fails, time limit 30 seconds; only in our tmpfs (`OWN_TMPFS`: exit 3 when there is no tmpfs or another one, nothing removed); as root after the same take-back, as the user after mode 0700 on its folders; exit 1 when `ls -A .` fails or lists anything); best effort, logged. A stopped container holds no token: nothing runs then. A container that starts without an open (a restart by Docker, `docker start` of the user) has an empty tmpfs until the next open: the credential helper answers nothing, and `gh` cannot read its folder. After each creation of a container, `docker exec -u root` writes the `~/.gitconfig` of the remote user (`HOME_GIT_CONFIG_CONTENT`: `[credential] helper =`, then an `[include]` of `credentials.gitconfig` and `gitconfig`, for Git older than 2.32 and processes without the variables) when it is missing or empty; a file of the image with content and links stay as they are. The copy of the Git configuration of the computer is switched off only by the setting `copyGitConfig` of the container (section 8), not by this file. Then `docker exec -u <remote user> … git --version`: Git older than 2.9 gives the warning `Messages.oldGit`, Git 2.9 to 2.31 a log line, no Git nothing.

## 9. Image check

- **References** (concept 7.7): `image`; each `FROM` of the Dockerfile (with `ARG` values from `build.args` and from `ARG` defaults; without references to earlier stages and without `scratch`); each Feature key that is an OCI reference. Local Features (`./…`), tarball URLs, and references with `@sha256:` are not checked.
- **Normalization:** Docker Hub is `registry-1.docker.io`, official images get the prefix `library/`, and the default tag is `latest`.
- **Request:** `HEAD /v2/<name>/manifests/<tag>` with the `Accept` types for OCI index, Docker manifest list, Docker manifest v2, and OCI manifest. The digest comes from the header `Docker-Content-Digest`.
- **Authentication:** first without credentials. On `401`, read `WWW-Authenticate: Bearer realm=…,service=…,scope=…` and request a token, with Basic credentials if Docker has credentials for this registry (`~/.docker/config.json`: `auths`, `credsStore`, `credHelpers`; credential helpers through `docker-credential-<name> get`). For `ghcr.io`, the fallback is the GitHub session with the scope `read:packages`, requested only when needed (concept 7.7). The `docker pull` of such an image uses the same session: the extension writes it to a temporary Docker config folder (`docker --config`, mode 0700, removed after the pull) and passes the endpoint of the current Docker context as `DOCKER_HOST`. The session is sent only over a local or encrypted connection to the Docker engine (`isProtectedDockerEndpoint`): the default endpoint, `unix://`, `npipe://`, `ssh://`, or `tcp://` with `DOCKER_TLS_VERIFY` (not `0`) and `DOCKER_CERT_PATH` set in the environment of VS Code. The TLS files of a Docker context are not used, because the temporary config folder has no contexts and the context store is internal to Docker: a `tcp://` context counts as unencrypted unless these variables are set. Over any other connection, the session is not sent; the extension downloads the image with a plain `docker pull` (Docker's own credentials, which is enough for a public image), and when that fails too, the error says that the connection to Docker is not encrypted.
- **Time limit:** all requests of one connection run in parallel under one `AbortController` with 5 seconds (NFR-08). If one registry does not answer, the whole update step is skipped (FR-13).
- **Proxy:** use the Node.js `https` module. VS Code applies its proxy settings to this module in the extension host.
- **Build record:** it stores the digests that the check read right before the build. The comparison uses the build record, not the local images (concept 7.7).

## 12. Session Monitor

- Start: `child_process.spawn(process.execPath, [<dist/sessionMonitor.js>, <global storage path>], { detached: true, stdio: "ignore", env: { ...process.env, ELECTRON_RUN_AS_NODE: "1" } })`, then `unref()`.
- The decision logic (rule 1, rule 2, sleep rule of concept 7.9) is a pure function in `src/monitor/rules.ts`, with unit tests for every row of the table "Results for typical situations".
- A process is alive if `process.kill(pid, 0)` does not throw `ESRCH`.
- The Session Monitor never starts Docker. If `docker info` fails, no container runs, and it does nothing.
- Sweep of the storage folder (monitor cleanup, user decision 2026-09-29; `src/core/storage/storageSweep.ts`, `sweepStorage`): `MonitorLoop` runs it at its first tick and then when `STORAGE_SWEEP_INTERVAL_MS` (1 hour) of its run time (`performance.now()`, not the wall clock) passed since the last one, never at every tick; an error is logged as a warning and never fails the tick. It deletes (R6) `pending/<environment id>.json` whose `createdAt` is more than 1 hour from now, both ways (the readers ignore it after `PENDING_MAX_AGE_MS`, 2 minutes); (R7) `disconnect/<environment id>.json` whose `requestedAt` is more than 10 minutes from now (the readers ignore it after `DISCONNECT_REQUEST_MAX_AGE_MS`, 1 minute); a file of either without a valid time, or larger than 64 KB (`MAX_READ_BYTES`, not read), counts by its modification time; (R8) temporary files of the atomic writers, which all name them with `atomicTemporaryPath` (`src/core/storage/atomicJson.ts`): `writeJsonAtomic`, the cut of `monitor.log` (`FileLogger`; review round 8 of PR #63, R8-1), the status file of `SessionCoordinator`, and `computer.id` (`readOrCreateComputerId`; review round 9 of PR #63, A4/B6) (`ATOMIC_TEMPORARY_FILE`, `^\..+\.\d+\.[0-9a-f]{8}\.tmp$`) whose modification time is more than 1 hour from now, in the storage folder, `sessions/`, `pending/`, `operations/`, and `disconnect/`. Only regular files (`lstat`), never a link or what it points to, never a folder, and a folder that is a link is not entered; before the unlink it checks that the file is still the same (inode and modification time), so a file that a window replaced meanwhile stays. Every error is ignored. The log names the number of deleted files. Delete (`EnvironmentService.removeEnvironmentFiles`) also deletes `disconnect/<environment id>.json` (`SessionFiles.removeDisconnectRequest`; the path is `StoragePaths.disconnectFile`).
- Docker Compose (section 15): every container of the project carries `nimblescape.devenv.environment-id`, so the monitor sees all containers of the environment. `devContainerFirst` puts the dev container (the name of the environment, or no label `nimblescape.devenv.compose-service`) first; the Git summary is read only there (none when only other services run); before each further `docker stop` the lock is refreshed (`lockLost` ends the tick). Each call keeps its 30-second limit, so `stop_grace_period` is limited to 20 seconds.
- Protocol version. `MONITOR_PROTOCOL_VERSION` in `src/monitor/lock.ts` is 2 (review round 3 of PR #58, F1: a monitor of version 1 sends heartbeats without the kernel lock of the records). Raise it whenever a monitor of the previous version would decide wrongly with the files of the current windows: a window of the new version then asks a running monitor of an older version to exit and starts its own (see below). No window ever sends a signal to another process. The version is in `monitor.version` (`{ pid, version }`, written atomically with `writeJsonAtomicSync` and `retryTransientSync` right after the monitor takes the lock), not in `monitor.lock`, which holds only the bare process ID, so that the lock stays the same across protocol versions. `readMonitorVersion` reads with `readJsonTolerantSync` (transient errors of Windows are retried) and counts the file only when its `pid` is the one in the lock; a missing file, a file that cannot be read, and the file of another process all give an unknown version, never an older one. `SessionCoordinator.ensureMonitorRunningSync`: a live, fresh lock whose monitor has an unknown version, the current version, or a newer one is left alone (an unknown version, for example while a new monitor has not written its version yet, only means that the window does nothing this time; so no grace time is needed); a known, older one is asked to exit (`retireMonitor`), and the current monitor is started (still limited by `MONITOR_START_GRACE_MS`). Asking: `monitor.exit` names the process ID and the time (`requestMonitorExit`, `{ pid, requestedAt }`; the time is only for diagnostics). At its start the monitor records the exact content of `monitor.exit` (`readMonitorExitText`). It reads `monitor.exit` in every tick (in `refreshLock`) and honours it only when it names its process ID and its content differs from the recorded one (`isMonitorExitRequested`): a leftover request for an earlier process whose ID the new monitor got does not end it, and a clock that was set back neither lets a leftover end it nor blocks a new request (round-3 review of PR #26). It then calls `MonitorLoop.stop()`, which ends the loop after the current step, so a `docker stop` that has started is finished; the window never forces it. A new monitor first removes the request only when it is known to be left over (`removeLeftoverExitRequest`): it is not a valid request, no lock file exists, or the lock names a dead process or a live process other than the named one; a request that names the live lock holder stays whatever its version, and so does any request when the request or the lock cannot be read (transient errors are retried) or the lock has no valid process ID yet. It then waits in `waitForRetiringMonitor` (at most 60 seconds, polled every 250 ms) while the lock holds the process that `monitor.exit` names, then takes the lock, removes the request of the older monitor (before it writes its version, so that no request of a window that has read the new version is removed), and writes its version. A failed write of the version is logged, and the monitor keeps running; windows leave it alone because its version is unknown. If the older one does not end in time, the new one tries the lock once and ends; a window starts another later. Without a request in `monitor.exit`, a new monitor ends at once when another live monitor holds the lock, as before.
- Keep Running When Closed (concept 7.9; user decision 2026-09-26, "go with the proposal for closing"): the registry entry has the optional field `keepRunning` (validated as a boolean in `registry.ts`; a missing field means false). The commands `devEnvironments.keepRunning` and `devEnvironments.stopWhenClosed` (`Controller.setKeepRunning`) write it with `EnvironmentRegistry.updateEnvironment`, under the registry lock, and render the sidebar. The monitor reads the registry at each tick (`MonitorLoop.readSnapshot`) and passes `keepRunning` in `MonitorEnvironment`; `mayStop` in `rules.ts` returns false for it, like for `stopOnClose = false`. So a kept environment gets no waiting time, a running one is dropped (also after the sleep grace, a stale window, and a failed stop that would be tried again), `containerStatesNeeded` leaves it out (no Docker call for it), and the monitor may end while it runs. `MonitorLoop.idleEnvironment` checks the switch again with freshly read files right before the stop. No other code stops a container because no window uses it: the Session Coordinator only writes the window status, `closing`, and the reopen record, and starts the monitor. The user's Stop (`EnvironmentService.stop`) does not look at the switch and leaves it set.
- Close and Keep Running (unit 7, PR 2): the optional registry field `keepRunningOnce` (validated as a boolean in `registry.ts`). `Controller.closeAndKeepRunning` acts on the environment of this window only: it sets the field with `updateEnvironment`; for an environment on an SSH host (only when Docker is set to that host, else `otherDockerHost`) it sends one heartbeat with `keepRunning: true` first (`ControllerDeps.remoteMonitor.sendKeepRunning`, section 16) and, when that fails, removes the field again and shows `ControllerTexts.closeAndKeepRunningUnreachable` (the window stays open); then `ConnectionAdapter.closeWindow` (`workbench.action.closeWindow`). Review round 1 of PR #39 (F1): the command resolves when the close starts, not after the dialog about unsaved files, so the window does not clear the field when it is still open later; a cancelled close leaves the environment kept until the next open or attach, or Stop (the safe side). Accepted leftover (review round 2 of PR #39, L2): an open that starts the container and then fails or is cancelled leaves `keepRunningOnce` set; the next successful open, attach, Stop, or Delete clears it. `MonitorEnvironment.keepRunning` is `keepRunning || keepRunningOnce`, and `idleEnvironment` checks both. The field is removed when a window connects (`finish` of the open pipeline, in the same registry update as `lastUsedAt`; `Controller.openAttachedEnvironment` and the restored window, `clearKeepRunningOnce`), and by `EnvironmentService.stop`; Delete removes the entry. The row shows ` · kept` and the tooltip line `TreeTexts.keptOnce`; its menu keeps Keep Running When Closed. `MONITOR_PROTOCOL_VERSION` stayed 1 with PR 2 (versions reset to 1, user decision 2026-09-27; 2 since review round 3 of PR #58, see *Protocol version*): a Session Monitor of a build before PR 2 that still runs during an update of the extension does not know the field and would stop such an environment after the waiting time (it sends no heartbeats either); it ends when no window is open.
- Tree: the `contextValue` of a row with an environment has `canKeepRunning` or `kept` (`treeModel.contextValue`); the menus use `viewItem =~ /;canKeepRunning(;|$)/` and `/;kept(;|$)/`, so exactly one command shows. `rowStateText` adds ` · kept` in every state (`Running · kept`, `Connected · kept`, `Stopped · kept`, also `No container · kept`, `Files missing · kept`, and `Updating · kept`), as the menu offers **Stop When Closed** in every state; the icon stays the icon of the state, because a tree item has one icon only, and the tooltip has the line `TreeTexts.kept`.

## 14. Repository discovery

- **Scan scope** (concept 7.4, setting `owners`): `DiscoveryService` reads the setting at each refresh (`DiscoveryOptions.scope`); `scope.ts` normalizes it (trimmed, case-insensitive, without duplicates). Empty: `DISCOVERY_QUERY` over `viewer.repositories`, one sequential cursor. Configured: `SCOPE_VIEWER_QUERY` (login, `databaseId` for the account check, organizations; no repositories), then per owner `OWNER_REPOSITORIES_QUERY` (`repositoryOwner(login:)` with `... on Organization` and `... on User` (`ownerAffiliations: [OWNER]`)), or `VIEWER_REPOSITORIES_QUERY` (`affiliations` and `ownerAffiliations` `[OWNER]`) for the login of the account. `repositoryOwner: null` with only NOT_FOUND, SAML, OAuth, or FORBIDDEN errors is a missing owner: hint kind `notFound` (`Messages.organizationNotFound`, the row opens `https://github.com/<login>`), unless a SAML or OAuth hint names the owner. The probe of organizations asks only organizations of the scope. The result stores `scope`; the sidebar shows a stored list, and the result of a refresh, only when its scope equals the setting (`sameScope`), and calls `Sidebar.onScopeChanged` when the setting changes (clears a list of another scope, then a refresh with `again`). `repositoriesToLookUp` skips repositories outside the scope, so no `getRepository` request is about them.
- **List and lookups:** the list queries (`DISCOVERY_QUERY`, `OWNER_REPOSITORIES_QUERY`, `VIEWER_REPOSITORIES_QUERY`) never contain the configuration lookups and read 100 repositories per page (`DISCOVERY_PAGE_SIZE`). `RepositoryCollector.addPage` returns the repositories that need a lookup, and `LookupQueue` starts a batch of `configurationsQuery` (aliases `r<i>`, variables `o<i>`/`n<i>`, `LOOKUP_BATCH_SIZE` 50) as soon as 50 are listed; `finish` starts the rest and waits for all batches. First load: every repository gets a lookup. A refresh with a stored list (`flushEachPage`) also starts the rest of a page at once when a slot for lookups is free (`RequestLimiter.lookupIdle`): the few new and changed repositories come first (last push first), so their batch runs beside the other pages instead of after the last one.
- **Concurrency:** one `RequestLimiter` of 4 (`DISCOVERY_CONCURRENCY`, `concurrency.ts`) per refresh covers every request (account, list pages, lookups, organizations, probes): it starts a request only while fewer than 4 run, whatever their kind, so there are never more than 4. Every request of a refresh goes through `DiscoveryService.request` with its kind (`list`, `lookup`, `other`). While a list is open (`openList`, one per cursor: the viewer list, or each owner of the scope), lookups use at most 3 slots, so the next page never waits for a slow batch (before, the fourth batch took the last slot and the page waited up to one batch time, about 3 seconds, several times per load); list pages and other requests go before waiting batches. More open lists share the free slots; the lookups keep 3, because they are the larger part of the work. When the last list closes, the lookups use all 4. The refresh has one `AbortController`: the first failure of an owner or a batch (`guard`), and any other failure of the refresh (for example an HTTP 403 of a later page of the empty scope), aborts all other requests, and the refresh fails with that failure as a whole (the stored file stays); an abort of the caller gives an AbortError. Every request of the run (also the organizations and the probes) gets the signal of that controller. A failed or aborted refresh rejects only when all its requests settled (`RefreshRun.pending`, also those that wait for a slot), and reports no part after its abort; since the sidebar starts the next refresh only after it, the requests of two refreshes never run at the same time. The 30-second time limit per request and the smaller page on a timeout (100, 50, 25, 12, 10) stay; a lookup batch that times out is split in halves (`allOrAbort`). The GitHubApi 401 hooks cover the list, lookup, and account requests, because all go through `GitHubApi.graphql`.
- **Request count of the first load:** empty scope, n repositories: ⌈n/100⌉ list requests and ⌈n/50⌉ lookup requests (664 repositories: 7 + 14 = 21 requests), plus further pages of organizations (more than 100) and probes. Configured scope: 1 account request, ⌈n_owner/100⌉ list requests per owner, and ⌈n/50⌉ lookup requests. The lookups are the larger part: with a batch time T and 4 at the same time, the first load needs at least one list page plus ⌈n/50⌉ · T / 4 (666 repositories: 14 batches; T = 3 seconds: about 13 seconds; T = 6 seconds: about 25 seconds). The empty scope also needs its ⌈n/100⌉ pages one after another (7 pages of 3 seconds: about 21 seconds, plus the last batch). A refresh with few changes needs about the time of its list pages (7 pages one after another for the empty scope).
- **Incremental detection:** with a stored list (`loadStored`, also of another scope), `needsConfigurationLookup` (new repository, other `pushedAt`, or other default branch) selects the repositories for the lookups; unchanged repositories keep their stored `configPaths`. A repository that an error of its list page points into, or whose lookup GitHub did not answer, is not kept in `withoutConfiguration` and is read again at the next refresh; one that has a configuration is listed in `uncertain`, which `storedDetections` skips, so it is read again too. Each refresh logs "loaded in N seconds with M requests", "configurations of N repositories read with M requests", and one line with the requests of each kind (list, lookup, other) with their average time, the most requests that ran at the same time, and the time until the first repository with a configuration was known (the first rows of the progressive display). The average times show which estimate applies (list page about 0.5 to 1 second, batch about 3 seconds, not measured yet).
- **Progressive display:** `DiscoveryService.onPartialResult` gets the repositories with a configuration found so far after each list page and each lookup batch (account ID, scope); on the first load they join as their batches finish. extension.ts passes them to `Sidebar.onPartialResult`, which shows them only during a refresh that started while the view had no list of the account, and only for this account and the current scope; the complete result replaces them. The sidebar shows the complete result as soon as `refresh` returns; the single lookups of environment repositories that the list lacks (`lookUpUnlisted`, `getRepository`) follow, at most 4 at the same time (`mapLimit`; the refresh has ended, and refreshes run one at a time), and a second render adds their `not on GitHub` labels. At start, the stored list is shown before any request (`initialize`); the refresh runs in the background.
- **Refreshes one at a time:** `Sidebar.refreshDiscovery` runs one refresh at a time (`CoalescingTask`). `onSessionChanged` (VS Code reports a change of the GitHub sessions, also for a session of other scopes, for example `read:packages`, or of another extension) starts one more refresh after a running one only when the account changed, the user was not signed in, or the running refresh does not use the token of the current session (`refreshToken`); otherwise it reuses the running refresh, whose list would be the same, so that Refresh does not wait for two refreshes.
- **Select Organizations…** (`ownerSelector.ts`, rules in `ownerChoices.ts`): multi-select Quick Pick with the account ("your account"), its organizations in alphabetical order (from the list of the view when it belongs to the account, else `DiscoveryService.viewerOrganizations`, which lists no repository), and the owners of the setting in neither list ("from your settings"); the setting is pre-selected. OK writes `owners` with `ConfigurationTarget.Global`; an empty selection writes `[]`. Not signed in: `Messages.signInRequired` with **Sign in**.

## 16. Remote Docker host

Unit 7 (user decisions 2026-09-27; concept 7.16). The remote host is the current Docker context; nothing of the extension points Docker anywhere else.

- **Modules.** `src/core/docker/dockerHost.ts` (pure): `classifyDockerEndpoint` (local: empty, `unix://`, `npipe://`, `tcp://` to the loopback; remote: `ssh://`, host = the part after `ssh://`; everything else `unsupported`), `parseContextInspect`, `parseSshAddress` and `isUsableSshAlias` (the checks of an address and an alias: no spaces, no leading `-`, no path, query, or shell character, IPv6 in brackets), `sshCommandArgs` (`-o BatchMode=yes -o ConnectTimeout=… -T [-p] [-l] -- <host> <command>`), `sshCommandLine` (the command line of the host key advice: `ssh [-p <port>] [<user>@]<host>`, IPv6 without brackets, `ssh <alias>` for an alias), `remoteContextName`/`isOwnRemoteContext` (the context per host, `devenv-remote-<first 8 hex digits of sha256(host)>`), `dockerHostProblem` (the plain reason of an error of `docker info` or `ssh`), `environmentsOfHost`/`isOnDockerHost` (the registry filter), `rootlessSocketPath`, `isRootlessEngine`. `src/core/sshConfig.ts` (pure, with a small file interface): the concrete `Host` entries of `~/.ssh/config` (`%USERPROFILE%\.ssh\config` on Windows), `Include` followed (relative to `~/.ssh`, `~`, globs with `*` and `?`, at most 16 levels, at most 256 files), patterns and `Match` blocks skipped, the first `HostName`, `User`, `Port` of each alias. `src/core/docker/dockerTargets.ts`: `DockerTargets` reads the current target (`docker context inspect --format '{{json .}}'`, or `DOCKER_HOST` of VS Code) and runs operations with it (`withOperation`, an `AsyncLocalStorage`). `src/core/docker/remoteDocker.ts`: the SSH check (`checkSshLogin`, `SshLoginCache`), the test of a host (the SSH check, then `docker -H ssh://<host> info --format …`), `ensureDockerHostReachable` (the step "Docker start" of a remote host: the SSH check, then `docker info`), `startDockerFor` (local → `ensureDockerRunning` as before; remote → the check; unsupported → refused), the context commands (`useRemoteContext`, `chooseLocalContext`), the rootless socket. `src/core/storage/remoteDockerState.ts`: `remote-docker.json` in the global storage folder (the previous context; the rootless socket per host). `src/vscode/remoteDockerCommands.ts`: the two commands and the switch back of a restored window.
- **A context per host (review C1).** "Use a Remote Docker Host…" uses the context `remoteContextName(host)`: created with `host=ssh://<host>` when missing (`docker context create`), never updated afterwards, then `docker context use`. One context for all hosts, updated at each switch, moved the running operations of other windows (which pin the context by name, see below) to the new host mid-way. One of our names that points elsewhere is refused ("remove it with `docker context rm`"). The contexts of earlier hosts stay (a pinned call on a removed one fails cleanly); `isOwnRemoteContext` (`devenv-remote-<8 hex digits>`) replaces every comparison with one name (the remembered context, the switch back).
- **The switch back (review C2).** "Use the Local Docker" uses the remembered context only when `docker context inspect <name>` classifies as local (`classifyDockerEndpoint`), else `default`. The message follows where Docker points afterwards: "Docker now uses the local Docker (context …)" only when it does; otherwise a warning names the context and its endpoint.
- **Per operation, not for ever.** Each command, the flows of the window roles, and each `operation` of the controller run in `DockerTargets.withOperation`: the context is read once at the start, and every Docker call of the operation (`ContainerAdapter.run` without an explicit `env`) gets `DOCKER_CONTEXT=<that context>`, so a switch in the middle does not move the rest of the operation to another engine. Outside of an operation (the sidebar, `inspectStates`), each read is fresh. `DOCKER_HOST` is never set by the extension (the only exception is unchanged: the credentialed pull of section 9 passes the endpoint of the context of the operation as `DOCKER_HOST` to its own `docker --config` call); when `DOCKER_HOST` is set for VS Code it decides the endpoint, and the calls get no `DOCKER_CONTEXT`.
- **No questions.** The Docker CLI starts `ssh` for an `ssh://` endpoint in a new session (`Setsid`, docker/cli `connhelper/commandconn/session_unix.go`) with `-o ConnectTimeout=30 -T` (`connhelper.go`), and has no documented variable for more ssh options; so the test uses the Docker CLI path with `SSH_ASKPASS_REQUIRE=never` (ssh(1), OpenSSH 8.4 and later) and a time limit of 45 s: without a terminal and without an askpass program, ssh cannot ask for a password, a passphrase, or a host key, and fails at once (checked here with OpenSSH 9.2 and Docker CLI 29.3: unknown host key, wrong key, closed port, Docker missing each fail within a second). Our own `ssh` calls add `BatchMode=yes`. The Docker calls of the operations get no extra variable; the time limits of the adapter apply.
- **The SSH check (review C3).** On Windows the Docker CLI starts `ssh.exe` without `Setsid`, and the OpenSSH client of Windows asks on the hidden console (host key, password) until the time limit ("does not answer"). So, on every platform, before the test of a host and before each operation on a remote host (`ensureDockerHostReachable`, the step "Docker start"), our own `ssh -o BatchMode=yes -o ConnectTimeout=15 -T [-p] [-l] -- <host> true` runs (`checkSshLogin`, time limit 30 s): it fails at once instead of asking, and its error gives the reason (`dockerHostProblem`: host key, login, unreachable, closed before the login); then no Docker call is made. It is one connection instead of the several of the Docker CLI, which also lowers the risk of a lock-out by `PerSourcePenalties`. A success counts for 60 s per host (`SshLoginCache`, one per extension host), a failure never; the test before a switch always connects. A host that is no usable alias or address (a context of the user with a path) is left to the Docker CLI. `NodeProcessRunner` ends the whole process tree on Windows at a time limit, an abort, or too much output (`taskkill /T /F /PID <pid>` from `%SystemRoot%\System32`, arguments without a shell; `windowsTreeKillCommand`), so an `ssh.exe` that `docker.exe` started does not survive; elsewhere `child.kill()` as before.
- **Unsupported endpoints (review D2).** One check in `EnvironmentService` (`dockerTarget`, from `DockerTargets.current` of the operation): every operation (open, stop, delete, …) refuses an endpoint that is neither local nor SSH with `dockerEndpointUnsupported` before Docker is asked; the reads (`reconcileFromVolumes`, `inspectStates`, `currentBranch`, the volumes and service data of Delete) do nothing on it (0, an empty map, `undefined`, `[]`), and the refusal is shown once per endpoint (`ui.warn`). So no environment ever records such a `dockerHost`. The controller and the window roles leave the check of a running Docker to `reconcileFromVolumes` (no `docker info` before the check of the target).
- **Registry.** `Environment.dockerHost` (missing = local, `REGISTRY_VERSION` stays 1). `openFirst` and `reconcileFromVolumes` record the host of the operation; `findForAccount(repository, account, host)` and the check of `add` use the key (repository, account, host); `inspectStates` and the sidebar (`Sidebar.availableEnvironments`, the render) filter by the current host; the service refuses every operation on an environment of another host with `otherDockerHost` before Docker is asked; the controller skips pending operations and the reopen record of another host, and removes no token there. The computations over all entries that only protect data (foreign volumes of the host access policy, volumes kept at Delete, base images still in use) keep looking at every host: that is the conservative side (a volume or image name of another host is kept or refused, never removed or allowed).
- **Mismatch of a restored window.** `Controller.openAttachedWindow` compares the host of the environment with the current context before the open pipeline (`onWindowHost`). VS Code activates the extension in the restored window before it resolves the `attached-container` authority (V-2), so a switch there reaches the Dev Containers extension; without the switch the window closes its remote connection.
- **Workspace helper.** `HelperDeps.engine` gives the key of the engine, the socket (remote: recorded rootless socket or `/var/run/docker.sock`), and the local endpoint. The cached helper image is not reused for another engine, and a remote engine has its own state file (`helper-remote-<hash>.json`).
- **Messages.** `dockerHostUnreachable` (Show details, Try again; never Start Docker or Install Docker…), `dockerEndpointUnsupported`, `otherDockerHost` (warnings).
- **Session Monitor.** Each tick reads the current target once (`MonitorDockerClient.withCurrentTarget`: `docker context inspect`, which reads only local files) and pins its Docker calls to that context (`DOCKER_CONTEXT`). It acts only on the registry entries whose `dockerHost` equals the current host (the local Docker: none); on an endpoint that is neither local nor SSH it acts on none and makes no Docker call (logged once). Otherwise its rules are unchanged, so it stops the containers of the remote host while the computer is online and Docker is set to that host. For the time when the computer is offline, asleep, or switched to another host, see the next item.

## 17. Helper channel

The agreed plan for the next steps is in [plan-remote-worker.md](plan-remote-worker.md). User requests 2026-09-28 (the remote host is slow: every Docker call opens its own SSH connection, about 1.6 s each). Step 1 of 4: the channel itself. It has no callers yet; the refreshes and branch reads (step 2), the steps of Start (step 3), and the heartbeats of the Session Monitor (step 4) move to it in the next pull requests. Until then nothing changes for the user.

- **What it is.** One `docker run -i --rm` of the workspace helper image per window and remote Docker host that stays open (`HelperChannels`, `src/core/helperChannel/helperChannels.ts`): opened at the first use, closed after 10 minutes without an operation (`CHANNEL_IDLE_CLOSE_MS`), opened again after it was lost. The extension sends *operations*; the script in the container runs all steps of an operation there, next to the engine, and answers with progress, log lines, output, and one result. So an operation costs one message instead of an SSH connection per Docker call. Only for remote hosts: the local Docker needs no channel.
- **Container.** `channelRunArgs`: `docker run --rm -i --pull never --name devenv-channel-<12 hex digits> --label nimblescape.devenv.helper-run=true --label nimblescape.devenv.helper-channel=<protocol>-<12 hex digits of sha256(script)> --network none --log-driver none --cap-drop ALL --security-opt no-new-privileges --mount type=bind,source=<socket>,target=/var/run/docker.sock <helper tag> node -e <loader>`, with the Docker context of the target (`runWithDockerTarget`, `ContainerAdapter.start`). The socket is the one of the workspace helper for that engine (rootless aware). No restart policy, no `-d`: it lives only as long as its connection. `--log-driver none` (review round 2, B3): the engine keeps no log of its commands and output, whatever its log driver (journald, syslog, …). Never a pull: without the helper image on the host the start fails and the callers take the way without the channel.
- **Start.** The loader (`CHANNEL_LOADER`, a short `node -e` program) reads the first line of its input, the script as a JSON string, writes it to `/opt/devenv/channel.js` in the container's own file system, and calls its `startChannel` with the rest of the input. So the script (`dist/helperChannel.js`, esbuild entry `src/helperChannel/main.ts`, minified; Node.js built-ins and small modules of `src/core`) has no limit of the command line of Windows. The loader exits when the input ends before the script or no script comes within 60 s. The extension checks the length of the script as its JSON line, as the loader reads it (8 M characters; review round 1, P6). Then `hello` (the protocol version; the answer names the Node.js version and the operations; another version closes the channel), then the operation `probe` (`docker version` in the container; a failure closes the channel: "does not reach Docker"), then in the background the operation `sweep` (review round 4, M1): `docker container prune -f --filter label=nimblescape.devenv.helper-channel --filter until=10m` removes the channel containers that an earlier open created but never started (a connection that broke between the create and the start of `docker run -i --rm`: `--rm` acts only after an exit, so such a container would stay); prune removes only stopped containers, and the age keeps it away from an open that runs now.
- **Messages** (`src/core/helperChannel/protocol.ts`, one JSON object per line, both sides check strictly). From the extension: `hello`, `ping`, `op` (`id`, `op`, `params`, optional `secret`, optional `timeoutMs`), `cancel`. From the script: `hello`, `pong`, `progress` (a step began), `log` (a line of the log, info or warn), `out` (output of a tool, stdout or stderr, pieces of at most 16 K characters), `result` (a value, or a failure with a code, and whether it was cancelled or timed out). Lines are limited (4 MB), a longer one ends the channel.
- **Operations** (`src/helperChannel/operations.ts`). Step 1: `docker` (one Docker call without a shell: its arguments, an optional input or secret input, and an optional cleanup label; its output comes back as `out`, its value is the exit code; `HelperChannel.docker` returns the `RunResult` of `ProcessRunner.run`, with the same limit of the standard output and the end of the standard error output) and `probe`. An operation gets an `OperationContext`: its signal, its secret, `progress`, `log`, `output`, and `docker` (every call ends when the operation is cancelled; the script keeps at most 64 M characters of its standard output, beyond the call is ended and fails, and the last 1 M characters of its error output, review round 1, S5).
- **Output that the connection cannot carry fast enough** (review round 2, A2). `process.stdout.write` to a pipe does not wait, so while more than 1 M characters of answers wait to be written, the script pauses the reading of the output of every call (the pipe fills, the Docker CLI waits) until they are written. A log or progress text is cut to 16 K characters, and a result that would be longer than the extension reads fails (`tooLarge`) instead of ending the channel there (review round 2, C1).
- **What the channel does not carry** (review round 1, P2, S6). A request whose line would be longer than the script reads (4 M characters; the extension sends at most 256 KiB, review round 5, F3), a Docker call beyond the limits of the operation (1000 arguments of at most 64 K characters, an input of at most 1 M characters), a secret shorter than 4 characters (it could not be masked), and a time limit that is no whole number of milliseconds from 1 to 24 h (review round 2, A5; a missing `params` travels as null) are not sent: `HelperChannelError('unsendable')`, and `HelperChannels.docker` returns undefined, so the caller takes the way without the channel, as for a closed one.
- **The log** (user requests 2026-09-28: "the output of these operations piped to our console, as detailed as the helper writes the logs and records the results"). Each Docker call of an operation is a line `[<host>] <op>#<id>: $ docker …` and a line with its exit code and duration (and the last line of its error output when it failed); `progress` and `log` messages are lines of the log; the output of a tool that a step streams goes to the log as it comes; an operation of steps gets a line at its start and one with its outcome and duration. The `docker` operation logs its call, but its output is its result, not a log.
- **The secret** (the GitHub token, for the later steps). `HelperChannel.docker` takes it as `secretInput` (review round 1, S4), never as `input`. It travels only in the `secret` field of its operation, on the input of `docker run` (so over the SSH connection of the Docker CLI); in the script it is only ever the input of a process, never an argument, a variable, or a log. The script masks it in every progress, log, and output message (`StreamRedactor`, also when a chunk splits it; each streamed call has redactors of its own, review round 2, B1; the error output that a call keeps is masked before it is cut to its last 1 M characters and before its last line is cut to 500 characters, review rounds 1 and 2, S2 and B2). The results of the operations of step 1 hold no text of a tool that was given the secret. The extension never logs the parameters or the secret of an operation.
- **Cancel and time limits.** A cancelled operation (the signal of the caller, its time limit in the script, or the end of the channel) aborts its signal; its Docker calls get SIGTERM, then SIGKILL after 5 s; then the containers of its cleanup label are removed; then its result is sent. Review round 1 (S1): a call that starts a container puts `--label nimblescape.devenv.channel-step=<value>` on it (`channelStepLabel`) and names the value as its cleanup; the value is new for each call (`newCleanupLabel`: 24 random hex digits; the channel refuses any other form; review round 2, B4), because the containers of a cancelled or lost operation can still be removed later (up to 35 s after a cancel, and after a lost connection when the script ends by its silence), so a value must never be used again, also not by a retry. The cleanup runs `docker ps -aq --no-trunc --filter label=nimblescape.devenv.channel-step=<value>` and `docker rm -f` of exactly those IDs, and once more 2 s later for a create that the engine still ran when the call was ended (review round 2, C3; all within 30 s). A cancel that crossed the result of an operation that ended by itself still removes its containers within 60 s (review round 2, A1): the caller took it as cancelled; the exit of the script waits for that cleanup too (review round 3, K1). Never a name: a container with the same name that the operation did not start, or one whose ID begins with the name, is never removed. On its signal the extension sends the cancel and rejects with an AbortError when the script confirmed it (review round 4, M2): by the result of the operation, or by `cancelled` for one that had ended there already (its containers are removed then); when the channel is lost before the confirmation, the operation rejects as `lost` (its outcome is not known). It gives up on a result that does not come 50 s after the time limit (review round 1, P4: longer than the kill grace and the cleanup of the script). At most 8 operations of a channel run at the same time; a place that ends goes straight to the next waiting operation, and a waiting operation whose signal aborted is never sent (review round 1, L1, L5).
- **It ends by itself** (user request 2026-09-28: nothing on the host can clean up after it). Four independent ways, each enough alone: (1) the end of its input: the connection closed or `docker run` ended (`docker run -i` passes the end of its connection on as the end of the input); (2) no message for 60 s (`CHANNEL_SILENCE_EXIT_MS`) while the connection hangs without an end, for example after the computer went to sleep; the extension sends a ping every 15 s; (3) no operation for 15 minutes and none running (`CHANNEL_SERVER_IDLE_EXIT_MS`, a backstop behind the idle close of the extension); (4) `--rm` removes the container when the script ended, and tini passes signals on. Before it exits it cancels every operation (above); a hard deadline (40 s) ends it even when a call does not end. An answer that cannot be written (EPIPE), a line that is too long, SIGTERM, SIGINT, and SIGHUP end it the same way; an uncaught error too (review round 1, P5), and a timer ends the process 45 s later in any case. The extension takes the channel as lost when no answer came for 30 s (`CHANNEL_PONG_TIMEOUT_MS`, checked at each ping: at most 45 s after the last answer, before the script's 60 s; review round 1, P3), stops `docker run` (SIGTERM, then SIGKILL after 5 s: `docker run -i` passes SIGTERM on to its container and would wait for ever over a hung connection; review round 1, L2; before the SIGKILL, `pkill -KILL -P <pid>` ends the programs that it started, above all the `ssh` that the Docker CLI starts in a session of its own, which would stay on macOS; review round 2, A3), and rejects what ran with `HelperChannelError('lost')` (the outcome is not known); an operation that was not sent, also one whose write failed (review round 1, L3), gets `HelperChannelError('closed')`, and the callers take the way without the channel. The idle close counts from the end of the last operation (review round 1, P10).
- **The end of the window** (review round 4, M3). When the window closes (`HelperChannels.dispose`), each channel is closed at once (`closeNow`): `docker run` and the programs that it started (its `ssh`) get SIGKILL now, synchronously (`pkill -KILL -P <pid>`, on Windows `taskkill /T /F`), because the extension host may end right after and none of its timers runs then; one `exit` handler of the extension host does the same for every program of `NodeProcessRunner.start` that still runs. The container on the host then ends by the end of its input, at the latest by its silence. A crash of the extension host (SIGKILL) leaves them until TCP gives up.
- **Waiting for a channel** (review round 2, A4). A call waits for a channel that is still being opened at most 5 s (`CHANNEL_OPEN_WAIT_MS`) or its own time limit; then it takes the way without the channel, and the opening goes on for the next calls. When its signal aborts during the wait, it rejects with an AbortError at once, as any call with that signal does (review round 3, K5).
- **Review round 5.** (F1) The channels are kept per Docker context and endpoint (`keyOf`), not per context alone: a context of the user that was pointed to another host under the same name (`docker context update`) kept the channel to the old engine, and calls through it went there while the calls without it went to the new one. The channel of the old endpoint gets no new operation and closes after 10 minutes without use. Not seen: an SSH alias of `~/.ssh/config` that was pointed to another machine (the endpoint stays the same). (F2) An operation waits for a free place at most 5 s (`CHANNEL_SLOT_WAIT_MS`) or its own time limit, whichever is shorter; then it is `unsendable` and takes the way without the channel (before, a call with a short time limit waited for as long as the 8 running operations ran). (F3) The pings go behind a request in the same stream, so a long request on a slow link looked like a lost connection: the extension now sends at most 256 KiB of UTF-8 per request (`MAX_CHANNEL_REQUEST_BYTES`, about 70 kbit/s for the 30 s of the pong limit; a longer one is `unsendable`), and the script counts any text that arrives as a sign of life for its silence, also in the middle of a request (a hung connection sends none).
- **Review round 6.** (R6-2) The waits added up: the wait for the channel (up to 5 s or the time limit), then the wait for a place (the same again), then the full time limit in the script, so a call could take its limit plus 10 s (three times a short limit). - **Failures.** A channel that cannot be opened (no helper image on the host, no Docker in reach) is logged once; the callers take the way without it; the next attempt for that host waits 5 minutes (`CHANNEL_RETRY_AFTER_FAILURE_MS`).
