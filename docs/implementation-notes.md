# Implementation Notes — Version 1

These notes add the technical decisions that the concept ([vscode-dev-environments.md](vscode-dev-environments.md)) leaves open. The concept is the source of the requirements. If a note and the concept differ, the concept wins, and the note must be corrected.

## 1. Scope

- Phase 1 and phase 2 of the concept (section 12), including Docker Compose configurations (`dockerComposeFile` and `service`, section 15).
- Not in scope: phase 3 (profile template, backup of unpushed work, `build.cacheFrom`, Podman).
- The verification tasks V-1 to V-12 are not done yet. Code that depends on an unverified assumption has a comment `// Assumption (V-n): …`, so that a later check can find it.

## 2. Technology

| Item | Decision |
|---|---|
| Language | TypeScript, `strict: true`, target ES2022. The type check resolves imports like the bundler (`module: preserve`, `moduleResolution: bundler`); esbuild writes CommonJS bundles for Node.js 20. |
| Bundler | esbuild. Two bundles: `dist/extension.js` (external: `vscode`) and `dist/sessionMonitor.js` (plain Node.js, no `vscode`). |
| Runtime dependencies | None. Use the Node.js modules `https`, `child_process`, `fs`, `crypto`, `os`, `path`. The Dev Container CLI is not a dependency of the extension: it is installed in the workspace helper image. `package.json` lists `@devcontainers/cli` as an exact devDependency only to pin this version: the build passes it to the code as `__DEVCONTAINER_CLI_VERSION__`, and the package is neither bundled nor shipped. So Dependabot proposes each new CLI version in a pull request of its own, and the contract tests (the options and the lifecycle error text, against the package) and `npm run test:docker` check it before a release. |
| Tests | vitest. Unit tests run without VS Code and without Docker. `npm run test:docker` (folder `test/docker/`, not part of `npm test`) runs the core modules against the real Docker engine: the clone of a public repository, the open pipeline on a seeded environment (first open, update, no connection, a removed container, a container of an older version, delete), the container-only Git (variables, label, the settings of the Dev Containers extension in the label, token file, Git configuration, `~/.gitconfig`, credential helper, the helpers of `credentials.gitconfig`, a removed token file, and Git 2.30 of an Alpine 3.13 image), the host access policy (refused configurations, among them a label of Dev Environments, a variable of container-only Git, and a volume of a Docker Compose project; ports on 127.0.0.1; a service on the computer reached through `host.docker.internal`; `--platform`, `--cap-drop ALL`, `--rm`, and `-it`; two GitHub accounts with one repository: two volumes and containers with the identity of each owner, both restored after a lost registry), and the refresh and cleanup of the helper image. It uses a Docker configuration without credentials and credential helpers (its only `auths` entry, for a registry that does not exist, turns off the default credential helper of the platform), so no credentials of the user, and fails when it leaves or removes a Docker object other than the helper image and pulled base images. |
| VS Code API | `engines.vscode` `^1.90.0`, `@types/vscode` of the same version |
| Package | `@vscode/vsce` creates the VSIX file (decision D-6: private VSIX) |

**Layering rule.** Code in `src/core/` never imports `vscode`. It receives everything it needs through interfaces (process runner, file system paths, logger, clock). Code in `src/vscode/` adapts VS Code to these interfaces. The Session Monitor bundle uses only `src/core/` and `src/monitor/`. So most of the logic can be tested without VS Code.

## 4. Local storage

All files are in the global storage folder of the extension (`context.globalStorageUri.fsPath`), on the local computer.

| File | Content | Writers |
|---|---|---|
| `registry.json` | Environment Registry (concept 7.5) | windows, Session Monitor |
| `repositories-<account ID>.json` | Stored result of the discovery of one GitHub account (concept 6.2, 7.4); the account ID is the numeric GitHub user ID of the session. It also records the scan scope it was built with (`scope`, lower-case logins, sorted; missing in lists of older versions: all repositories) and the repositories without configuration with their `pushedAt` and default branch (`withoutConfiguration`, for the incremental detection). The shared `repositories.json` of the first version is removed at activation. | windows |
| `sessions/<window-id>.json` | Window status file (concept 7.9) | one window |
| `pending/<environment-id>.json` | Pending connection file (concept 7.9) | windows |
| `operations/<environment-id>.json` | Pending operation, for example `rebuild` (concept 7.14) | windows |
| `disconnect/<environment-id>.json` | Request from a window to the window that is connected to the environment: close the connection first, then hand off the stop, rebuild, or delete (concept 6.2, 7.14). Dropped after 60 seconds. | windows |
| `reopen.json` | Reopen record (concept 7.10) | windows |
| `monitor.json` | Settings for the Session Monitor: waiting time, `stopOnClose` | windows |
| `monitor.lock` | Process ID of the running Session Monitor | Session Monitor |
| `monitor.log` | Log of the Session Monitor (the process has no output channel), at most about 1 MB | Session Monitor |
| `helper.json` | State of the workspace helper images (section 7): per helper tag the base image and its digest at the build, `builtAt`, `checkedAt`, `lastUsedAt`, a rebuild that a check asked for, and the marks of the cleanup for foreign and removed tags; the time of the last cleanup | windows |

Rules:
- Every JSON write is atomic: write a temporary file in the same folder, then rename it.
- Read-modify-write of `registry.json` happens under a lock (a lock folder created with `mkdir`, removed after the write; a lock older than 10 seconds counts as stale).
- `deactivate()` uses only synchronous file writes.
- In the workspace volume (not in the global storage), the folder `/workspaces/.devenv+` holds the configuration of the container: `gitconfig`, `credentials.gitconfig`, `github-token`, `docker/`, and `gh/` (`GH_CONFIG_DIR`; the extension writes only `gh/hosts.yml`) (concept section 9, section 7 "Container-only Git" below). A `gnupg/` of an earlier version stays unused.

## 5. Names and labels

- Environment ID: `crypto.randomUUID()`. Short ID: the first 8 characters. An ID is not used when an entry of the registry has its short ID or its volume exists (at most 5 tries), because the names end in the short ID: two environments of one repository (of two accounts) get different names.
- Volume and container name: `devenv-<owner>-<repository>-<short id>`, lower case, only `[a-z0-9_.-]`, at most 63 characters.
- Environment image: `devenv-<short id>:<build number>`.
- Labels on the volume: `devenv.environment-id`, `devenv.repository`, and `devenv.owner-id` (the GitHub user ID of the owner account; `reconcileFromVolumes` restores the owner from it, and its login at the next open). Additional volumes: before `up` creates a container, the pipeline creates each named volume that it mounts (configuration `mounts`, the `runArgs` that Docker gets, and the image metadata; `mountedVolumeNames`) and that does not exist yet, with the same three labels and `devenv.volume=additional` (`LABEL_VOLUME`, `VOLUME_KIND_ADDITIONAL`, `additionalVolumeLabels`). Only these labels make a volume an environment's own (`isOwnVolume`: `devenv.environment-id` is its ID, and `devenv.owner-id` is its owner when both are set): the pipeline records such volumes as additional volumes, and Delete removes only them. It records also the existing additional volumes of other environments of the same owner that the environment mounts (`recordedVolumes`, `isSameOwnerAdditionalVolume`), only to protect them (host access policy below). After a lost registry, `reconcileFromVolumes` restores these own volumes (`devenv.volume` with the environment's labels), the additional volumes of other environments of the same owner that the surviving container mounts (`isSameOwnerAdditionalVolume`), and, to protect them (`protectedMountedVolumes`), the named volumes without devenv labels that the surviving container of the environment mounts (`listEnvironmentContainers`, label `devenv.environment-id`), for example the volumes that a version before the labels recorded: not the workspace volume, not a name that `foreignVolumeName` gives to something else, not an existing volume with labels of another program or environment (`volumeLabelOwner`), and not a volume that does not exist. As recorded volumes, the policy refuses them to the environments of other accounts; Delete keeps them (`removableVolumes`: not the environment's own) and records them in `keptVolumes` with the owner. A name with `${devcontainerId}` is not created: Dev Container CLI 0.89.0 substitutes `${devcontainerId}` in `read-configuration` only when a container with the id labels exists (`dA&&(q=yn(q,EA=>tg(ht(nA),EA)))` in `devContainersSpecCLI.js`), so before the first `up` the name is unknown; Docker creates that volume at `up` without labels, and it is never the environment's (Delete keeps it). The container gets `devenv.environment-id` through the CLI option `--id-label`, and `devenv.container-version=4` through `runArgs` (2: container-only Git; 3: the settings of the Dev Containers extension for the container, which reach it only through the label of a new container, and only the documented variables of Git and Docker; 4: `GH_CONFIG_DIR`, the GitHub CLI signed in as the owner account (containers are created again once)). A label of `runArgs` whose key starts with `devenv.` or `devcontainer.` is refused (section 7, host access policy), except these two labels of the override configuration with their exact values (`CONTAINER_VERSION_LABEL`, `CONTAINER_CONFIG_UNKNOWN_LABEL`). A container without this label, or with an older value, is created again from its environment image (`up --remove-existing-container`, no build, the volume is kept), and the progress shows that the files outside the volume are removed; without the workspace helper, such a container is not started with `docker start`. A container created while the configuration could not be read gets `devenv.container-config=unknown` (and no `runArgs` or `appPort` of the repository); it is created again in the same way at the first open that can read the configuration (`containerIsCurrent`).
- Registry entry: `owner: { id, login }`. An entry without it (of the first version, or restored from a volume without `devenv.owner-id`) is hidden until a claim (`EnvironmentClaims`, one at a time, the owner written under the registry lock only while the entry has none). A claim asks `DiscoveryService.getRepository` in its quiet mode (no repository name in the log or in an error) with the token of the signed-in account, token and account from one session. Mode `auto` (after each successful refresh of the repository list, and for a restored window) assigns only when the repository is private, its owner is the login of the account, and `viewerPermission` is ADMIN, MAINTAIN, or WRITE (`isUnambiguousClaim`). Mode `interactive` (a command of the user, and an open of the environment service) also asks the modal question `Messages.assignOlderEnvironment` for any other repository that GitHub returns; a "Not now" is remembered per account and entry for the window. For a command that names the entry, a failed question, or an entry that stays without owner, gives `Messages.olderEnvironmentNotAssigned` (code `environmentUnassigned`), never the text of another account; for an open of a repository see `EnvironmentService.open` below. The rule `isAvailableTo` (src/core/ownership.ts) applies to the sidebar, the pickers, all commands, the reopen, restored windows, pending operations, and disconnect requests; the environment service checks it again in each operation, and the controller once more right before it connects the window. One environment per repository and account (D-3): the registry refuses a second entry with the same repository (case-insensitive) and owner (entries without owner count as one owner), `findForAccount(repository, accountId)` gives the environment of the signed-in account, and `findUnowned(repository)` an entry of an older version. A claim (`canClaim`) never gives an account a second environment of a repository; it is checked before GitHub or the user is asked and again under the registry lock. `EnvironmentService.open` reads the session first and uses its account: its own environment, else an older entry that it claims (declined or no access: a new environment; GitHub could not be asked: `environmentUnassigned`), else a new environment. The controller looks up only the environment of the signed-in account for a repository (for Start, Search, the switcher, Switch branch…, and Select configuration…, the account of a session with a working token: while GitHub rejects the token, the new sign-in comes before the environment is chosen, so an account change at that sign-in chooses the environment of the new account, also for Try again of a Start; Stop and Delete ask for no new sign-in); A restored window checks the account again right after it takes its environment, and after a failed open pipeline (an account change during its claim or its checks, which found no environment of the window yet), and leaves an environment that the account may not use, with its token file. `otherAccount` applies only to an environment that a command names by its ID (a row or the status bar item from before an account change, a restored window, an account change during an open, and an account change during Switch branch…: the environment whose branch it switched, also after a repository pick). Try again of a first open of Switch branch… or Select configuration… runs the step of the command after its pick again, with the same branch or configuration, for the account signed in then: it asks about an entry of an older version like the command (`withOlderEnvironment`), and an environment that the account has then gets the branch switched or is rebuilt with the configuration (nothing more when it has that configuration already), as the command does. `reconcileFromVolumes` restores one environment per repository and owner (label `devenv.owner-id`), and at most one per repository for volumes without that label, and only volumes whose name is `resourceName(repository, id)` of their labels; after each `up` (also a failed or cancelled one) and at each open of a running container, its mounted named volumes whose labels make them its own (`isOwnVolume`) join the additional volumes too (a failed first open removes the environment, and its additional volumes stay with its account, a known limit); the additional volumes of a restored entry are the volumes with `devenv.volume` whose labels make them its own. Every other volume (anonymous volumes, volumes of other programs or environments, `${devcontainerId}` volumes, and volumes that a version before the labels created) is never recorded, restored, or removed. A command whose sign-in for a claim the user cancels ends with `signInRequired`; when the session of the claim belongs to another account (for example another account signed in at that sign-in), nothing is assigned and the command ends with `ControllerTexts.accountChangedDuringClaim` (code `environmentUnassigned`, with Try again, which runs the command again). A claim needs a working token: a command reads the session interactively, so that it asks for a new sign-in while GitHub rejects the token; Switch branch… and Select configuration… ask also about an entry that the user declined before (`askAgain`) and tell the open not to ask again (`olderEnvironmentAsked`). When the claim of an older entry is declined or refused and that entry records additional volumes, `open` creates nothing (`Messages.olderEnvironmentUsesVolumes`, code `environmentUnassigned`) and asks again at the next Start (`ClaimOptions.askAgain`). Delete removes only the additional volumes that the question listed and the user confirmed (`additionalVolumesToRemove`, also in pending operations and disconnect requests), and only when their labels make them the environment's own and no other environment records them and no Delete of another account kept them (`removableVolumes`); each other one is kept with a log line that names why (for example a volume that a version before the labels recorded: the user removes it). The question lists only the volumes that Delete would remove (`EnvironmentService.removableAdditionalVolumes`; none when Docker does not answer), so it never offers a volume that it keeps. The additional volumes that a Delete keeps (not confirmed, not removable, or all of them at the Delete of `filesMissing`) are recorded in the same registry change that removes the entry (`EnvironmentRegistry.remove(id, { kept, removed })`, `RegistryFile.keptVolumes`: name, owner, time; one record per name and owner; a removed volume drops all records of its name); `hostAccessInput` adds the records of other owners whose volume exists to `foreignVolumes`, and drops (`forgetKeptVolumes`) the records of a mounted name whose volume no longer exists. Only kept volumes that exist are recorded; a failed first open records the additional volumes that it leaves behind the same way. Invalid records are left out when the file is read, and the next write keeps a copy of the file first (`droppedRecords`). The records cannot be restored after a loss of the registry (container restrictions, section 10).

## 6. Docker

- **Finding the CLI.** The extension host on macOS often has a short `PATH`. Search `PATH`, then `/usr/local/bin`, `/opt/homebrew/bin`, `/Applications/Docker.app/Contents/Resources/bin` (macOS), and `C:\Program Files\Docker\Docker\resources\bin` (Windows). While the CLI is missing (or cannot be started), the extension searches again, at most every 10 seconds, so a Docker installed while VS Code runs is found without a reload.
- **Docker start** as in concept 7.6: `docker info` as the check; `docker desktop start`, and the fallbacks per platform; on Linux with Docker Engine, only the message with `sudo systemctl start docker`. Repeat `docker info` every 2 seconds for at most 2 minutes.
- **Installation plan** (`installPlan` in src/core/docker/dockerSetup.ts; the walkthrough step "Install Docker"). A modal confirmation lists the exact commands, or the download URL and the target file, and says that an administrator password may be requested in the terminal. The step first looks the CLI up (`lookUpCliNow`): found → "Docker is already installed on this computer." and nothing runs (the walkthrough stays reachable after the installation); the step WSL 2 likewise with `wslReady`. Commands run in a new terminal "Install Docker" (`createTerminal` with `installTerminalOptions`: `/bin/sh` on macOS and Linux, the Windows PowerShell of `%SystemRoot%` on Windows, `cwd` the home folder, `strictEnv` with a fixed `PATH` on every platform (Windows: the folders of `%SystemRoot%` and `%LOCALAPPDATA%\Microsoft\WindowsApps`, where winget lives) and a few kept variables of the computer (`HOME`, `USER`, `LOGNAME`, the language, `TERM`, a proxy, the certificate variables `SSL_CERT_FILE`, `SSL_CERT_DIR`, `CURL_CA_BUNDLE`, on macOS the `HOMEBREW_*` settings, on Windows the folders and names of the user), so that terminal profiles, `terminal.integrated.env.*` of the workspace, the search path of the shell that started VS Code, and files of the opened folder change nothing; on macOS the command names the full path of the Homebrew that was found (a path with unusual characters: the download instead); `show`, `sendText`): joined with `&&` on macOS and Linux, one line per command on Windows (Windows PowerShell before version 7 has no `&&`).
  - macOS: Homebrew found (`brew` in `PATH`, `/opt/homebrew/bin`, or `/usr/local/bin`) → `brew install --cask docker-desktop` (the cask `docker` was renamed to `docker-desktop`). Otherwise the download of `https://desktop.docker.com/mac/main/arm64/Docker.dmg` (Apple silicon, also for VS Code for Intel under Rosetta, `sysctl.proc_translated`) or `…/mac/main/amd64/Docker.dmg` (Intel) to `~/Downloads`, then `open` of the .dmg; the user drags Docker to Applications.
  - Windows: winget found → `winget install --exact --id Docker.DockerDesktop --accept-package-agreements --accept-source-agreements`. Otherwise the download of `https://desktop.docker.com/win/main/amd64/Docker%20Desktop%20Installer.exe` (arm64: `…/win/main/arm64/…`) to the Downloads folder; it is opened with `vscode.env.openExternal` of the file, so that the shell of Windows handles the elevation prompt of the installer.
  - Linux: Docker Engine from the repository of Docker, by `ID` of `/etc/os-release` (or `/usr/lib/os-release`), with the commands of https://docs.docker.com/engine/install/: `ubuntu` and `debian` with apt (the key to `/etc/apt/keyrings/docker.asc`, the source file `/etc/apt/sources.list.d/docker.sources` written with `printf … | sudo tee`, with the codename (`UBUNTU_CODENAME`, else `VERSION_CODENAME`) and the Debian architecture written out, so that the line works in every shell), `fedora` with `dnf config-manager addrepo --from-repofile` (Fedora 41 and later, DNF 5) or `dnf config-manager --add-repo` (older), `rhel` and `centos` with `dnf-plugins-core` and `dnf config-manager --add-repo`; then `docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin`, and `sudo usermod -aG docker <user>` with the user name written out (`os.userInfo().username`; a name that is not a plain login name → `manual`), with the note that a new login (or `newgrp docker`) is needed and that Docker's packages replace containerd, runc, or docker.io of the distribution (the package manager asks). With a source of download.docker.com in apt already (`/etc/apt/sources.list`, `sources.list.d/*.list` and `*.sources`; a second one with another key would stop apt) → `manual`. Other distributions and architectures → the installation guide of Docker opens (`manual`). Docker Desktop for Linux is not installed by the extension; the step text links its guide.
  - Downloads: only HTTPS URLs of desktop.docker.com, also the target of each redirect. Progress notification with Cancel; the file is written as a new `<name>.download` (an existing file or link there is removed first, then created with `wx`) and renamed when complete. Before it opens, it is marked as downloaded: `xattr -w com.apple.quarantine 0081;<time>;Dev Environments;` on macOS, the stream `Zone.Identifier` (zone 3) on Windows; when that fails, the installer is not opened and a message names the saved file.
  - After the terminal or the installer: the CLI is looked up every 5 seconds (without the 10-second waiting time of the adapter) for at most 30 minutes, until it is found; then the context keys and the sidebar update, and the extension offers **Start Docker**.
  - Start Docker (walkthrough): `ensureDockerRunning` with the progress "Starting Docker". Docker Engine on Linux (`dockerEngineNotRunning`): after a confirmation, `sudo systemctl enable --now docker` in the terminal.
- **Docker socket for the workspace helper:** mount `/var/run/docker.sock` to `/var/run/docker.sock`. This path works with Docker Desktop on macOS, Windows, and Linux, and with Docker Engine. If `DOCKER_HOST` is a `unix://` path, mount that path instead — only on Linux with Docker Engine: with Docker Desktop, the engine runs in a virtual machine, so a path of the computer is not a path of the engine, and the helper always mounts `/var/run/docker.sock`.

## 7. Workspace helper

- **Image.** `resources/helper/Dockerfile`, with `ARG BASE_IMAGE=node:24-trixie-slim` (Node.js 24 LTS on Debian 13). It installs `git`, `ca-certificates`, `openssh-client`, the Docker CLI with the buildx and the Compose plugins (Debian packages `docker-ce-cli`, `docker-buildx-plugin`, and `docker-compose-plugin` from `download.docker.com`; the Compose plugin is not pinned, like `docker-ce-cli`), and `@devcontainers/cli` in a pinned version. It sets `git config --system --add safe.directory '*'`, because the helper runs as root on files of another user.
- **Tag.** `devenv-helper:<first 12 characters of sha256(Dockerfile content + CLI version)>`, label `devenv.helper=true`. The extension builds the image when this tag is missing (first use, and after an extension update that changes the Dockerfile or the CLI version), with `--pull`; without it when the registry does not answer or when the build with `--pull` fails (for example the pull limit of Docker Hub, which counts the pull of the daemon but not the digest request of the extension): the image then comes from the local base image, and the next check that gets a digest asks for a build with a fresh base image. **Refresh:** only the open pipeline does it, and only with the setting `updateImagesOnConnect` on; the other helper runs (for example of a delete or a branch switch) only build a missing tag. At most once a week per tag, the extension reads the registry digest of the base image, with the registry client and the credentials of the image check (section 9) and its own 5-second limit, in the background: the open does not wait for it, so it overlaps with the image check and adds no wait (NFR-08). A changed digest makes the next open build the same tag again with `--pull --no-cache` (new base image, Debian packages, and Docker CLI; the progress shows "The workspace helper is being updated.") and remove the previous image if it has no tag anymore. No answer from the registry keeps the image, and the check runs again at most once a day; a failed build keeps the image (Docker moves the tag only after a successful build) and checks again a week later. An image built with `--pull` without a recorded digest (built before `helper.json` existed, or the registry answered without a digest) gets the current digest, without a build. A window reuses the result of its helper check for an hour. **Cleanup:** at most once a day, of the images with the label `devenv.helper=true`, except the image of the current tag, the extension removes dangling images and helper tags that no window used for 7 days (`lastUsedAt`, written at most once an hour). A helper tag that `helper.json` does not know is foreign (another extension version, possibly of another installation of VS Code such as Insiders, which has its own `helper.json`): it first gets 7 days of grace, so a helper that old windows of another extension version still use is not removed at once. A removed tag keeps a tombstone in `helper.json` for 90 days: when the tag comes back, another installation built it again and uses it, so it is not removed again, and two installations do not remove each other's helper in a loop. Tags of other repositories are never removed, and never with force; a failed removal (for example an image that a helper container uses) is logged and tried again at the next cleanup. Two windows can do this at the same time: each write of `helper.json` is atomic, and the file is advisory, so at worst a check or a build runs twice.
- **Run.** Each helper run is `docker run --rm -i` with the workspace volume at `/workspaces` and the label `devenv.helper-run=true`. Only the Dev Container CLI runs (read-configuration, build, up) also get the Docker socket and the cache volume `devenv-helper-cache` (`--user-data-folder`: only what the CLI keeps there itself; CLI 0.89.0 downloads Features into a new folder below the helper's temporary folder at each run, so the volume is no Features cache, and a build or rebuild with Features needs internet access). Git runs (clone, switch branch, Git summary) and the file-reading scripts get neither, because Git runs programs that the repository configuration names (filter drivers). Runs that need no network (Git summary, reading and listing configurations) use `--network none`.
- **Token for the clone.** The token never appears on a command line, in an environment variable of a container, or in `.git/config`. The helper receives it on standard input, writes it to a `tmpfs` mount, and a Git credential helper reads it from there. The remote URL is `https://github.com/<owner>/<repository>.git`.
- **Container-only Git** (concept section 9). At each open, before `devcontainer up` (and also when the container runs already), a helper run without the Docker socket, the cache volume, and network gets the token of the owner account on standard input (same `tmpfs` pattern) and writes `/workspaces/.devenv+/github-token` (mode 0600, replaced with a rename), creates `gitconfig` when it is missing (user.name: the GitHub profile name or the login; user.email: `<databaseId>+<login>@users.noreply.github.com`, from `viewer { databaseId login name }`, with the session account as fallback) and ensures its section `[credential "https://github.com"]` (an empty helper, then the helper of the container), creates `credentials.gitconfig` with an example in comments when it is missing (never overwritten), creates `docker/` (mode 0700), and writes `gh/hosts.yml` (mode 0600 in `gh/`, mode 0700; replaced with a rename at every open) with the same token and the login of the session account: the sign-in of the GitHub CLI as the account that owns the environment. The file has both forms that `gh` reads: the keys `oauth_token`, `user`, and `git_protocol: https` of the host `github.com` (gh before 2.40, and the active account of gh 2.40 and newer) and `users.<login>.oauth_token` (the accounts of gh 2.40 and newer); all values in double quotes. The login is checked as a GitHub login (1 to 39 letters, digits, hyphens, and underscores, starting with a letter or a digit; the underscore is part of the logins of Enterprise Managed Users), in TypeScript and in the script; a login that fails the check never goes into `hosts.yml`: the helper runs without it, writes the token and the Git configuration, removes `hosts.yml`, and prints a note (the GitHub CLI is not signed in, Git works); a token with characters that would need escaping in YAML (no GitHub token has them) removes `hosts.yml` instead. Other files of `gh/` (for example `config.yml`, which gh writes itself at its migration to several accounts) stay; the extension never writes `config.yml`. Everything gets the numeric owner of `/workspaces/<name>`; on a first open this runs after the ownership fix, and after each creation of a container the ownership fix also covers `/workspaces/.devenv+`. A link in place of the folder or of a file is removed first. A failure is a warning; the environment opens. The question for `viewer` starts as soon as the session is known (it overlaps with the Docker start, the clone, and the image check), is shared per account in the window, has a time limit of 5 seconds, and after a failure the fallback counts for 10 minutes. When a window leaves an environment because of the account (sign-out, or another account), the controller removes the token file and `gh/hosts.yml` in a workspace helper run on the volume of the environment (`REMOVE_GIT_TOKEN_SCRIPT`, without the Docker socket and network, time limit 30 seconds, best effort, logged), whether the container runs or not, and only when the volume exists (the helper would create an empty one); it needs no tool of the image of the dev container and is not bound by its `--cap-drop`. Otherwise the files stay in the volume (on the disk of the computer) until the next open of the owner account replaces it or **Delete** removes the volume (concept section 9). After each creation of a container, `docker exec -u root` writes the `~/.gitconfig` of the remote user (`HOME_GIT_CONFIG_CONTENT`: `[credential] helper =`, then an `[include]` of `credentials.gitconfig` and `gitconfig`, for Git older than 2.32 and processes without the variables) when it is missing or empty; a file of the image with content and links stay as they are. The copy of the Git configuration of the computer is switched off only by the setting `copyGitConfig` of the container (section 8), not by this file. Then `docker exec -u <remote user> … git --version`: Git older than 2.9 gives the warning `Messages.oldGit`, Git 2.9 to 2.31 a log line, no Git nothing.

Otherwise the user in the container cannot write the files, so the extension changes the owner of the files that belong to another user (`find … -exec chown`) to the user and group of `remoteUser`: before the first `devcontainer up` of a new clone, in a short-lived container of the environment image (the remote user is resolved as Dev Container CLI 0.89.0 does it: the last `remoteUser` of the label `devcontainer.metadata`, else the user of the container, which is the last `--user`/`-u` of the `runArgs` that `up` passes to Docker, else the last `containerUser` of the label, else the user of the image, else root; of `user:group` only the user part counts, and `0` is root), because `onCreateCommand` and `postCreateCommand` run during `up` as that user; and after each creation of a container, as root in the dev container.

A refusal is `UserFacingError('hostAccess')` with each setting named: settings that need access to the computer in `Messages.hostAccess`, settings that the policy does not know (unknown flags and options, arguments that are no flag, entries that are no text) and values that it does not support (for example `--restart=always`) in `Messages.unsupportedOptions` (`hostAccessReport`). `--network container:…` is refused, also in Docker's long form `name=container:…` (CSV, keys and values in lower case). The allow-list of `runArgs` (`RUN_FLAGS`) gives a one-line reason for each flag; it follows Docker's reading of the flags (a flag that takes a value takes the next argument, also one that starts with `-`; a group of short flags such as `-it` is read letter by letter). Values are checked for `--label`/`-l` (no key with the prefix `devenv.` or `devcontainer.`: the CLI puts its id label before the `runArgs`, and Docker keeps the last label of a key; refused as not supported), `-e`/`--env` (no variable of container-only Git, `isContainerGitVariable`: `GIT_CONFIG` and `GIT_CONFIG_*`, and the names of `containerEnvironment`, and no token or host variable of the GitHub CLI, `isGitHubCliAccountVariable`: `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GH_HOST`, refused with the reason `GITHUB_CLI_ACCOUNT_REASON` because `gh` prefers them over the sign-in in `GH_CONFIG_DIR` (user decision 2026-09-26; an `ENV` of a Dockerfile is not checked); with or without a value; `containerEnv` and `remoteEnv` of the repository configuration and of each entry of the image metadata are checked for the same names, but not those of the merged configuration, which for an existing container holds the values of the override configuration, also of an earlier version; the variables of the Dev Containers extension, the VS Code server, and GnuPG are not checked), `--env-file` (only a path below `/workspaces` without `..`: `docker run` reads it in the helper; its content is not checked, and Docker applies `-e` after it, so only variables that the override configuration does not set can come from it; like an `ENV` of an image, it can set `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, and `GH_HOST`, which `gh` prefers over its sign-in; Git is not affected), `--stop-timeout` (at most `MAX_STOP_TIMEOUT_SECONDS` = 20, because the Session Monitor ends each Docker call after 30 seconds), `--restart` (`no`, `on-failure[:n]`), `--oom-score-adj` (0 or more), `--log-driver` (`json-file`, `local`, `none`), `--log-opt`, and `--storage-opt` (`size=`). In a container where root may not change files of the user (for example `--cap-drop ALL`), `~/.gitconfig` is written as the remote user after the run as root failed. A mount may use a volume named like the workspace volume of an environment (`ENVIRONMENT_VOLUME_PATTERN`) only when it is its own. Refused: a volume of another owner, without an owner label, a workspace volume (no `devenv.volume`), and every such volume for an environment without owner; the `foreignVolumes` of other accounts are checked first. The pipeline records such a shared volume (`recordedVolumes`, in `saveConfiguration`, `createAdditionalVolumes` before `up`, and `recordContainerVolumes`) only to protect it: Delete removes a volume only when it is its own (`isOwnVolume`), no other entry records it, and no Delete of another account kept it (`removableVolumes`), so the Delete of either environment keeps it while the other records it, and the question of Delete does not list it. Before each check, the pipeline reads the labels of the named volumes of the mounts (`mountedVolumeNames`, `docker volume inspect`; no call without named volumes). `remote.localPortHost` other than `localhost` in `customizations.vscode.settings` of any source is refused, because the window applies the settings of the container (VS Code forwards on `0.0.0.0` for any other value); an image or a process in the container that writes `~/.vscode-server/data/Machine/settings.json` is not checked (container restrictions, section 10). When the merged configuration cannot be read within 10 seconds (without a container, the CLI reads the base image and the Features, from the registries when they are not local, without the credentials of the extension), the helper container of the read is removed and the configuration is read again without it (NFR-08); the image metadata check stays. - **Host access policy: the switch per repository** (concept sections 8 and 9, user request 2026-09-26; src/core/hostAccessChecks.ts). `parseHostAccessChecksOff` reads the user setting `devEnvLauncher.hostAccessChecksOff` (`readSettings` reads only its `globalValue` through `inspect`; the manifest gives it the scope `application`): entries are trimmed, compared without case, and entries that are no `owner/name` are ignored with one warning (`warnInvalidHostAccessChecksOff`, again only when they change). `hostAccessChecks(repository, settings)` gives `'on' | 'off'`; the pipeline reads it once at the start of each open (`PipelineContext.hostAccessChecks`, a warning line in the log when off) and passes a boolean to `hostAccessReport(input, checksOn)`, for the configuration, the `runArgs` of the override configuration, and the image metadata before `up`. | Step | Call |
|---|---|
| Read configuration | `devcontainer read-configuration --workspace-folder /workspaces/<repo> --config <config path> --id-label devenv.environment-id=<id> --include-merged-configuration` (at most 10 seconds; then again without `--include-merged-configuration`) |

| Create or start container | `devcontainer up --workspace-folder /workspaces/<repo> --override-config <override file> --id-label devenv.environment-id=<id> --skip-post-attach` (plus `--remove-existing-container` when the container is replaced) |

- The override configuration is the complete configuration for `up` (the CLI uses it instead of the repository configuration). It contains only: `image`, `workspaceMount`, `workspaceFolder`, `runArgs` (repository values without `--name`, `--rm`, `-i`, `-t`, and `-d`, read with the parser of the policy and named in the log, `-p`/`--publish` without an address with `127.0.0.1:`, or only `--label devenv.container-config=unknown` without a readable configuration; plus `--label devenv.container-version=4` and `--name <container name>`), `appPort` (a number `n` as `127.0.0.1:n:n`, a string without address with `127.0.0.1` in front, for example `8080:80` → `127.0.0.1:8080:80` and `80` → `127.0.0.1::80`; a string with a loopback address stays; the long syntax with `=` is refused), `containerEnv` and `remoteEnv`, `customizations.vscode.settings` (`devContainersSettings`), `shutdownAction: "none"` (concept 7.6). `initializeCommand` is never passed (the policy refuses it). Everything else comes from the label `devcontainer.metadata` of the environment image; the CLI appends the properties of the override configuration as the last entry of the label of the container.
- `customizations.vscode.settings`, flat keys, as the Dev Containers extension 0.470.0 reads the settings of a container (class `kv`: the new key `dev.containers.*`, for some settings then the old key `remote.containers.*`): `dev.containers.copyGitConfig` and `remote.containers.copyGitConfig` `false` (a `false` under the new key alone falls back to the old key), `dev.containers.gitCredentialHelperConfigLocation` `none`, `dev.containers.dockerCredentialHelper` `false`, and `dev.containers.githubCLILoginWithToken` `false` (these two only under the new key). The Dev Containers extension writes the settings of all entries of the label into `~/.vscode-server/data/Machine/settings.json` at the first attach of a new container, the later entries winning (to verify in V-8). The CLI collects `customizations` of all entries, so the extensions and other settings of the repository stay.
- `containerEnv` and `remoteEnv` (merged over those of the image metadata), only documented variables of Git, Docker, and the GitHub CLI: `GIT_CONFIG_GLOBAL=/workspaces/.devenv+/gitconfig`, `DOCKER_CONFIG=/workspaces/.devenv+/docker`, `GH_CONFIG_DIR=/workspaces/.devenv+/gh`, `GIT_SSH_COMMAND=ssh -o IdentityAgent=none`, and four Git settings of the command line level as `GIT_CONFIG_COUNT=4` with `GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` (Git 2.31 and newer): `credential.helper=` (removes every credential helper of the configuration files, among them a forwarding helper that the Dev Containers extension writes with `git config --system` and `--global` when its settings of the container do not apply), `include.path=/workspaces/.devenv+/credentials.gitconfig` (the helpers of the user for other hosts), `credential.https://github.com.helper=` (removes them again for github.com), and `credential.https://github.com.helper=<helper of the container>`. Older Git gets the same through the `~/.gitconfig` of the extension. By user decision (2026-09-25), no variable of the Dev Containers extension or the VS Code server is set, blanked, or changed (`SSH_AUTH_SOCK`, `REMOTE_CONTAINERS_IPC`, `REMOTE_CONTAINERS*`, `BROWSER`, `VSCODE_*`), and neither `GNUPGHOME` nor `GIT_CONFIG_PARAMETERS`; their sockets stay usable by a process that looks for them (concept section 9, limits). No token in any variable (no `GH_TOKEN`, no `GITHUB_TOKEN`).
- `--skip-post-attach`: the Dev Containers extension runs `postAttachCommand` when it attaches (to verify in V-1).
- `build` and `up` get `--user-data-folder /devenv-cache` (the cache volume; `read-configuration` does not get it). CLI 0.89.0 keeps there only its own data, for example an empty folder for builds, not the downloaded Features: it puts them into a new folder below the helper's temporary folder at each run, which is removed with the helper container, so a first build or a rebuild with Features needs internet access. `up` also gets `--update-remote-user-uid-default never`, because the CLI runs as root in the helper and would otherwise build an extra image at each container creation. `build` gets `--no-lockfile` unless the repository has the lockfile of its configuration (`devcontainer-lock.json`, or `.devcontainer-lock.json` next to a configuration named `.devcontainer.json`), so the build does not add a file to the repository.
- The last line of standard output of `build` and `up` is a JSON result (`outcome`, `imageName`, `containerId`, `remoteUser`, `remoteWorkspaceFolder`). All other output goes to the output channel.
- When a lifecycle command fails, `up` exits with code 1 and the result `{ outcome: 'error', containerId, description: '… from … failed.' }` (to verify in V-10). If that container runs, the helper keeps it, and the open continues with a warning, as with the Dev Containers extension. The remote user then comes from the label `devcontainer.metadata` of the image.
- The config hash (`configHash`) is `sha256` of the text of `devcontainer.json` plus the text of the Dockerfile, if there is one.

## 9. Image check

- **References** (concept 7.7): `image`; each `FROM` of the Dockerfile (with `ARG` values from `build.args` and from `ARG` defaults; without references to earlier stages and without `scratch`); each Feature key that is an OCI reference. Local Features (`./…`), tarball URLs, and references with `@sha256:` are not checked.
- **Normalization:** Docker Hub is `registry-1.docker.io`, official images get the prefix `library/`, and the default tag is `latest`.
- **Request:** `HEAD /v2/<name>/manifests/<tag>` with the `Accept` types for OCI index, Docker manifest list, Docker manifest v2, and OCI manifest. The digest comes from the header `Docker-Content-Digest`.
- **Authentication:** first without credentials. On `401`, read `WWW-Authenticate: Bearer realm=…,service=…,scope=…` and request a token, with Basic credentials if Docker has credentials for this registry (`~/.docker/config.json`: `auths`, `credsStore`, `credHelpers`; credential helpers through `docker-credential-<name> get`). For `ghcr.io`, the fallback is the GitHub session with the scope `read:packages`, requested only when needed (concept 7.7). The `docker pull` of such an image uses the same session: the extension writes it to a temporary Docker config folder (`docker --config`, mode 0700, removed after the pull) and passes the endpoint of the current Docker context as `DOCKER_HOST`. The session is sent only over a local or encrypted connection to the Docker engine (`isProtectedDockerEndpoint`): the default endpoint, `unix://`, `npipe://`, `ssh://`, or `tcp://` with `DOCKER_TLS_VERIFY` (not `0`) and `DOCKER_CERT_PATH` set in the environment of VS Code. The TLS files of a Docker context are not used, because the temporary config folder has no contexts and the context store is internal to Docker: a `tcp://` context counts as unencrypted unless these variables are set. Over any other connection, the session is not sent; the extension downloads the image with a plain `docker pull` (Docker's own credentials, which is enough for a public image), and when that fails too, the error says that the connection to Docker is not encrypted.
- **Time limit:** all requests of one connection run in parallel under one `AbortController` with 5 seconds (NFR-08). If one registry does not answer, the whole update step is skipped (FR-13).
- **Proxy:** use the Node.js `https` module. VS Code applies its proxy settings to this module in the extension host.
- **Build record:** it stores the digests that the check read right before the build. The comparison uses the build record, not the local images (concept 7.7).

- Sign-in state: `auth.ts` alone sets the context key `devEnvironments.signedIn` (welcome view **Sign in with GitHub**). Signed in means a session with `repo read:org` exists and GitHub did not reject its token. Every GitHub caller reports an HTTP 401 to `reportRejectedToken`: `GitHubApi` (`onUnauthorized`, all GraphQL requests: the repository list, branches, single repositories, the identity of the container Git), the clone and the fetch of Switch branch (Git "Authentication failed" for github.com, `isGitHubTokenRejected`), and the token service of ghcr.io for the GitHub session (`RegistryClient.onCredentialsRejected`). The rejection is kept per scope set and session (ID and token), and cleared by a session with another ID or token or by a request that succeeds (`reportAcceptedToken`). While it holds, an interactive request, for example the unchanged command `devEnvironments.signIn`, calls `getSession(…, { forceNewSession: true })` instead of `createIfNone`, which would return the rejected session without a dialog. Workaround for VS Code keeping such a session; remove it when VS Code handles it. The button, the welcome texts, and the sign-in row are unchanged; the account and its environments stay available (`getAccount` gives the account of a rejected session without a dialog, so Stop and Delete ask for no new sign-in; requests that need a working token do), and the one-time warning with the action **Sign in** (`SIGN_IN_AGAIN_DETAIL`) stays.
- While an environment is Updating, Start, Stop, and Rebuild are hidden (concept 7.9 rule 1). Delete stays (concept 7.15), except while the operation is itself a delete: after the confirmations, it waits until the operation of the other window has ended, in a progress notification with Cancel.

## 14. Repository discovery

- **Scan scope** (concept 7.4, setting `owners`): `DiscoveryService` reads the setting at each refresh (`DiscoveryOptions.scope`); `scope.ts` normalizes it (trimmed, case-insensitive, without duplicates). Empty: `DISCOVERY_QUERY` over `viewer.repositories`, one sequential cursor. Configured: `SCOPE_VIEWER_QUERY` (login, `databaseId` for the account check, organizations; no repositories), then per owner `OWNER_REPOSITORIES_QUERY` (`repositoryOwner(login:)` with `... on Organization` and `... on User` (`ownerAffiliations: [OWNER]`)), or `VIEWER_REPOSITORIES_QUERY` (`affiliations` and `ownerAffiliations` `[OWNER]`) for the login of the account. `repositoryOwner: null` with only NOT_FOUND, SAML, OAuth, or FORBIDDEN errors is a missing owner: hint kind `notFound` (`Messages.organizationNotFound`, the row opens `https://github.com/<login>`), unless a SAML or OAuth hint names the owner. The probe of organizations asks only organizations of the scope. The result stores `scope`; the sidebar shows a stored list, and the result of a refresh, only when its scope equals the setting (`sameScope`), and calls `Sidebar.onScopeChanged` when the setting changes (clears a list of another scope, then a refresh with `again`). `repositoriesToLookUp` and `EnvironmentClaims` (`ClaimDeps.inScope`) skip repositories outside the scope, so no `getRepository` request is about them.
- **List and lookups:** the list queries (`DISCOVERY_QUERY`, `OWNER_REPOSITORIES_QUERY`, `VIEWER_REPOSITORIES_QUERY`) never contain the configuration lookups and read 100 repositories per page (`DISCOVERY_PAGE_SIZE`). `RepositoryCollector.addPage` returns the repositories that need a lookup, and `LookupQueue` starts a batch of `configurationsQuery` (aliases `r<i>`, variables `o<i>`/`n<i>`, `LOOKUP_BATCH_SIZE` 50) as soon as 50 are listed; `finish` starts the rest and waits for all batches. First load: every repository gets a lookup.
- **Concurrency:** one `Semaphore` of 4 (`DISCOVERY_CONCURRENCY`) per refresh covers every request (account, list pages, lookups, organizations, probes); list pages and the account request are `priority` requests that go before waiting batches, so the list keeps loading. The refresh has one `AbortController`: the first failure of an owner or a batch (`guard`) aborts all other requests, and the refresh fails with that failure as a whole (the stored file stays); an abort of the caller gives an AbortError. The 30-second time limit per request and the smaller page on a timeout (100, 50, 25, 12, 10) stay; a lookup batch that times out is split in halves (`allOrAbort`). The GitHubApi 401 hooks cover the list, lookup, and account requests, because all go through `GitHubApi.graphql`.
- **Request count of the first load:** empty scope, n repositories: ⌈n/100⌉ list requests and ⌈n/50⌉ lookup requests (664 repositories: 7 + 14 = 21 requests), plus further pages of organizations (more than 100) and probes. Configured scope: 1 account request, ⌈n_owner/100⌉ list requests per owner, and ⌈n/50⌉ lookup requests. With about 3 seconds per batch and 4 at the same time, 664 repositories load in about 12 to 15 seconds (previously 14 combined requests one after another, about 43 seconds).
- **Incremental detection:** with a stored list (`loadStored`, also of another scope), `needsConfigurationLookup` (new repository, other `pushedAt`, or other default branch) selects the repositories for the lookups; unchanged repositories keep their stored `configPaths`. A repository that an error of its list page points into, or whose lookup GitHub did not answer, is not kept in `withoutConfiguration` and is read again at the next refresh; one that has a configuration is listed in `uncertain`, which `storedDetections` skips, so it is read again too. Each refresh logs "loaded in N seconds with M requests" and "configurations of N repositories read with M requests".
- **Progressive display:** `DiscoveryService.onPartialResult` gets the repositories with a configuration found so far after each list page and each lookup batch (account ID, scope); on the first load they join as their batches finish. extension.ts passes them to `Sidebar.onPartialResult`, which shows them only during a refresh that started while the view had no list of the account, and only for this account and the current scope; the complete result replaces them.
- **Select Organizations…** (`ownerSelector.ts`, rules in `ownerChoices.ts`): multi-select Quick Pick with the account ("your account"), its organizations in alphabetical order (from the list of the view when it belongs to the account, else `DiscoveryService.viewerOrganizations`, which lists no repository), and the owners of the setting in neither list ("from your settings"); the setting is pre-selected. OK writes `owners` with `ConfigurationTarget.Global`; an empty selection writes `[]`. Not signed in: `Messages.signInRequired` with **Sign in**.

## 15. Docker Compose

Unit 6 (user decision 2026-09-26). A configuration with `dockerComposeFile` and `service` (and optionally `runServices` and `workspaceFolder`) opens like an image or Dockerfile configuration: one `devcontainer up` starts the dev service and the other services. The code: `src/core/helper/compose.ts` (model, names, rewrite), `composeAccess.ts` (policy), `COMPOSE_MODEL_SCRIPT` and `WRITE_AND_RUN_SCRIPT` in `scripts.ts`, and the Compose branches of `environmentService.ts`. The facts about CLI 0.89.0 that the design relies on are checked by `devcontainerCli.contract.test.ts`.

- **The checked model is the model that runs** (decision D-1). A helper run without the Docker socket, without network, and with a tmpfs over `/workspaces/.devenv+` (the token) runs `docker compose -f <files> --profile '*' config --format json` with `COMPOSE_PROJECT_NAME=devenv-<short id>` (`WorkspaceHelper.composeModel`). The compose files are those of `dockerComposeFile`, resolved against the folder of the configuration as the CLI does, and must be in the repository (`resolveComposeFiles`; a missing `dockerComposeFile`, a variable, or a path outside is not supported). The script also reports the Compose version, whether `config` escapes `$` as `$$` (a probe), the Dockerfile of each built service (a file in the repository, also after links, or a file outside of it that is no path of the workspace helper), the real path of each bind mount source, `env_file`, local build context, and Dockerfile (links), and `inputsHash`, the sha256 of the files that Compose read (the compose files, the `.env` of the project folder, the `env_file`s; only the hash leaves the run). The pipeline checks this model (`composeAccessReport`, container restrictions section 13) before any build, and again, with the labels of the volumes then, before each `up` that creates containers. `build` and `up` get our rewrite of exactly this model as the only compose file (`/tmp/devenv-override/compose.json`, written by `WRITE_AND_RUN_SCRIPT` from standard input), named with an absolute path by our copy of devcontainer.json (`composeConfigOverride` for `read-configuration` and `build`, which has no `--override-config`; `buildComposeOverrideConfig` for `up`). The repository's compose files are read once, so nothing can change between the check and `up`, and no `!override` YAML tag is needed.
- **Project name** (D-2): `devenv-<short id>` (`composeProjectName`, the same as the repository of the environment image), set by `COMPOSE_PROJECT_NAME` of each helper run (it wins over a `.env` of the repository) and by `name:` of the model. The CLI finds the dev container only by the project and the service; `up` fails when its result names another project (L-2).
- **Environment image** (D-3, D-8): `devcontainer build --image-name devenv-<short id>:<n>` with the build model (`composeBuildModel`): the dev service builds `devenv-<short id>-<service>` (an image-only dev service gets a synthesized `FROM <image>` build, so the CLI never uses its shared `vsc-<repository>-<hash>` name), which the CLI tags as the environment image. The up model (`composeUpModel`) runs the dev service from the environment image (`image`, no `build`, `pull_policy: never`). Other services: images that the pipeline pulls before `up` with the credentials of the image check (`pull_policy: missing`), and images that Compose builds as `devenv-<short id>-<service>`. Build numbers, the metadata check of the image before `up`, refused updates, and the fallback to the previous image work as for a single container. The build record gets `compose: { service, images, serviceImages, version, inputsHash }`: the built images, which Delete removes; the images of the other services that are not built (`composeServiceImageReferences`), which `removeUnusedBaseImages` never removes (they are the user's images, for example `postgres:16`, not base images of the environment image; concept 7.7 removes base images: the `FROM` images and the image of the dev service; a record without the list removes none); and the Compose version and the hash of the files as written (`composeInputsHash`: devcontainer.json, `inputsHash`, the Dockerfiles). `configHash` is `composeConfigHash`: devcontainer.json, the merged model (keys sorted), and the Dockerfiles of the built services. Whether the configuration changed (`composeConfigurationChange`, review round 1, P-4): the files differ, or they are equal and the same Compose version printed another model. When only the Compose version (the helper installs the current plugin) and with it the printed model differ, it is no change: the open takes the new model hash and version into the record without a question. The image check covers every service image and each `FROM` of a built service (`composeReferences`).
- **The rewrite** (`composeUpModel`, logged as "Changed in the Docker Compose model"): every container gets `devenv.environment-id`; the dev container also `devenv.container-version`, the name of the environment (`container_name`), the workspace volume at `/workspaces` (the templates' bind mount `../..:/workspaces` is dropped), and `hostname: <repository name>` (`containerHostname`, as `--hostname` of a single container) unless the service sets `hostname`, uses `network_mode` `host`, `service:…`, or `container:…`, or `uts: host` (`serviceDecidesHostname`); the other services get `devenv.compose-service=<service>` and lose `container_name` (D-12, two environments of one repository would collide). Published ports without an address get `127.0.0.1`. A bind mount of a path inside the repository becomes the workspace volume with `volume.subpath` (Docker Engine API 1.45 or newer, `docker version --format '{{.Server.APIVersion}}'`; older: refused) and `nocopy`, read-only as before: the service can read and change those files of the repository, and nothing else of the volume. Every named volume is declared `external`; `$` is escaped when the output of `docker compose config` does not escape it. `network_mode: service:<name>` of a service of the same model stays (D-9).
- **Volumes** (D-7): before `up` creates containers, the pipeline creates each missing named volume with the labels of the environment: the volumes of the project (`devenv-<short id>_<key>` of the model, and `devenv-<short id>_<source>` of the `mounts` of devcontainer.json and of Features, which the CLI puts into the project) with `devenv.volume=compose`, other named volumes with `devenv.volume=additional`. `compose` volumes are never shared with another environment (`isSameOwnerAdditionalVolume` needs `additional`). All of them join the additional volumes of the entry by the unit-5 rules (`recordedVolumes`, over every container of the environment).
- **Containers and lookups** (D-4): `ContainerAdapter.findContainer` skips containers with `devenv.compose-service` unless they have the name of the environment (`isDevContainer`; review round 1, D2: an image could give a single container that label), so it always returns the dev container, which the window, `currentBranch`, and the Git summary use. The labels `devenv.…`, `devcontainer.…` (except `devcontainer.metadata`), and `com.docker.compose.project` of another project than the environment's (Compose labels the images it builds for the project itself) of the environment image and of the existing images of the other services are refused before containers are created (`imageLabelItems`, class *protected*), also for a single container. Stop, the Session Monitor, `inspectStates` (running when any container runs), Delete, and the restore find all containers by `devenv.environment-id`.
- **Start** (D-15, D-20, D-22): a stopped dev container starts with `up` (Compose starts the services of `runServices`, default all). When the dev container runs, the CLI does not call Compose, so stopped services are started with `docker start` first. Without the workspace helper, or when the configuration cannot be read (no model, so no `up`), `docker start` starts the containers as they are, the other services first and the dev container last, unless they must be created again (below): then the open stops.
- **Stop** (D-20): `docker stop` of the dev container first (after the Git summary), then of the running other services; also when the dev container does not run. The Session Monitor checks again before each further container that no window uses the environment (review round 1, D4); if one does, the others keep running.
- **Host access checks off** (container restrictions section 12): the check, the rewrite, and the metadata check follow the switch of the repository. Each refused item has the class that the same setting has for a single container (`composeAccessClassification`): with the checks off only `computer` is lifted. The rewrite then keeps the published ports and the lifted mounts as the model has them, and every container gets `devenv.host-access=unrestricted`. With the checks on again, an environment whose dev container or any other container has this label is not current: `up --remove-existing-container` creates the dev container again, and Compose the services whose model changed (the label is gone from it).
- **Delete** (D-19): the containers with `devenv.environment-id`, then the other containers of the project (label `com.docker.compose.project`, for example of `docker compose run`; never one whose `devenv.environment-id` names another environment, review round 1, D3), the networks of the project, the images of the build record's `compose.images` and every `devenv-<short id>-*` image (also without a build record, after a failed first open or a lost registry; not one whose `devenv.environment-id` names another environment), the environment images, and the workspace volume. The question of Delete lists the other additional volumes as before (modal, Remove or Keep), then the data of the services in a multi-select list with none ticked ("hold data of the services, for example of a database"): only ticked ones are removed, Escape cancels the Delete (`removableServiceDataVolumes`; `removableAdditionalVolumes` leaves them out). The data of the services are classified by use, not by the label (review round 1, D1; relabelling would break `isSameOwnerAdditionalVolume`): an own volume with `devenv.volume=compose`, an own volume that a service other than the dev service mounts in the model (`composeServiceVolumeNames`, recorded at each open in the entry as `serviceVolumes` and kept once recorded, so that it works when the configuration cannot be read at Delete, or has changed since), or one that a container of another service mounts now (read at Delete, which needs no helper run). A failed first open removes the containers, networks, and images of the project the same way.
- **Switching kind only with a build** (review round 1, P-1): a configuration of the other kind (Docker Compose or a single container) than the environment (its dev container, else its build record) applies only with a build. Without one (**Rebuild later**, a failed or refused update), the open starts the environment as it is (`configurationOfKind`): the containers of Docker Compose with `docker start` (as D-15; without a dev container the open stops), a single container as a container whose configuration is not known. With a build, a single container is replaced by the containers of Docker Compose (the progress says that files outside the repository are removed, `Messages.containerComposeCreated`).
- **A configuration that no longer uses Docker Compose** (after a build): the dev container of Compose is created again (the progress says so, `Messages.containerComposeReplaced`: the named volumes of the services are kept; their volumes without a name are no longer used and stay in Docker as unused volumes, which the extension does not remove), its merged configuration is not checked (the CLI finds containers by `--id-label`, which every container of the project has, so it could merge the metadata of another service; the image metadata is checked before `up`), and before `up` creates the single container the containers of the other services are removed (their volumes stay); after `up`, the networks of the project. The images that Compose built go with the next build record (`removeEnvironmentImages` with the old record's `compose.images`).
- **Restore after a lost registry**: `reconcileFromVolumes` is unchanged: the `compose` volumes carry `devenv.volume` and the labels of the environment, so they join the restored entry (`isOwnVolume`); the containers of all services are found by `devenv.environment-id`. Without a build record, the next open builds and runs `up --remove-existing-container` in the same project, and Compose keeps or recreates the services.
- **Ignored** (D-18): `runArgs`, `appPort`, `workspaceMount`, and `build.options` of a Compose configuration have no effect in the CLI; they are not checked and not passed, with a log line.
- **Volumes before each `up`** (review round 1, P-2): the missing volumes of the model and of the `mounts` are created with the labels of the environment before every Compose `up`, also when `up` only adds containers (a service that the model gained, started after **Rebuild later**); the check of the model and of the image metadata runs again only when `up` creates the dev container.
- **Build paths and networks of other environments** (review round 1, S1, S2): a local build context or Dockerfile is checked with its real path (a link out of the repository, a missing path, or a path of the workspace helper: `isHelperPath`, class *protected*; the same helper paths are refused for `build.context`/`build.dockerfile` of a single container, checked as written). A local build whose Dockerfile the model run could not read is refused. The labels and the attached containers of every network that the model names (`composeNetworkReferences`) are read before the check (`ContainerAdapter.inspectNetworks`); a network of another environment is refused (`foreignNetworkItem`), as the network of another environment in `runArgs` of a single container.
- **Images of other environments** (review round 1, S4): `imageReferenceFinding` normalizes the reference (`docker.io/`, `index.docker.io/`, `registry-1.docker.io/`, `library/`, tags and digests) and refuses the namespace `devenv-` (class *protected*) and image IDs (not supported) in `image` of each service, the `FROM` images of each Dockerfile and `dockerfile_inline` (with the build arguments), `docker-image://` additional contexts, and for a single container in `image`, the Dockerfile, and `--build-context` of `build.options`.
- **Cache volume** (L-5): the CLI writes a compose file into `/devenv-cache/docker-compose/` at each container creation; before each Compose `up`, `WRITE_AND_RUN_SCRIPT` removes those files older than 30 days (the CLI writes a missing one again without a build).
- **Limits**: a running dev container of the environment can swap a link of the repository between the model run (which reads the real paths) and the build (minutes later, in a helper run that mounts the cache volume), so the builder follows the new link; only a process of the environment itself can do so. The labels of images that Compose builds during `up`, and of an image of another service that Compose pulls during `up`, are not checked before `up` (the model sets the labels of the extension on every container, which win). A change only in a file that `include` or `extends` names changes the model hash, not `inputsHash`: it counts as a change only when the Compose version is the same. L-3 a stopped side service of a running dev container is started by the extension, not by the CLI; L-4 `--remove-existing-container` replaces only the dev container, Compose recreates the other services only when their model or image changed; L-6 a new key of a newer Compose version is refused as not supported until the policy knows it; L-7 remote `include`/`extends` (Git, OCI) do not work (the model run has no network); L-10 old images of rebuilt side services become dangling; L-11 a project volume whose key looks like the name of a workspace volume is refused by its name; a configuration that no longer uses Docker Compose, after a lost registry (no build record) and with the dev container removed by hand: the containers of the other services are not recognized before `up`, which may then find one of them by `--id-label` (Delete removes them).
