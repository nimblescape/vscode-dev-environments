# Implementation Notes — Version 1

These notes add the technical decisions that the concept ([vscode-dev-environments.md](vscode-dev-environments.md)) leaves open. The concept is the source of the requirements. If a note and the concept differ, the concept wins, and the note must be corrected.

## 1. Scope

- Phase 1 and phase 2 of the concept (section 12), except Docker Compose configurations. For a Docker Compose configuration (`dockerComposeFile`), the extension shows the message "Docker Compose configurations are not supported yet."
- Not in scope: phase 3 (profile template, backup of unpushed work, `build.cacheFrom`, Podman).
- The verification tasks V-1 to V-12 are not done yet. Code that depends on an unverified assumption has a comment `// Assumption (V-n): …`, so that a later check can find it.

## 2. Technology

| Item | Decision |
|---|---|
| Language | TypeScript, `strict: true`, target ES2022, module CommonJS |
| Bundler | esbuild. Two bundles: `dist/extension.js` (external: `vscode`) and `dist/sessionMonitor.js` (plain Node.js, no `vscode`). |
| Runtime dependencies | None. Use the Node.js modules `https`, `child_process`, `fs`, `crypto`, `os`, `path`. The Dev Container CLI is not a dependency of the extension: it is installed in the workspace helper image. `package.json` lists `@devcontainers/cli` as an exact devDependency only to pin this version: the build passes it to the code as `__DEVCONTAINER_CLI_VERSION__`, and the package is neither bundled nor shipped. So Dependabot proposes each new CLI version in a pull request of its own, and the contract tests (the options and the lifecycle error text, against the package) and `npm run test:docker` check it before a release. |
| Tests | vitest. Unit tests run without VS Code and without Docker. `npm run test:docker` (folder `test/docker/`, not part of `npm test`) runs the core modules against the real Docker engine: the clone of a public repository, the open pipeline on a seeded environment (first open, update, no connection, a removed container, a container of an older version, delete), the container-only Git (variables, label, the settings of the Dev Containers extension in the label, token file, Git configuration, `~/.gitconfig`, credential helper, the helpers of `credentials.gitconfig`, a removed token file, and Git 2.30 of an Alpine 3.13 image), the host access policy (refused configurations, among them a label of Dev Environments, a variable of container-only Git, and a volume of a Docker Compose project; ports on 127.0.0.1; a service on the computer reached through `host.docker.internal`; `--platform`, `--cap-drop ALL`, and `--rm`), and the refresh and cleanup of the helper image. It uses a Docker configuration without credentials and credential helpers (its only `auths` entry, for a registry that does not exist, turns off the default credential helper of the platform), so no credentials of the user, and fails when it leaves or removes a Docker object other than the helper image and pulled base images. |
| VS Code API | `engines.vscode` `^1.90.0`, `@types/vscode` of the same version |
| Package | `@vscode/vsce` creates the VSIX file (decision D-6: private VSIX) |

**Layering rule.** Code in `src/core/` never imports `vscode`. It receives everything it needs through interfaces (process runner, file system paths, logger, clock). Code in `src/vscode/` adapts VS Code to these interfaces. The Session Monitor bundle uses only `src/core/` and `src/monitor/`. So most of the logic can be tested without VS Code.

## 4. Local storage

All files are in the global storage folder of the extension (`context.globalStorageUri.fsPath`), on the local computer.

| File | Content | Writers |
|---|---|---|
| `registry.json` | Environment Registry (concept 7.5) | windows, Session Monitor |
| `repositories-<account ID>.json` | Stored result of the discovery of one GitHub account (concept 6.2, 7.4); the account ID is the numeric GitHub user ID of the session. The shared `repositories.json` of the first version is removed at activation. | windows |
| `sessions/<window-id>.json` | Window status file (concept 7.9) | one window |
| `pending/<environment-id>.json` | Pending connection file (concept 7.9) | windows |
| `operations/<environment-id>.json` | Pending operation, for example `rebuild` (concept 7.14) | windows |
| `disconnect/<environment-id>.json` | Request from a window to the window that is connected to the environment: close the connection first, then hand off the stop, rebuild, or delete (concept 6.2, 7.14). Dropped after 60 seconds. | windows |
| `reopen.json` | Reopen record (concept 7.10) | windows |
| `monitor.json` | Settings for the Session Monitor: waiting time, `stopOnClose` | windows |
| `monitor.lock` | Process ID of the running Session Monitor | Session Monitor |
| `monitor.log` | Log of the Session Monitor (the process has no output channel), at most about 1 MB | Session Monitor |
| `helper.json` | State of the workspace helper images (section 7): per helper tag the base image and its digest at the build, `builtAt`, `checkedAt`, `lastUsedAt`, a rebuild that a check asked for, and the marks of the cleanup for foreign and removed tags; the time of the last cleanup | windows |

Rules:
- Every JSON write is atomic: write a temporary file in the same folder, then rename it.
- Read-modify-write of `registry.json` happens under a lock (a lock folder created with `mkdir`, removed after the write; a lock older than 10 seconds counts as stale).
- `deactivate()` uses only synchronous file writes.
- In the workspace volume (not in the global storage), the folder `/workspaces/.devenv+` holds the configuration of the container: `gitconfig`, `credentials.gitconfig`, `github-token`, and `docker/` (concept section 9, section 7 "Container-only Git" below). A `gnupg/` of an earlier version stays unused.

## 5. Names and labels

- Environment ID: `crypto.randomUUID()`. Short ID: the first 8 characters. An ID is not used when an entry of the registry has its short ID or its volume exists (at most 5 tries), because the names end in the short ID: two environments of one repository (of two accounts) get different names.
- Volume and container name: `devenv-<owner>-<repository>-<short id>`, lower case, only `[a-z0-9_.-]`, at most 63 characters.
- Environment image: `devenv-<short id>:<build number>`.
- Labels on the volume: `devenv.environment-id`, `devenv.repository`, and `devenv.owner-id` (the GitHub user ID of the owner account; `reconcileFromVolumes` restores the owner from it, and its login at the next open). The container gets `devenv.environment-id` through the CLI option `--id-label`, and `devenv.container-version=3` through `runArgs` (2: container-only Git; 3: the settings of the Dev Containers extension for the container, which reach it only through the label of a new container, and only the documented variables of Git and Docker). A label of `runArgs` whose key starts with `devenv.` or `devcontainer.` is refused (section 7, host access policy), except these two labels of the override configuration with their exact values (`CONTAINER_VERSION_LABEL`, `CONTAINER_CONFIG_UNKNOWN_LABEL`). A container without this label, or with an older value, is created again from its environment image (`up --remove-existing-container`, no build, the volume is kept), and the progress shows that the files outside the volume are removed; without the workspace helper, such a container is not started with `docker start`. A container created while the configuration could not be read gets `devenv.container-config=unknown` (and no `runArgs` or `appPort` of the repository); it is created again in the same way at the first open that can read the configuration (`containerIsCurrent`).
- Registry entry: `owner: { id, login }`. An entry without it (of the first version, or restored from a volume without `devenv.owner-id`) is hidden until a claim (`EnvironmentClaims`, one at a time, the owner written under the registry lock only while the entry has none). A claim asks `DiscoveryService.getRepository` in its quiet mode (no repository name in the log or in an error) with the token of the signed-in account, token and account from one session. Mode `auto` (after each successful refresh of the repository list, and for a restored window) assigns only when the repository is private, its owner is the login of the account, and `viewerPermission` is ADMIN, MAINTAIN, or WRITE (`isUnambiguousClaim`). Mode `interactive` (a command of the user, and an open of the environment service) also asks the modal question `Messages.assignOlderEnvironment` for any other repository that GitHub returns; a "Not now" is remembered per account and entry for the window. A failed question, or an entry that stays without owner, gives `Messages.olderEnvironmentNotAssigned` (code `environmentUnassigned`), never the text of another account. The rule `isAvailableTo` (src/core/ownership.ts) applies to the sidebar, the pickers, all commands, the reopen, restored windows, pending operations, and disconnect requests; the environment service checks it again in each operation, and the controller once more right before it connects the window. One environment per repository and account (D-3): the registry refuses a second entry with the same repository (case-insensitive) and owner (entries without owner count as one owner), `findForAccount(repository, accountId)` gives the environment of the signed-in account, and `findUnowned(repository)` an entry of an older version. A claim (`canClaim`) never gives an account a second environment of a repository; it is checked before GitHub or the user is asked and again under the registry lock. `EnvironmentService.open` reads the session first and uses its account: its own environment, else an older entry that it claims (declined or no access: a new environment; GitHub could not be asked: `environmentUnassigned`), else a new environment. The controller looks up only the environment of the signed-in account for a repository; `otherAccount` applies only to an environment that a command names by its ID (a row or the status bar item from before an account change, a restored window, an account change during an open). `reconcileFromVolumes` restores one environment per repository and owner (label `devenv.owner-id`), and at most one per repository for volumes without that label.

## 6. Docker

- **Finding the CLI.** The extension host on macOS often has a short `PATH`. Search `PATH`, then `/usr/local/bin`, `/opt/homebrew/bin`, `/Applications/Docker.app/Contents/Resources/bin` (macOS), and `C:\Program Files\Docker\Docker\resources\bin` (Windows). While the CLI is missing (or cannot be started), the extension searches again, at most every 10 seconds, so a Docker installed while VS Code runs is found without a reload.
- **Docker start** as in concept 7.6: `docker info` as the check; `docker desktop start`, and the fallbacks per platform; on Linux with Docker Engine, only the message with `sudo systemctl start docker`. Repeat `docker info` every 2 seconds for at most 2 minutes.
- **Docker socket for the workspace helper:** mount `/var/run/docker.sock` to `/var/run/docker.sock`. This path works with Docker Desktop on macOS, Windows, and Linux, and with Docker Engine. If `DOCKER_HOST` is a `unix://` path, mount that path instead — only on Linux with Docker Engine: with Docker Desktop, the engine runs in a virtual machine, so a path of the computer is not a path of the engine, and the helper always mounts `/var/run/docker.sock`.

## 7. Workspace helper

- **Image.** `resources/helper/Dockerfile`, with `ARG BASE_IMAGE=node:24-trixie-slim` (Node.js 24 LTS on Debian 13). It installs `git`, `ca-certificates`, `openssh-client`, the Docker CLI and the buildx plugin (Debian packages `docker-ce-cli` and `docker-buildx-plugin` from `download.docker.com`), and `@devcontainers/cli` in a pinned version. It sets `git config --system --add safe.directory '*'`, because the helper runs as root on files of another user.
- **Tag.** `devenv-helper:<first 12 characters of sha256(Dockerfile content + CLI version)>`, label `devenv.helper=true`. The extension builds the image when this tag is missing (first use, and after an extension update that changes the Dockerfile or the CLI version), with `--pull`; without it when the registry does not answer or when the build with `--pull` fails (for example the pull limit of Docker Hub, which counts the pull of the daemon but not the digest request of the extension): the image then comes from the local base image, and the next check that gets a digest asks for a build with a fresh base image. **Refresh:** only the open pipeline does it, and only with the setting `updateImagesOnConnect` on; the other helper runs (for example of a delete or a branch switch) only build a missing tag. At most once a week per tag, the extension reads the registry digest of the base image, with the registry client and the credentials of the image check (section 9) and its own 5-second limit, in the background: the open does not wait for it, so it overlaps with the image check and adds no wait (NFR-08). A changed digest makes the next open build the same tag again with `--pull --no-cache` (new base image, Debian packages, and Docker CLI; the progress shows "The workspace helper is being updated.") and remove the previous image if it has no tag anymore. No answer from the registry keeps the image, and the check runs again at most once a day; a failed build keeps the image (Docker moves the tag only after a successful build) and checks again a week later. An image built with `--pull` without a recorded digest (built before `helper.json` existed, or the registry answered without a digest) gets the current digest, without a build. A window reuses the result of its helper check for an hour. **Cleanup:** at most once a day, of the images with the label `devenv.helper=true`, except the image of the current tag, the extension removes dangling images and helper tags that no window used for 7 days (`lastUsedAt`, written at most once an hour). A helper tag that `helper.json` does not know is foreign (another extension version, possibly of another installation of VS Code such as Insiders, which has its own `helper.json`): it first gets 7 days of grace, so a helper that old windows of another extension version still use is not removed at once. A removed tag keeps a tombstone in `helper.json` for 90 days: when the tag comes back, another installation built it again and uses it, so it is not removed again, and two installations do not remove each other's helper in a loop. Tags of other repositories are never removed, and never with force; a failed removal (for example an image that a helper container uses) is logged and tried again at the next cleanup. Two windows can do this at the same time: each write of `helper.json` is atomic, and the file is advisory, so at worst a check or a build runs twice.
- **Run.** Each helper run is `docker run --rm -i` with the workspace volume at `/workspaces` and the label `devenv.helper-run=true`. Only the Dev Container CLI runs (read-configuration, build, up) also get the Docker socket and the cache volume `devenv-helper-cache` (Features cache, to verify in V-10). Git runs (clone, switch branch, Git summary) and the file-reading scripts get neither, because Git runs programs that the repository configuration names (filter drivers). Runs that need no network (Git summary, reading and listing configurations) use `--network none`.
- **Token for the clone.** The token never appears on a command line, in an environment variable of a container, or in `.git/config`. The helper receives it on standard input, writes it to a `tmpfs` mount, and a Git credential helper reads it from there. The remote URL is `https://github.com/<owner>/<repository>.git`.
- **Container-only Git** (concept section 9). At each open, before `devcontainer up` (and also when the container runs already), a helper run without the Docker socket, the cache volume, and network gets the token of the owner account on standard input (same `tmpfs` pattern) and writes `/workspaces/.devenv+/github-token` (mode 0600, replaced with a rename), creates `gitconfig` when it is missing (user.name: the GitHub profile name or the login; user.email: `<databaseId>+<login>@users.noreply.github.com`, from `viewer { databaseId login name }`, with the session account as fallback) and ensures its section `[credential "https://github.com"]` (an empty helper, then the helper of the container), creates `credentials.gitconfig` with an example in comments when it is missing (never overwritten), and creates `docker/` (mode 0700). Everything gets the numeric owner of `/workspaces/<name>`; on a first open this runs after the ownership fix, and after each creation of a container the ownership fix also covers `/workspaces/.devenv+`. A link in place of the folder or of a file is removed first. A failure is a warning; the environment opens. The question for `viewer` starts as soon as the session is known (it overlaps with the Docker start, the clone, and the image check), is shared per account in the window, has a time limit of 5 seconds, and after a failure the fallback counts for 10 minutes. When a window leaves an environment because of the account (sign-out, or another account), the controller removes the token file from the running container (`docker exec -u root … rm -f`, best effort); otherwise the file stays in the volume (on the disk of the computer) until the next open of the owner account replaces it or **Delete** removes the volume (concept section 9). After each creation of a container, `docker exec -u root` writes the `~/.gitconfig` of the remote user (`HOME_GIT_CONFIG_CONTENT`: `[credential] helper =`, then an `[include]` of `credentials.gitconfig` and `gitconfig`, for Git older than 2.32 and processes without the variables) when it is missing or empty; a file of the image with content and links stay as they are. The copy of the Git configuration of the computer is switched off only by the setting `copyGitConfig` of the container (section 8), not by this file. Then `docker exec -u <remote user> … git --version`: Git older than 2.9 gives the warning `Messages.oldGit`, Git 2.9 to 2.31 a log line, no Git nothing.
- **Ownership.** The helper clones as root. Otherwise the user in the container cannot write the files, so the extension changes the owner of the files that belong to another user (`find … -exec chown`) to the user and group of `remoteUser`: before the first `devcontainer up` of a new clone, in a short-lived container of the environment image (the remote user comes from its label `devcontainer.metadata`), because `onCreateCommand` and `postCreateCommand` run during `up` as that user; and after each creation of a container, as root in the dev container.
- **`${localEnv:NAME}`.** The values of the computer are not passed to the helper: the CLI resolves the variables in the helper, to the value of the helper for a variable that it sets itself (`HELPER_ENV_NAMES`: `HOME`=/root, `PATH`, `HOSTNAME`, `NODE_VERSION`, `YARN_VERSION`), otherwise to an empty value or to their default. The extension finds the names in the text of `devcontainer.json` and names them in one warning, which also names those that get the values of the helper.
- **Host access policy** (concept section 9, src/core/helper/hostAccess.ts): checked on the resolved configuration and the `mergedConfiguration` of `read-configuration --include-merged-configuration` before any build, and on the label `devcontainer.metadata` of the environment image before each `up` that creates a container. Before `up`, the `runArgs` of the override configuration are checked again as a whole (as Docker gets them). A refusal is `UserFacingError('hostAccess')` with each setting named: settings that need access to the computer in `Messages.hostAccess`, settings that the policy does not know (unknown flags and options, arguments that are no flag, entries that are no text) and values that it does not support (for example `--restart=always`) in `Messages.unsupportedOptions` (`hostAccessReport`). `--network container:…` is refused, also in Docker's long form `name=container:…` (CSV, keys and values in lower case). The allow-list of `runArgs` (`RUN_FLAGS`) gives a one-line reason for each flag; it follows Docker's reading of the flags (a flag that takes a value takes the next argument, also one that starts with `-`; a group of short flags such as `-it` is read letter by letter). Values are checked for `--label`/`-l` (no key with the prefix `devenv.` or `devcontainer.`: the CLI puts its id label before the `runArgs`, and Docker keeps the last label of a key; refused as not supported), `-e`/`--env` (no variable of container-only Git, `isContainerGitVariable`: `GIT_CONFIG` and `GIT_CONFIG_*`, and the names of `containerEnvironment`, with or without a value; `containerEnv` and `remoteEnv` of the repository configuration and of each entry of the image metadata are checked for the same names, but not those of the merged configuration, which for an existing container holds the values of the override configuration, also of an earlier version; the variables of the Dev Containers extension, the VS Code server, and GnuPG are not checked), `--env-file` (only a path below `/workspaces` without `..`: `docker run` reads it in the helper; its content is not checked, and Docker applies `-e` after it, so only variables that the override configuration does not set can come from it), `--stop-timeout` (at most `MAX_STOP_TIMEOUT_SECONDS` = 20, because the Session Monitor ends each Docker call after 30 seconds), `--restart` (`no`, `on-failure[:n]`), `--oom-score-adj` (0 or more), `--log-driver` (`json-file`, `local`, `none`), `--log-opt`, and `--storage-opt` (`size=`). A value flag at the end of the list is refused, because it would take the next argument that the extension adds. `--name`, `--rm`, `-i`, `-t`, and `-d` (also in groups) are removed from the `runArgs` of the override configuration with the same parser (`overrideRunArgs`), and `runUp` logs each one with its reason (`removedRunArgs`). In a container where root may not change files of the user (for example `--cap-drop ALL`), `~/.gitconfig` is written as the remote user after the run as root failed, and the controller removes the token file as the owner of `/workspaces/.devenv+` (`stat -c %u:%g`). A mount may use a volume named like the workspace volume of an environment (`ENVIRONMENT_VOLUME_PATTERN`) only when it is its own. Named volumes that belong to something else are refused (`volumeNameProblems`): the helper's cache volume; the additional volumes of the environments of other GitHub accounts, from the registry (`foreignVolumes`; an entry without owner counts once an account has taken it over); the volumes of the Dev Containers extension by their names (`vscode`, `vsc-remote-containers`, and names that end in a hexadecimal MD5 or SHA-256 hash, as its clones of repositories); and existing volumes by their labels (`volumeLabelOwner`: `com.docker.compose.*`, `vsch.*` and `dev.container.volume`, `com.docker.volume.anonymous`, `devenv.environment-id`). Before each check, the pipeline reads the labels of the named volumes of the mounts (`mountedVolumeNames`, `docker volume inspect`; no call without named volumes). `remote.localPortHost` other than `localhost` in `customizations.vscode.settings` of any source is refused, because the window applies the settings of the container (VS Code forwards on `0.0.0.0` for any other value). When the merged configuration cannot be read within 10 seconds (without a container, the CLI reads the base image and the Features, from the registries when they are not local, without the credentials of the extension), the helper container of the read is removed and the configuration is read again without it (NFR-08); the image metadata check stays. A new environment image of an update that the metadata check refuses is removed, the old container or image starts with `Messages.updateRefused`, and the refusal is stored in the registry entry (`refusedUpdate`: configuration path and hash, digests, settings); the same update is not built again until a digest or the configuration changes, or a forced rebuild. `${localWorkspaceFolder}` outside of `mounts` and `runArgs` still gets the message of concept RK-10.

## 8. Dev Container CLI calls (in the helper)

| Step | Call |
|---|---|
| Read configuration | `devcontainer read-configuration --workspace-folder /workspaces/<repo> --config <config path> --id-label devenv.environment-id=<id> --include-merged-configuration` (at most 10 seconds; then again without `--include-merged-configuration`) |
| Build environment image | `devcontainer build --workspace-folder /workspaces/<repo> --config <config path> --image-name devenv-<short id>:<n>` |
| Create or start container | `devcontainer up --workspace-folder /workspaces/<repo> --override-config <override file> --id-label devenv.environment-id=<id> --skip-post-attach` (plus `--remove-existing-container` when the container is replaced) |

- The override configuration is the complete configuration for `up` (the CLI uses it instead of the repository configuration). It contains only: `image`, `workspaceMount`, `workspaceFolder`, `runArgs` (repository values without `--name`, `--rm`, `-i`, `-t`, and `-d`, read with the parser of the policy and named in the log, `-p`/`--publish` without an address with `127.0.0.1:`, or only `--label devenv.container-config=unknown` without a readable configuration; plus `--label devenv.container-version=3` and `--name <container name>`), `appPort` (each port as `127.0.0.1:<host>:<container>`), `containerEnv` and `remoteEnv`, `customizations.vscode.settings` (`devContainersSettings`), `shutdownAction: "none"` (concept 7.6). `initializeCommand` is never passed (the policy refuses it). Everything else comes from the label `devcontainer.metadata` of the environment image; the CLI appends the properties of the override configuration as the last entry of the label of the container.
- `customizations.vscode.settings`, flat keys, as the Dev Containers extension 0.470.0 reads the settings of a container (class `kv`: the new key `dev.containers.*`, for some settings then the old key `remote.containers.*`): `dev.containers.copyGitConfig` and `remote.containers.copyGitConfig` `false` (a `false` under the new key alone falls back to the old key), `dev.containers.gitCredentialHelperConfigLocation` `none`, `dev.containers.dockerCredentialHelper` `false`, and `dev.containers.githubCLILoginWithToken` `false` (these two only under the new key). The Dev Containers extension writes the settings of all entries of the label into `~/.vscode-server/data/Machine/settings.json` at the first attach of a new container, the later entries winning (to verify in V-8). The CLI collects `customizations` of all entries, so the extensions and other settings of the repository stay.
- `containerEnv` and `remoteEnv` (merged over those of the image metadata), only documented variables of Git and Docker: `GIT_CONFIG_GLOBAL=/workspaces/.devenv+/gitconfig`, `DOCKER_CONFIG=/workspaces/.devenv+/docker`, `GIT_SSH_COMMAND=ssh -o IdentityAgent=none`, and four Git settings of the command line level as `GIT_CONFIG_COUNT=4` with `GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` (Git 2.31 and newer): `credential.helper=` (removes every credential helper of the configuration files, among them a forwarding helper that the Dev Containers extension writes with `git config --system` and `--global` when its settings of the container do not apply), `include.path=/workspaces/.devenv+/credentials.gitconfig` (the helpers of the user for other hosts), `credential.https://github.com.helper=` (removes them again for github.com), and `credential.https://github.com.helper=<helper of the container>`. Older Git gets the same through the `~/.gitconfig` of the extension. By user decision (2026-09-25), no variable of the Dev Containers extension or the VS Code server is set, blanked, or changed (`SSH_AUTH_SOCK`, `REMOTE_CONTAINERS_IPC`, `REMOTE_CONTAINERS*`, `BROWSER`, `VSCODE_*`), and neither `GNUPGHOME` nor `GIT_CONFIG_PARAMETERS`; their sockets stay usable by a process that looks for them (concept section 9, limits). No token in any variable (no `GH_TOKEN`).
- `--skip-post-attach`: the Dev Containers extension runs `postAttachCommand` when it attaches (to verify in V-1).
- All calls get `--user-data-folder /devenv-cache` (the cache volume). `up` also gets `--update-remote-user-uid-default never`, because the CLI runs as root in the helper and would otherwise build an extra image at each container creation. `build` gets `--no-lockfile` unless the repository has a `devcontainer-lock.json`, so the build does not add a file to the repository.
- The last line of standard output of `build` and `up` is a JSON result (`outcome`, `imageName`, `containerId`, `remoteUser`, `remoteWorkspaceFolder`). All other output goes to the output channel.
- When a lifecycle command fails, `up` exits with code 1 and the result `{ outcome: 'error', containerId, description: '… from … failed.' }` (to verify in V-10). If that container runs, the helper keeps it, and the open continues with a warning, as with the Dev Containers extension. The remote user then comes from the label `devcontainer.metadata` of the image.
- The config hash (`configHash`) is `sha256` of the text of `devcontainer.json` plus the text of the Dockerfile, if there is one.

## 9. Image check

- **References** (concept 7.7): `image`; each `FROM` of the Dockerfile (with `ARG` values from `build.args` and from `ARG` defaults; without references to earlier stages and without `scratch`); each Feature key that is an OCI reference. Local Features (`./…`), tarball URLs, and references with `@sha256:` are not checked.
- **Normalization:** Docker Hub is `registry-1.docker.io`, official images get the prefix `library/`, and the default tag is `latest`.
- **Request:** `HEAD /v2/<name>/manifests/<tag>` with the `Accept` types for OCI index, Docker manifest list, Docker manifest v2, and OCI manifest. The digest comes from the header `Docker-Content-Digest`.
- **Authentication:** first without credentials. On `401`, read `WWW-Authenticate: Bearer realm=…,service=…,scope=…` and request a token, with Basic credentials if Docker has credentials for this registry (`~/.docker/config.json`: `auths`, `credsStore`, `credHelpers`; credential helpers through `docker-credential-<name> get`). For `ghcr.io`, the fallback is the GitHub session with the scope `read:packages`, requested only when needed (concept 7.7). The `docker pull` of such an image uses the same session: the extension writes it to a temporary Docker config folder (`docker --config`, mode 0700, removed after the pull) and passes the endpoint of the current Docker context as `DOCKER_HOST`.
- **Time limit:** all requests of one connection run in parallel under one `AbortController` with 5 seconds (NFR-08). If one registry does not answer, the whole update step is skipped (FR-13).
- **Proxy:** use the Node.js `https` module. VS Code applies its proxy settings to this module in the extension host.
- **Build record:** it stores the digests that the check read right before the build. The comparison uses the build record, not the local images (concept 7.7).

## 10. Git operations

| Purpose | Commands (in the helper on the volume, or with `docker exec` in a running container) |
|---|---|
| Branch | `git branch --show-current` |
| Uncommitted files | `git status --porcelain` (count of lines) |
| Unpushed commits | `git rev-list --count HEAD --branches --not --remotes` (HEAD and all local branches, so it includes branches left by Switch branch…, concept 7.5 / 7.14 step 1; with an unborn HEAD only `--branches`) |
| Stashes | `git stash list` (count of lines) |
| Switch branch | `git fetch https://github.com/<owner>/<repository>.git '+refs/heads/*:refs/remotes/origin/*'` (the same result as `git fetch origin`, but a changed remote in `.git/config` cannot redirect the token), then `git switch <branch>` |

## 11. Connection to the container

- Folder URI: `vscode-remote://attached-container+<hex of {"containerName":"/<container name>"}><remoteWorkspaceFolder>` (to verify in V-2).
- Open with `vscode.openFolder` and `forceNewWindow: false`, always in the current window.
- "Close Remote Connection" is the command `workbench.action.remote.close`.

## 12. Session Monitor

- Start: `child_process.spawn(process.execPath, [<dist/sessionMonitor.js>, <global storage path>], { detached: true, stdio: "ignore", env: { ...process.env, ELECTRON_RUN_AS_NODE: "1" } })`, then `unref()`.
- The decision logic (rule 1, rule 2, sleep rule of concept 7.9) is a pure function in `src/monitor/rules.ts`, with unit tests for every row of the table "Results for typical situations".
- A process is alive if `process.kill(pid, 0)` does not throw `ESRCH`.
- The Session Monitor never starts Docker. If `docker info` fails, no container runs, and it does nothing.

## 13. User interface

- Texts: exactly the texts of the concept where it gives them (section 6.5), plain language (NFR-02).
- Progress: one notification with the steps of concept 6.5, and a button **Show details** for the output channel "Dev Environments".
- Tree: groups by owner, rows as in concept 6.2. `contextValue` lists the possible actions, for example `repository;canStart;canDelete;multiConfig`, and the menus use `viewItem =~ /canStart/`.
- The sidebar, Search, and the switcher get only the environments of the signed-in account (`availableEnvironments`); without a sign-in, the view is empty and shows the welcome view with the sign-in. A listed repository with an environment of another account is a row like any repository without environment: Start creates the environment of the signed-in account (D-3). On an account change (`authentication.onDidChangeSessions`), a window connected to an environment that the account may not use closes its remote connection at once (after a sign-out with `ControllerTexts.signedOutConnection`), removes the token from the running container, and checks after about 10 seconds (`LEAVE_CHECK_MS`) whether it is still attached: then a modal message, and the close again. When the account may use the environment again, the window reloads instead. A restored window whose container has no current `devenv.container-version` and whose open pipeline fails leaves the container the same way; Start on such a connected container does too. The view loads the stored list of the new account.
- Sign-in state: `auth.ts` alone sets the context key `devEnvironments.signedIn` (welcome view **Sign in with GitHub**). Signed in means a session with `repo read:org` exists and GitHub did not reject its token. Every GitHub caller reports an HTTP 401 to `reportRejectedToken`: `GitHubApi` (`onUnauthorized`, all GraphQL requests: the repository list, branches, single repositories, the identity of the container Git), the clone and the fetch of Switch branch (Git "Authentication failed" for github.com, `isGitHubTokenRejected`), and the token service of ghcr.io for the GitHub session (`RegistryClient.onCredentialsRejected`). The rejection is kept per scope set and session (ID and token), and cleared by a session with another ID or token or by a request that succeeds (`reportAcceptedToken`). While it holds, an interactive request, for example the unchanged command `devEnvironments.signIn`, calls `getSession(…, { forceNewSession: true })` instead of `createIfNone`, which would return the rejected session without a dialog. Workaround for VS Code keeping such a session; remove it when VS Code handles it. The button, the welcome texts, and the sign-in row are unchanged; the account and its environments stay available, and the one-time warning with the action **Sign in** (`SIGN_IN_AGAIN_DETAIL`) stays.
- While an environment is Updating, Start, Stop, and Rebuild are hidden (concept 7.9 rule 1). Delete stays (concept 7.15), except while the operation is itself a delete: after the confirmations, it waits until the operation of the other window has ended, in a progress notification with Cancel.
