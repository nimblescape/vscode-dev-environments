## Why (user report)
The user has two GitHub accounts, scalarion and staussh. An environment of the private repository majikmate/module-ts was created with scalarion. After signing out of scalarion and signing in to VS Code as staussh (no access to that repository), the user could still open the environment, commit, and push — the push was authenticated as scalarion, because the Dev Containers extension forwards the container's Git credential requests to the Mac's Git credential helper (`gh auth git-credential`, gh is signed in as scalarion), and it copies the Mac's ~/.gitconfig (identity scalarion@nimblescape.com) into the container.

## Decisions of the user (they change the concept; update it)
1. **An environment belongs to the GitHub account that created it. Environments of another account are never available** — not listed, not startable, not connectable, not in the switcher/search/reopen — to the account that is signed in.
2. **The container never uses the Mac's Git.** No copied ~/.gitconfig, no forwarded Git credential helper, no forwarded Docker credentials, no forwarded SSH agent, no forwarded GPG agent — everything Git needs comes from the container/volume.
3. **Git credentials: the extension puts the owner account's GitHub token (the VS Code GitHub session of that account) into the environment**, like GitHub Codespaces. This replaces NFR-03 "The extension stores no secrets" for this token.
4. **The forwarding is switched off per environment inside the container** (the global Dev Containers settings stay unchanged, so the user's other dev containers keep working). Git in the environment ignores the forwarded files and helper; the forwarded helper, the SSH agent socket and the Dev Containers IPC socket still exist in the container — document them as a known limit.
5. **No access to the host except the network.** The container may use the network (internet, LAN, services on the Mac; a repository may use `--network host`). Ports of the container reach the Mac only on localhost: VS Code port forwarding (localhost), and ports that the configuration publishes itself (`appPort`, `-p`/`--publish`) are bound to `127.0.0.1` (the extension adds `127.0.0.1:` when no address is given; an explicit non-loopback address is refused). Everything else that gives the container access to the host is REFUSED with a clear message (see section 2b).
6. **Enforce everything possible; document the channels that the Dev Containers extension and VS Code open by design** (SSH agent socket `/tmp/vscode-ssh-auth-*.sock`, the IPC socket `REMOTE_CONTAINERS_IPC` with `$BROWSER`/`code`, VS Code's remote API: clipboard, open URL, commands of local extensions, sign-in requests with consent). Full isolation needs a boundary outside the container (separate macOS user, VM, Docker Enhanced Container Isolation).

## 1. Account ownership
- `Environment.owner?: { id: string; login: string }` (GitHub numeric user id as string = `session.account.id`, and the login = `session.account.label`). Set at creation. New volume label `devenv.owner-id=<id>` at creation, so `reconcileFromVolumes` restores the owner.
- Current account: `GitHubAuth` gets `getAccount(options: { interactive: boolean }): Promise<{ id: string; login: string } | undefined>` (from the same session as `getToken`). Not signed in → no account → NO environment is available (the list shows only the sign-in welcome/row).
- A pure function `isAvailableTo(environment, account)` in src/core: `owner` set → `owner.id === account.id`. Legacy entries without `owner` (the user's two existing environments): available only after a claim — the claim succeeds only if `discovery.getRepository(repo, token)` of the current account returns the repository (the account has access on GitHub); then `owner` is written (and the volume keeps working; the label cannot be added to an existing volume — that's fine, the registry holds the owner). Until claimed, a legacy environment is hidden. Run the claim check after each successful discovery refresh, for legacy entries only, serialized; network errors → stay hidden.
- Apply the rule EVERYWHERE: sidebar model (treeModel input: only available environments; do not show names of hidden ones, do not show a count that reveals them), switcher, search, the Start/Stop/Delete/Rebuild/Switch branch/Select configuration flows (refuse with a plain message if called with another account's environment), reopen at startup (7.10 #2), restored windows (role A: a window attached to another account's container → do NOT run the pipeline, do not start the container; close the remote connection and show a short message), status bar Reconnect, pending operations (`operations/*.json` of another account's environment are not run by this window; they expire as today), disconnect requests.
- The stored discovery data contains repository names of one account: store it per account (`repositories-<accountId>.json` — update StoragePaths) and never show another account's list. Delete the old shared `repositories.json` on first run (or ignore it).
- Account change while running (`vscode.authentication.onDidChangeSessions`, or the account returned changes): if this window is connected to an environment that is not available to the new account → close the remote connection at once (Close Remote Connection) and show a message; refresh the sidebar for the new account. The Session Monitor then stops the container after the waiting time (unchanged).
- The Session Monitor is not account-aware (it only stops containers); unchanged.

## 2. Container-only Git (per environment)
Config folder in the workspace volume (persists across rebuilds, removed with Delete): `/workspaces/.devenv+/` — a name that a GitHub repository name can never have (repository names only allow `[A-Za-z0-9._-]`), so it cannot collide with the repository folder `/workspaces/<name>`. Contents:
- `gitconfig` — the container's global Git config. Created if missing (keep user edits otherwise), owned by the remote user:
  ```
  [user]
      name = <GitHub profile name, or the login>
      email = <databaseId>+<login>@users.noreply.github.com
  [credential "https://github.com"]
      helper =
      helper = "!f() { test \"$1\" = get || exit 0; echo username=x-access-token; printf 'password=%s\n' \"$(cat /workspaces/.devenv+/github-token)\"; }; f"
  ```
  (identity from the GitHub API `viewer { databaseId login name }` with the owner's token, at creation; an existing file is not changed except that the credential section is ensured.)
- `github-token` — the owner's token, mode 0600, owned by the remote user. Written/refreshed by the extension at EVERY open (the session token can change after a new sign-in), BEFORE `devcontainer up` (so lifecycle commands can use it), through the workspace helper with the token on STDIN (never on a command line or in an environment variable of a container; reuse the existing secrets/tmpfs pattern and the clone script conventions), chown to the owner of the repository folder (numeric uid:gid of `/workspaces/<name>`, which the ownership fix already sets to the remote user). The file is removed by Delete (volume removal).
- `docker/` (DOCKER_CONFIG) and `gnupg/` (GNUPGHOME, mode 0700): empty container-owned folders.
Environment variables for everything in the container — add to the override configuration of `devcontainer up` (this extends the fixed property list of notes section 8; update the notes) as BOTH `containerEnv` (all processes incl. lifecycle commands and `docker exec`) and `remoteEnv` (VS Code server, terminals — the Dev Containers extension may set some of these itself):
  - `GIT_CONFIG_GLOBAL=/workspaces/.devenv+/gitconfig` → Git ignores ~/.gitconfig, where the Dev Containers extension copies the Mac's config and writes its forwarding credential helper.
  - `DOCKER_CONFIG=/workspaces/.devenv+/docker` → the forwarded Docker credential helper in ~/.docker/config.json is not used.
  - `GNUPGHOME=/workspaces/.devenv+/gnupg` → the forwarded GPG agent socket in ~/.gnupg is not used.
  - `GIT_SSH_COMMAND=ssh -o IdentityAgent=none` and remoteEnv `SSH_AUTH_SOCK` set to an empty value → the forwarded SSH agent is not used by Git.
  - `GH_TOKEN` is NOT set (no token in environment variables); gh CLI inside the container is out of scope.
- Additionally, before the first attach, create an EMPTY `~/.gitconfig` for the remote user in the container if none exists (the Dev Containers extension "will not overwrite an existing Git configuration file", so the Mac's config is not even copied). Do this with `docker exec -u root` right after a container is created (the pipeline already runs the ownership fix there). (Changed after the review: an empty file does not stop the copy, because the Dev Containers extension copies unless the file has a section other than `[filter]`/`[safe]`. The extension writes `HOME_GIT_CONFIG_CONTENT` instead: `[credential] helper =` and an `[include]` of the volume's configuration.)
- Existing containers were created without these variables: give new containers a label `devenv.container-version=2` (via runArgs `--label`); when the pipeline finds a container without this label (or an older value), it recreates it from the existing environment image (`up --remove-existing-container`, no build, the volume is kept — like the "no container" path). Test this.
- Mark with `// Assumption (V-8)` what must be verified in real VS Code (that the Dev Containers extension applies remoteEnv from the label and does not override these variables; that `git push` from the Source Control view and the terminal uses the container's helper).

## 2b. Host access policy (enforced before every build and before every `up`)
Check the MERGED configuration (use `devcontainer read-configuration --include-merged-configuration` in the helper and read `mergedConfiguration`, which includes the metadata of Features and of the base image; also check the repository configuration itself, and the build options). Refuse with a plain message that names each offending setting, e.g. "This configuration needs access to your computer, which Dev Environments does not allow: bind mount /Users/…, privileged mode. Change the configuration of the repository." (new code 'hostAccess'; message text in messages.ts). Do not change anything silently. Rules:
- `mounts` (string and object form): only `type=volume` and `type=tmpfs` are allowed. `type=bind` (also a string without `type` whose source is a path) → refused. A volume whose source is another environment's volume (`devenv-…` other than its own) or `devenv-helper-cache` → refused. (Changed after the review: "another environment's volume" means a name like a workspace volume, `ENVIRONMENT_VOLUME_PATTERN` = `devenv-<name>-<8 hex>`; other `devenv-*` volumes of a repository are allowed.)
- `runArgs`: refused: `--privileged`; `-v`/`--volume` with a host path (a named volume `name:/path` is allowed, same volume rules as above); `--mount` with `type=bind`; `--device`, `--device-cgroup-rule`, `--gpus`; `--pid=host`, `--ipc=host`, `--uts=host`, `--userns=host`, `--cgroupns=host`; `--volumes-from`; `--cap-add` with anything other than `SYS_PTRACE`; `--security-opt` other than `seccomp=unconfined`; `-p`/`--publish` with a non-loopback address; `-P`/`--publish-all` (publishes on all addresses). Allowed: `--network`/`--net` (including `host`), `--add-host`, `--dns*`, `--init`, `--label`, `--hostname`, `--env`/`-e`, `--env-file` (read from the volume), `--shm-size`, `--ulimit`, `--memory*`, `--cpus`, `--user`, `--workdir`, `--cap-add SYS_PTRACE`, `--security-opt seccomp=unconfined`. Unknown flags → refused (conservative), listed in the message.
- Merged properties: `privileged: true` → refused (e.g. docker-in-docker); `capAdd` other than `SYS_PTRACE` → refused; `securityOpt` other than `seccomp=unconfined` → refused; `mounts` from Features (e.g. docker-outside-of-docker's Docker socket bind) → refused by the mount rule.
- `initializeCommand` (repository or merged) → refused (it would run in the workspace helper, which has the Docker socket). Remove the `initializeCommand` passing from the override configuration (notes 8 currently passes it).
- `build.options` (docker build options): refused: `--secret`, `--ssh`, `--allow` (entitlements), `--build-context` with a host path, `--output`/`-o`. Allowed: `--network` (including `host`), `--add-host`, `--build-arg`, `--target`, `--label`, `--platform`, `--pull`, `--no-cache`. Unknown options → refused.
- `appPort`: numbers/`"8080:80"` → bound to 127.0.0.1 in the override (`"127.0.0.1:8080:80"`); an explicit non-loopback address → refused.
- `${localEnv:NAME}`: values of the Mac are NO LONGER passed to the helper (change notes 7 `${localEnv:NAME}` and the code in workspaceHelper/pipeline). The CLI then resolves them to empty/default. Show one warning naming the variables that stay empty.
- Replace the RK-10 "computer dependent" warning where it overlaps (bind mounts are now refused, not warned).
- Apply to first open, open, update, rebuild, select configuration, switch branch (the next open checks the configuration of the new branch). An existing environment whose configuration is refused keeps its volume; Start shows the message and does nothing else (NFR-07). Tests for every rule (pure function in src/core, table-driven).
- The GPG agent is forwarded by the Dev Containers extension only when the container has no private keys: put a placeholder file into `/workspaces/.devenv+/gnupg/private-keys-v1.d/` (GNUPGHOME) so it does not forward (// Assumption (V-8), verify). The SSH agent socket and the IPC socket cannot be switched off — documented limit.
