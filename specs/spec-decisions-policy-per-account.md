## Decision 1 — runArgs: extend the allow-list (user decision, 2026-09-25)
Allow the flags that give NO access to the Mac. At least:
- `--platform` (e.g. `linux/amd64` on Apple silicon)
- `--cap-drop` (any value), `--read-only`, `--security-opt no-new-privileges` / `no-new-privileges:true` / `no-new-privileges=true`
- `--tmpfs <container path>[:options]` (a tmpfs inside the container; no host path is involved)
- `-i`, `-t`, `-it`, `-ti`, `--interactive`, `--tty` (harmless; the CLI runs detached)
- further flags that the analysis classifies as safe (e.g. `--group-add`, `--pids-limit`, `--stop-signal`, `--stop-timeout`, `--expose`, `--health-*`, `--oom-score-adj`), each with a one-line reason in the code table
- `--rm`: NOT refused, but REMOVED from the runArgs passed to `devcontainer up`, with a log line — the extension manages the container life cycle (stop/start, recreation); `--rm` would delete the container at every stop.
Still refused (unchanged): bind mounts / `-v`/`--mount` of host paths, `--device*`, `--gpus`, `--privileged`, `--pid|--ipc|--uts|--userns|--cgroupns=host`, `--volumes-from`, `--network container:<x>` (joins another container's network, e.g. another environment's services), `--cap-add` other than SYS_PTRACE, `--security-opt` other than `seccomp=unconfined` and no-new-privileges, `--runtime`, `--volume-driver`, `--env-file` outside the workspace volume, unknown flags. Table-driven tests for every added flag and for `--rm` removal. Concept section 9 "Host access" and notes updated.

## Bug 3 — "Sign in with GitHub" cannot replace a token that GitHub rejects (user report, 2026-09-25)
Observed in the Extension Development Host: VS Code has a GitHub session with the scopes `repo read:org` for the extension, but GitHub answers `401 Bad credentials` for its token (revoked/outdated, e.g. after the user signed out and in with other accounts). The sidebar shows the "Sign in with GitHub" welcome, and the log says "GitHub API request failed with HTTP status 401: Bad credentials". The one-time warning (sidebar.ts `offerSignInAgain`, text SIGN_IN_AGAIN_DETAIL) uses `forceNewSession` and works, but it is shown only once per window and is easy to miss. The sidebar button / command `devEnvironments.signIn` calls `getSession(..., { createIfNone: true })`, which returns the SAME rejected session without a dialog — so the button can never fix it, and the refresh fails again (loop).
Required (user decision 2026-09-25: the button keeps its name — "we do not change the name of the GitHub sign-in button; the button will vanish as soon as the VS Code bug is fixed"):
- NO new label, NO new welcome text, NO new context key or view state for a rejected token: the welcome view and the sign-in row keep "Sign in with GitHub" exactly as today.
- Behind the unchanged button/command `devEnvironments.signIn`: remember that GitHub rejected the token of the current session (per session id); while it is rejected, the command calls `getSession(..., { forceNewSession: true })` (no custom detail text needed) instead of `createIfNone`, so the user gets a new token; the remembered state clears when a session with another id/token arrives or a request succeeds. Mark it with a comment: workaround for VS Code keeping a GitHub session whose token GitHub rejects; remove when VS Code handles it.
- `devEnvironments.signedIn` is set in ONE place with one meaning (today auth.updateContextKey and sidebar.setSignedIn both set it, with different conditions); a session whose token GitHub rejected does not count as signed in, so the existing "Sign in with GitHub" welcome shows.
- Every GitHub caller that gets a 401 (discovery refresh, listBranches, getRepository, clone, image check for ghcr via the session, the container Git token) reports it to that one place, not only the sidebar refresh.
- The one-time warning `offerSignInAgain` (sidebar.ts) may stay as it is.
- Tests (fake vscode): 401 → signedIn false → signIn uses forceNewSession → new session → refresh runs; labels and welcome texts unchanged.

## User decision (2026-09-25): never override variables that belong to Dev Containers or the VS Code server
Reason (user): Dev Containers and the VS Code server expect their own variables to be set correctly; their behavior is not defined when the extension blanks or changes them.
- Do NOT set, blank, or change variables that Dev Containers or the VS Code server own: REMOTE_CONTAINERS_IPC, SSH_AUTH_SOCK, BROWSER, VSCODE_*, REMOTE_CONTAINERS, REMOTE_CONTAINERS_SOCKETS, REMOTE_CONTAINERS_DISPLAY_SOCK, and any other variable they set. Remove the committed remoteEnv SSH_AUTH_SOCK='' and do NOT add REMOTE_CONTAINERS_IPC=''.
- Do NOT rely on internal behavior to switch features off: remove the GPG placeholder file in private-keys-v1.d (it exploits an internal skip rule); keep GNUPGHOME only if it serves a purpose without the placeholder, otherwise remove it too.
- Switch Dev Containers features off ONLY through their documented settings, per container in the override configuration's customizations.vscode.settings (dev.containers.copyGitConfig / remote.containers.copyGitConfig false, dev.containers.gitCredentialHelperConfigLocation "none", dev.containers.dockerCredentialHelper false, dev.containers.githubCLILoginWithToken false); the per-container reading is verified in the installed code, not documented: mark it // Assumption (V-8) and list it for the live check.
- Keep only the tools' own documented variables where they are needed: Git (GIT_CONFIG_GLOBAL, GIT_CONFIG_COUNT/KEY/VALUE, GIT_SSH_COMMAND with IdentityAgent=none so Git ignores the SSH agent) and Docker (DOCKER_CONFIG) — they change only where these tools read their configuration.
- Document as limits (docs/container-restrictions.md, concept section 9): the IPC socket, the SSH agent socket and the GPG agent socket still exist and can be used by a process that looks for them; Git does not use them.
- Reviewers: treat any override of a Dev Containers or VS Code server variable, and any reliance on an internal skip rule, as a defect.
