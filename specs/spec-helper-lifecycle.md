## Part 1 — CLI version as a pinned devDependency (tooling)

1. `package.json` devDependencies: `"@devcontainers/cli": "0.89.0"` (EXACT version, no ^/~). `npm install` (updates package-lock.json). The package has no dependencies. It is NOT shipped (vsce --no-dependencies; .vscodeignore excludes node_modules) and NOT bundled.
2. `scripts/cliVersion.mjs`: `export function devcontainerCliVersion()` reads package.json, returns the devDependency version, and throws a clear error if it is missing or not an exact `x.y.z` version.
3. Global compile-time constant `__DEVCONTAINER_CLI_VERSION__` (declared in `src/types/globals.d.ts`; make sure tsconfig includes it): esbuild.mjs `define` for the extension bundle; vitest.config.ts `define` too (and the docker vitest config of part 3).
4. helperImage.ts: `export const DEVCONTAINER_CLI_VERSION: string = __DEVCONTAINER_CLI_VERSION__;` with a doc comment saying where the version comes from and that a bump changes the helper tag, so every user's helper is rebuilt at first use.
5. Tests (`npm test`, no Docker): 
   - the constant equals package.json's devDependency and the version of the installed `node_modules/@devcontainers/cli/package.json`;
   - **contract tests against the real CLI package** (`src/core/helper/devcontainerCli.contract.test.ts`): run `node node_modules/@devcontainers/cli/devcontainer.js <command> --help` for `read-configuration`, `build`, `up`; collect every `--option` that OUR arg builders (readConfigurationArgs/buildArgs/upArgs in devcontainerCli.ts) and the helper scripts (e.g. `--no-lockfile` in scripts.ts BUILD_SCRIPT) emit — derived from the builders' actual output, not a hand-written list — and assert each option is documented by that command's help. Also assert the lifecycle-failure text that `isLifecycleCommandFailure` matches still exists in the CLI bundle (find the message template in `node_modules/@devcontainers/cli/dist/spec-node/devContainersSpecCLI.js`, build an example description from it, assert the function accepts it). Prove the tests bite: temporarily rename an option in a builder → test fails (then revert).
6. `.github/dependabot.yml`: npm ecosystem weekly; `@devcontainers/cli` in its own PR (a group for the other devDependencies is fine); github-actions ecosystem weekly.
7. `.github/workflows/ci.yml`: on push to main and pull requests. Job `test` (ubuntu-latest, Node 20 = VS Code 1.90's runtime): `npm ci`, `npm run typecheck`, `npm test`, `node esbuild.mjs --production`, `npm run package`. Job `docker` (ubuntu-latest, Docker Engine is preinstalled): `npm ci`, `npm run test:docker`. Use the current major versions of actions/checkout and actions/setup-node (check with `git ls-remote --tags https://github.com/actions/checkout` / setup-node). Minimal permissions (`contents: read`).
8. implementation-notes.md section 2, row "Runtime dependencies": the CLI stays a helper-only tool; package.json lists it as an exact devDependency only to pin the version, so Dependabot proposes updates and the contract tests + `npm run test:docker` check a new version before a release.

## Part 2 — Helper image refresh and cleanup (src/core)

State file `<global storage>/helper.json` (add `helperState` to `StoragePaths`; atomic writes via atomicJson; tolerate a missing/invalid file). Shape:
```ts
interface HelperState { version: 1; images: Record<string /* tag */, { baseImage?: string; baseDigest?: string; builtAt?: string; checkedAt?: string; lastUsedAt?: string }> }
```
Behavior of `WorkspaceHelper.ensureImage` (keep its signature; add optional deps: `statePath?: string`, `baseDigest?: (reference: string, signal?: AbortSignal) => Promise<string | 'unreachable' | undefined>`, `clock?`; without them it behaves as today):
1. Tag as today. Base image reference = `extractBaseImages(dockerfileText)` (src/core/imageCheck/dockerfile.ts — it resolves `ARG BASE_IMAGE=…` defaults), first entry.
2. Tag missing → build with `--pull` (so a new helper uses the current base), then record `baseImage`, `baseDigest` (from `baseDigest()` — skip when unreachable/undefined), `builtAt`, `checkedAt`. Without `--pull` when the registry is unreachable, and again without it when the build with `--pull` fails (pull limit, rejected stored credentials, daemon proxy); such a build records `builtWithoutPull` and no digest, and the next check that gets a digest asks for a `--pull --no-cache` rebuild.
3. Tag present and `checkedAt` missing or older than 7 days (and `attemptedAt` missing or older than 1 day) → `baseDigest(base)` in the background, with its own 5 s limit, so it overlaps with the image check and the open never waits for it (NFR-08); offline → 'unreachable' → keep the image, do NOT update checkedAt, write `attemptedAt`, so the check runs again at most once a day. Only `ensureImage` of the open pipeline does this, and only with `updateImagesOnConnect` on; helper runs only build a missing tag. The result is recorded; a rebuild that it asks for (`latestBaseDigest`) runs at the next ensure:
   - equal to the recorded digest → `checkedAt = now`.
   - no recorded digest (image built before this feature) → record the digest, `checkedAt = now`, no rebuild.
   - different → rebuild the SAME tag with `--pull --no-cache` (fresh base, fresh Debian packages, fresh Docker CLI), record the new digest/builtAt/checkedAt; then remove the previous image ID if it is dangling now (`docker image rm <id>`, never force, ignore failures). A failed rebuild keeps the old image (docker only moves the tag on success): log a warning, set `checkedAt = now` (retry next week), continue with the old image.
   Report progress through the existing `onOutput`; the pipeline already shows the detail "The workspace helper is being prepared…" when the build prints output.
4. `lastUsedAt[tag] = now` (write at most once per hour).
5. Cleanup, at most once per day (`lastCleanupAt` in the state file), after a successful ensure: list images with the label `devenv.helper=true` (including dangling ones). For each image whose ID differs from the current tag's image ID: dangling (no tag) → remove; tag known in the state with `lastUsedAt` older than 7 days → remove and delete its state entry; tag unknown → add it with `foreignSince = lastUsedAt = now` (starts a 7-day grace period, so a helper of another extension version that is still in use — e.g. old windows during an update — is not removed at once). A removed tag keeps a tombstone (`removedAt`, 90 days): when it comes back, another installation with its own helper.json (VS Code Insiders) built it again and uses it, so it is not removed and rebuilt in a loop. Never use force; failures are logged and ignored. Only images with the label `devenv.helper=true` are ever removed.
6. Two windows may do this at the same time: at worst a duplicate build; state writes are atomic, the state is advisory. Document this.

Docker adapter (src/core/docker/containerAdapter.ts): `buildImage` gains `pull?: boolean` and `noCache?: boolean`; new `listImagesByLabel(label: string): Promise<Array<{ id: string; tags: string[]; createdAt: string }>>` (include dangling, `docker images -a`? no: `docker image ls --filter label=… --no-trunc --format '{{json .}}'` shows dangling as `<none>`); `imageId(reference): Promise<string | undefined>`. Tests with the fake runner.

Wiring (src/vscode/extension.ts): pass `statePath: paths.helperState` and a `baseDigest` function built from the SAME RegistryClient/credentials the image check uses (`parseImageReference` + `client.getDigest` under a 5 s AbortController; map `unreachable`/timeout → 'unreachable', other non-digest results → undefined).

Tests (no Docker): state transitions for each case above with a fake docker + fake clock; cleanup never touches the current image, removes dangling and expired, starts grace for unknown tags, runs at most daily; failed rebuild keeps the old image; offline does not update checkedAt.

implementation-notes.md: section 4 table row `helper.json`; section 7 "Tag" bullet: add the refresh (weekly base digest check, rebuild with `--pull --no-cache` when the base changed) and the cleanup (other helper images unused for 7 days, dangling ones).

## Part 3 — Docker integration tests (`npm run test:docker`)

- `vitest.docker.config.ts` (include `test/docker/**/*.test.ts`, `fileParallelism: false`, long timeouts, same `define`), script `"test:docker": "vitest run --config vitest.docker.config.ts"`, tsconfig includes `test/**/*.ts`. `npm test` must NOT run them.
- Port the scratchpad smoke harness (smoke/run.ts) into proper vitest tests with the REAL core modules and real Docker, but FAST enough for CI (target < 5 minutes on a warm machine):
  - clone scenario: `WorkspaceHelper.clone` of a small PUBLIC repository (default `microsoft/vscode-remote-try-node`, override with env `DEVENV_TEST_REPOSITORY`) with a dummy token, then `listConfigurations` / `readConfigFiles` (no build of that repository);
  - pipeline scenarios on a SEEDED environment (volume + registry entry + a git repository created in the volume through the helper) whose `.devcontainer/devcontainer.json` uses a tiny image (e.g. `alpine:3.22`, with `"remoteUser": "guest"` so the ownership fix runs): first open → build `devenv-<short>:1` + up; stop records the git summary; open again up to date → no build; simulated newer digest → pull + build `:2` + container replaced, untracked file kept, old image removed; offline (failing HttpTransport) → info message + start within the 5 s limit; container removed outside → recreated offline; safety check + delete removes container, images, volume, registry entry.
  - helper refresh/cleanup against real Docker with a TINY test Dockerfile (e.g. `FROM alpine:3.22` + `LABEL devenv.helper=true`, own temp path → its own tag): digest change → rebuild of the same tag; a labeled dummy old image with an expired `lastUsedAt` is removed; an unknown tag gets a grace period and stays.
- Mandatory cleanup in `afterAll` (also on failure) of every container, volume and image the tests created (track them; never touch other objects of the user). The real helper image may stay.
- Run `npm run test:docker` for real at the end and report the timings.
